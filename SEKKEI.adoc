== 何のために作ったか — 混ざっていた物を分ける(2026-08-18 発注者)

発注者「officework を何のために作ったかがよくわかるでしょう。
xlsm、microsoft がごった煮にしていたものを整理。
プログラム、テンプレート、文書データ、数値データ、画像等を分離した」。

*これが一番上の答えである。* 下の「目的は2つ」も、その下の決めも、全部この1行から出ている。

[cols="1,1,1"]
|===
|中身 |xlsm / docx が入れていた所 |officework の置き場

|プログラム |ブックの中(VBA・マクロ) |`~/.config/officework/` の `.py`
|テンプレート(見た目) |ブックの中(styles.xml) |フォルダの `テンプレート.toml`
|文書のデータ |ブックの中 |`.adoc`(字だけ)
|数のデータ |ブックの中 |`.adoc` の表、大きければ `parquet`
|画像 |ブックの中(zip の中の binary) |隣のファイル(`images/`)
|===

*分けると何が起きるか。*

* *開いた瞬間に他人のコードが走らない。* プログラムがファイルの中に無いから
* *差分が読める。* 字のファイルなので、git で「どこを直したか」が見える
* *見た目を配れる。* テンプレートを1枚渡せば、書いた人の文書ぜんぶが揃う
* *大きいデータが軽い。* 10万行で parquet 0.24 MB(xlsx 2.08 MB)
* *写真で膨らまない。* 119 升の xlsx が 2.9 MB になるのは、中に写真が入っているから

*ごった煮の代償は互換性ではなく、中が見えないことだった。* 1つの zip に全部入れると、何が入っているのか開くまで分からず、開くと走る。
分ければ、どれが何かがファイルの名前で分かる。

=== Microsoft の罪、と言えるか

*形式が悪いのではない。* OOXML は公開された規格(ECMA-376)で、Office.js もGraph API もある。
だから「閉じているから繋がらない」は正しくない。

*繋がらない本当の理由は、1つのファイルに全部入れたことである。*

* プログラムが中にあるので、*開くことが危ない*。だから配る側も受け取る側も止める(`.xlsm` は多くの職場でメールを通らない)
* 見た目と中身が同じ zip にあるので、*取り出すのに必ずライブラリが要る*。Web からは直に読めない
* 字のファイルでないので、*差分が出ない*。git に置けず、レビューもできない

**officework がやったのは、規格を作り直すことではなく、置き場を分けたこと**である。
分けた結果、繋ぎ先ごとに要るのは「読み手」ではなく「書き出し」だけになった。

== 目的は2つ、向きが逆(2026-08-13 発注者確定)

*第一: Python を用いて Office を自動操作する*(Python → Office)。
他のすべて(2つのアプリ・エンジン・互換の顔)はこの線の上に並ぶ:

* *エンジン*(`pip install officework`)が主役 — xlsx / docx を書式ごと壊さずに読み書きし、openpyxl・python-docx・xlwings の書き味を継ぐ(0.2.0 の「三つの顔」がこの線)
* *writer と calc は、自動化の結果を見ながら整える面* — 人が確かめ、手で仕上げ、起動中のブックを Python から直に操る相手にもなる(ops の言葉は Python もアプリも同じ意味で使う)
* ayumi の目標「移行の壁を消す」との関係: 壁の最大の物は VBA と手作業の帳票運用で、その置き換えの答えが Python 自動化。だから「ブックはコードを運ばない・コードは .py」も、この目的の形そのもの

*第二: Office から Python を利用する*(Office → Python)。
セルの式が plugins の Python 関数を呼び(`=倍(A1)`、2次元はスピル)、パネルの `@名前` が手続きを回し、グラフ・ピボット・ソルバーのボタンの裏で matplotlib・polars・scipy が働く — Python in Calc の側。

*出自*: 発注者が 2018-12-24 に書いた記事「https://qiita.com/yniji/items/b38bc312e860027108ac[ExcelにPythonが搭載?その後 — xlwings を使おう]」。
Microsoft の「Excel に Python」は実現せず、記事は xlwings で**「Excel から Python を利用する」ことを「メインの使い方」**と呼び、マクロと UDF(動的配列で複数セルへ)を勧めた。
officework はその答え合わせ — 8年後に自分の calc へ本搭載した(python.ja.adoc「UDF とスピル」、続編は docs/articles/excel-python-sonogo-2026.ja.adoc)。

以下の各節(2本のアプリ・ネイティブファースト…)は目的ではなく**手段の決め**として読む。

== Office を一つのソフトにしない(2026-08-02 確定)

文書は *writer*(docx互換)、表は *calc*(xlsx互換)。
**別のバイナリ**にする。
共有するのは書式(docx/xlsx)と核(kumihan/sheet)だけで、アプリは分ける。
巨大なスイートにしないほうが、小さく作れて検査もできる。

範囲は「Euro-Office ができている程度」で十分。
凝った機能は要らない。
*VBA 型のマクロは実装しない* — 「開く=実行」という攻撃経路を持たない(aiseed-migration-kit DESIGN.md §5 と同じ思想)。
コードの持ち運びはPython in Calc が担う(2026-08-04 改訂): ブックにコードを**載せられる**が、開いても決して自動実行せず、実行は明示の操作+サンドボックス(サンドボックス)の中だけ。
詳細は「Python in Calc」の節。

*↑の Python の姿は改めた(2026-08-09)* — いまは**ブックはコードを一切運ばない**(`@save` も joPython.xml への書き込みも廃止)。
コードは``~/.config/officework/plugins/*.py`` にだけあり、セルは `=倍(A1)` の普通の関数呼び出し。正は link:docs/sekkei/python.ja.adoc[docs/sekkei/python.ja.adoc] の「↑をさらに狭めて」の節。「開く=実行を持たない」という芯は変わっていない —むしろ「載せられるが走らせない」から「載せられない」へ強くなった。

== 前提の確定(2026-08-02)

* Euro-Office のデスクトップ版(DesktopEditors)は存在するが**遅い**。遅さはバグではなく構造 — JSエディタ + Chromium という Web スタックそのもの。シェルだけ Rust にしても(desktop-sdk の置き換えでも)この遅さは継承される

== ネイティブファースト(2026-08-07 発注者確定)

本家(Euro-Office)は自らの価値を「ブラウザファーストの体験」に置く。
*うちは逆* — ブラウザーファーストではなく、**ネイティブファースト・デスクトップファースト**でやる。
これは上の「前提の確定」の帰結であり、先方の看板文句を読んだうえでの明示の選択。

具体的には:

* *速さと手応えが第一。* GPU 直描き・即起動・キーボード一級・IME 一級。ブラウザ由来の層(webview/Electron/JS ランタイム)は今後も持ち込まない

== アプリは増える。エンジンは1つ(2026-08-12 発注者)

冒頭の「別のバイナリにする」は 2026-08-02 の2本(writer と calc)で始まり、2026-08-04 に「新しいバイナリは作らない」と狭めた(docs/sekkei/python.ja.adoc)。
その後 pyoffice(2026-08-09)と builder(2026-08-11)が加わり、**狭め方の形が違っていた**と分かった。
2026-08-04 の狙いはバイナリの本数の固定ではなく「*保守・検査・配布の対象を増やさない*」こと。
増えて困るのは**エンジン**であって、アプリではない。
だからこう改める:

[NOTE]
====
*エンジンは1つ。アプリはいくつあってもよい — ただしアプリは薄いこと。*
====

薄いかどうかの物差しは1つ: *そのアプリにしか無い意味を持たないこと。*「動いている表を Python から操る」は意味なのでアプリに置かない。
「GPUI でセルを描く」はアプリの仕事。
アプリを足したくなったら問うのは本数ではなく「*意味が漏れていないか*」。

いまのアプリは4つ — writer・calc(GPUI)、pyoffice(genoffice の Electron にsidecar で載る)、builder(これから)。
ブラウザー・スマホは WASM で後から(「ネイティブが先」の順序のまま)。

*↑を改めた(2026-08-13 発注者)。builder は作らない。* builder がやるはずだった「Web へ出す」は、**writer / calc の用紙の選択に「Web」を1枚足すだけ**でよい — A4 や Letter と並ぶ**写し先の1つ**であって、アプリではない。
「壊さずに作り直せるサイトビルダー」の野心は畳む(必要が実証されたら再訪)。
アプリは3つ(writer・calc・pyoffice)。
これに伴い、builder を理由にしていた工事は理由を失う —リボンの表の `tabs(app, lang)` 化(3つ組は来ない)、写し先の三重化の備えなど。
*builder と無関係に壊れている物*(条件付き書式の解決が画面と紙の2箇所に写して書かれている件)だけが残る。

*その1件は済んだ(2026-08-14)* → `sheet::look::resolve_cond`。
下の層の表の「見え(格子側)」の穴がこれで埋まった。
**写しは揃わない**という予言どおりで、実際に育っていた差はこう: 画面は 39 行あってデータバーもカラースケールもアイコンも描くのに、**紙は 11 行で塗り・文字色・太字だけ**だった。
1本にした結果、*カラースケールが紙にも出るようになった*(塗りとして返るので、紙は元から持っている塗りの道に自然に乗った。
実物の PDF を前後で刷り比べて確かめた)。
データバーとアイコンはまだ紙に出ない — 敷く/字を置く仕掛けが要り、**紙の書体に ↓→↑ と ●があるかを先に確かめる**必要がある(無い書体だと黙って豆腐になる)。
*この工事の副産物*: 当てはめが sheet に移ったので、*CI が見るようになった*(CI の試験は `-p sheet -p kumihan -p ooxml -p lang -p paper` だけで、calc の試験は一度も走らない)。
試験は `sheet/src/look.rs` に8本、`sheet/tests/cond_look.rs` に往復2本。

== 操作の言葉を1本に — calc をクレートに割る(2026-08-12 発注者)

出す側(画面も紙も同じ紙面を写す)は層になっているが、*「ブックに何ができるか」の側に同じ言葉が無い*。
Python から見た Book/Range の意味が3箇所(calc/src/rpc.rs・pysheet・calc.py)に別々に書かれ、動詞が食い違う。
calc の undo はシート丸ごとの控えで、「誰が何を変えたか」を持てない — builder の芯「壊さずに作り直せる」がこのままでは立たない。

*calc(約30,000行)を1クレートのままにしない。* クレート境界は Rust で唯一の本物の壁で、「アプリは薄い」を気持ちではなく構造で守らせる。
`Cargo.toml` の依存に gpui が無いことは cargo が保証する。
順番:

. *段A*: UI でない塊を切り出す — `ops`(Book/Range の語彙。rpc.rs の9命令+calc/writer に写経されている13関数)と `pyrun`(Python 実行の機構 — Cage・埋め込み台本・plugins/UDF の管理。writer と共有になる)
. *段B*: アプリの中の部屋(view/cmds/picks)のクレート化。Calc 構造体の欄を API にする工事が要る。*段B-1 は済んだ(2026-08-15、face クレート)* — 下の節を見よ
. *その次*: `sheet::Edit` + `apply(&[Edit]) -> Undo` — undo を丸ごとの控えから Edit の列へ。これが builder の「どのセルが人の手か」と、差分再計算(いまは1セル直すたびにシート全体を回している)の両方への道

   *崖の位置を測った(2026-08-13、release)。* 手元の実物10枚(日銀・統計局・LO 対照、最大 317KB / 50,104セル)は読み 52ms・全計算 1ms 以下 — *事務の帳票の規模では困っていない*。
合成の式の鎖(B{r}=A{r}+B{r-1})では線形に伸び、*式10万本で1打鍵 0.4秒、30万本で 1.4秒*。
差分再計算が効き始めるのはそこから。
読みも 52ms が最大なので遅延読み(G-2)も急がない。
*この工事は急がず、Edit の設計と一緒にやるのが安い*(別々にやると汚れ集合の口を2回作ることになる)

writer 側は表で1度通してから同じ問いを持ち込む(文書の編集は run 単位で形が違う)。
sidecar は載せ替えない — 向こうが決めた言葉を素通しするのが役目で、翻訳の層を挟むと余計な欄が入る余地になる。

=== 段B-1 済み: face(絵を描かない層)を切り出した(2026-08-15)

発注者「*GPUI のアプリを kotlin と swift で書く*」で段B に着手した。
アプリを増やすなら、アプリでない物がアプリの外に出ていないと同じ表をアプリの数だけ書き直す。

`face` クレート(*gpui を依存に持たない*)へ移した物: リボンの表と14言語の札、関数名・分類・説明の14言語、キーの割り当ての表と合成の芯、設定・窓の控え・コンボ・アイコン(SVG 262枚)。
`ui` と `calc` が再公開しているので**呼ぶ側 73 箇所は1行も変えていない**。

== 緑は「正しい」ではなく「この物差しでは差が出ない」(2026-08-10)

**1件なら事故、2件なら型**なので憲法に書く。
同じ日に、別々のセッションが**同じ形**で踏んだ。
どちらも試験は緑で、しかも壊れていた。

[cols="1,1,1,1"]
|===
| |物差し |見ていなかったもの |結果

|docx の節 |PDF の**ページの大きさ**が正しいか |*字がその紙の中にあるか* |向きの違うページで字が紙の外へ 87mm 出ていた
|xlsx の突き合わせ |両側の**セルの中身**が一致するか |道具が「中身の無いセルは**両側で**飛ばす」と決めていた |**罫線だけのセル**が落ちているのを構造的に見られなかった
|===

*共通の型はこれ。*

[NOTE]
====
*両側に同じ簡略化を教えた物差しは、その簡略化の中にある差を永久に見ない。*
片側だけの誤りは見つかるが、*物差しが最初から見ないと決めた所*は、
何回まわしても緑のままになる。
====

だから緑を読むときは、**「正しい」ではなく「この物差しでは差が出なかった」**と読む。
合っているのは\*測った物\*だけで、測っていない物については何も言っていない。

*手当て*(どちらもそうやって直した):

. *物差しをもう1本足す。* 節では「ページの大きさ」に加えて**字の座標が紙に収まっているか**を見る試験を別に立てた。xlsx では突き合わせとは別に**向こうの試験**(契約を見る道具)を通した
. *突き合わせと試験を混ぜない。* 突き合わせは「*同じ答えか*」を見る道具、試験は「*約束を守るか*」を見る道具。前者が緑でも後者は落ちる(実際に 57,352 セル一致で 9件中7件落ちた)
. *正規化・省略・飛ばしを入れたら、そこに札を立てる。* 「両側で飛ばす」は速さのための正しい判断でも、**そこが盲点になったと明記**しておく

*同じ日に4件出ている。* 上の2件のほかに、鍵割り当ての検査・文言の門番・clippy と試験の**対象クレートの並び**(calc・writer・ui が門番の外に居る)が同じ形だった — 数え上げは link:HIKITSUGI.adoc[HIKITSUGI.adoc] にある。
そちらは「*検査はあるが、検査が見ている場所が本番とずれている*」という言い方をしていて、こちらの「物差しが見ないと決めた所」と同じことを指している。
**4件なら型ではなく、この repo の癖**として扱う。

*実物で確かめる理由もここにある。* 自分で書いた文書は、自分の読み手が読める形しか持っていない — 自分の物差しで自分を測る形になる。
数式(`xml:space` で LibreOffice の4つが全滅)も、節(1ページ目だけ紙が違う)も、*実物を通して初めて出た*。

*できない事。* 表の題を名前にした構造化参照を**その列の中で**使うと循環参照になる(`=SUM(売上台帳[金額])` を金額の列に置く)。
Excel も同じで、向こうは「集計行」を宣言して除ける。
AsciiDoc に集計行の書き方が無いので、いまは*合計を別の列に置く*か`=SUM(B2:B4)` と番地で書く。

==== 4段目 — ブックを adoc で読み書きする(2026-08-19)

`sheet::adoc` を足した。`write(ブック)` と `parse(字)` の2つで、1つのシートが1つの表になる。
表の題がシート名で、式は字のまま入る。**値は持たない** — 読んだ所で計算し直すので、*式が正本*である。

表の綴りは書き直していない。ブックを `kumihan::Document` に写して `kumihan::adoc` に渡す。

===== 実物 16 冊で測った(2026-08-19)

作り物ではなく `sample/*.xlsx` を読んで、adoc に書き、読み戻して、**セルの値を1つずつ**突き合わせた。
はじめは *16 冊のうち 11 冊*しか値が戻らなかった。

*落ちていたのは全部同じ物 — 頭に 0 の付いた番号*(`001` `0001`)。
adoc の表は中身が全部字なので、読むときに `001` を数と読んで `1` にしていた。
**伝票番号・郵便番号・商品コードが黙って変わる**ということで、事務の帳簿ではいちばん困る形である。

見分け方を「0 の次が数字なら番号」にして直した(`0.5` と `0` は数のまま)。
*いまは 16 冊とも値が往復する。* 試験は `sheet/tests/adoc_round.rs` に置き、合わない冊があれば落ちる。

*大きさ*は設計の見立てどおりだった — `売上台帳.xlsx` は 4,225 バイト → 2,108 バイト(設計の書き置きは 2,130)。

===== 式の `*` が太字に食われていた(2026-08-19)

`=A2*B2*C2` を手で書くと、`*B2*` が太字の印として読まれ、印が消えて `A2B2C2` という別の式になっていた。
**黙って `#NAME?` に化ける**形で、往復の試験は緑のままだった(こちらが書くときは `\*` と逃がしていたため)。

`kumihan::adoc::is_formula_cell` を1つ置き、*読みと書きの両方がこれを見る*ようにした。
式のセルは中身を字のまま扱う。
セルの中の見出し(`= 見出し`)と見分けるのは**`=` の後ろの空白**である — 式は空白を置かない。

これで書く字も設計の見本どおりになった(`=C2*150`。前は `=C2\*150`)。

===== 折返しのセル(`a|`)を入れた — 実物 63 升で測った(2026-08-19)

*日本の様式は「1つのセルに段落がいくつも入る」形が多い。*
実物の docx 17 冊・395 升のうち **63 升**がそれだった(`実施要領様式` の4冊)。

|===

|結合の頭書き(`6+`)が前のセルの字の末尾にくっついていた |*区切りを頭書きより先に書く*。**行の2つ目から先の結合は前から黙って消えていた**(この回で見つけた別の穴)

=== テンプレートは `.adoc`。設定ではなく、穴の空いた文書(2026-08-18 発注者)

発注者「テンプレートの形式は adoc です。
申込書であれば、ユーザーが入力する以外はテンプレートです。
どう区別するかです」。

*これで `.toml` をやめる理由がはっきりした。* テンプレートは設定ではない。
**穴の空いた文書**である。
申込書なら、枠も見出しも固定の文も全部テンプレートで、人が入れる所だけがデータである。

*`.toml` は名前も嘘だった。* いまの `テンプレート.toml` は TOML として読めない — 日本語のキーに引用符が要るからで、Python の `tomllib` は1行目で断る(2026-08-18 に確かめた)。
うちの読み手だけが読める形になっていた。

=== 何がテンプレートで、何がデータか

*文書の中では、穴の印で分かる。*

[cols="1,1"]
|===
|印 |意味

|`field:名前[ラベル]` |*人が入れる穴*(申込書の記入欄)
|`{名前}` |*差し込みの穴*(データから入る)
|それ以外の字 |*テンプレート*(枠・見出し・固定の文)
|===

*ファイルとしては、名前で分ける。*

* `テンプレート.adoc` — そのフォルダの文書の見た目の元
* `申込書.adoc` — 穴つきの様式そのもの(これもテンプレート)
* 記入済みの物 — 穴が値で埋まった文書。頭に `:template: 申込書` と書いてどの様式かを言う(この書き方はもうある)

=== 見た目をどう書くか

*文書の頭の属性で書く。* 本家がそのまま受け、`{名前}` で参照もできる(2026-08-18 に確かめた)。

....
= 見学の申込
:書体: Noto Sans CJK JP
:用紙: A4
:送り先: https://example.jp/uketsuke
....

*スタイルの定義は表で書く。* 名前ごとに値が複数あるので、属性では足りない。

....
.スタイル
|===
|名前 |大きさ |太字 |色

|見出し1 |16 |true |
|注意 | |true |C7433F
|===
....

*様式(升目)も表で書く。* いま TOML の配列で書いている物が、そのまま表になる。
*升目を表で書くのは、升目の見た目そのものである。*

*失う物。* 表のセルは全部字なので、数と真偽の区別が形の上では付かない。
読むときに直す。
間違いは日本語で言う(いまと同じ)。

=== 設定とテンプレートを分ける

*`settings.toml` は残す。* こちらは本当の設定(言語・キーの割り当て)で、文書ではない。
英数字のキーなので TOML として正しい。

[cols="1,1"]
|===
|ファイル |中身

|`~/.config/officework/settings.toml` |*アプリの設定*。言語・キーの割り当て
|フォルダの `テンプレート.adoc` |*文書の型紙*。見た目と、穴の空いた枠
|===

== 画面を1つにする — フォルダを開く形(2026-08-19 発注者)

発注者「ユーザーインターフェースを一つにする設計を先にしませんか」。

=== 使う人から見た形

┌──────────────┬──────────────────────────────┐

│  売上台帳     │                              │
│   .sheet.adoc │   選んだファイルの中身         │
│  既定         │                              │

│  images/      │                              │

いまは writer と calc を別々に起動して、1つのウィンドウに1つのファイルを開いています。
1つのフォルダで仕事をしている人には、アプリを行き来する手間が無くなります。

=== どちらの画面を出すかは、ファイルの名前で決まります

[cols="1,1"]
|===
|名前 |出る画面

|`名前.adoc` |文章
|`名前.sheet.adoc` |表
|`名前.tmpl.adoc` |文章(見た目の元も文書です)
|`名前.form.adoc` |文章
|`.docx` `.xlsx` |読み込んで、それぞれの画面へ

中身を見て「表しか入っていないから表の画面にしよう」という決め方はしません。
名前で決まるほうが、使う人が次に何が起きるか分かります。

=== プログラムの側で何を1つにするか

*アプリを1つにします。編集画面は表と文章の2つのまま残します。*

[cols="1,2"]
|===
|所 |受け持ち

|アプリ(1つ) |フォルダ・ファイルの一覧・リボン・状態の表示・開く保存・Python・探す・設定
|編集画面(2つ) |表(いまの `Calc`)と文章(いまの `Writer`)
|===

いまの `Calc` と `Writer` を1つの型にまとめることはしません。
合わせて 48,566 行あり、まとめても得る物がありません。
違うのは描く中身だけなので、そこは2つのまま残します。

この形なら、後から2つに戻すときもアプリを2つに割るだけで済み、編集画面には触りません。
*5 段目は片道ではなくなります。*

=== 測った(2026-08-19)

[cols="1,1,1,1"]

|所 |writer |calc |合計

|リボンの段 |11 |13 |*15*(共通 9)
|リボンの命令 |117 |173 |*236*(両方にある 54)
|アプリの行数 |14,664 |33,902 |48,566
|===

共通の段は9つです — ファイル・ホーム・挿入・描画・レイアウト・共同編集・保護・表示・マクロ。

テンプレートは、開いているフォルダの物になります。

* `.tmpl.adoc` が1枚なら、そのフォルダの既定になります
* 何枚もあるときは `:template: 名前` で選びます。勝手に1枚目を選びません

これは 2026-08-13 に builder を作らないと決めたとき、いったん捨てた案です(`tabs(app, lang)`)。

[cols="1,1"]
|===
|変わる |変わらない

|バイナリが1つになります(`officework`) |エンジン(`sheet` `kumihan` `ops`)はそのまま

|===

* ウィンドウは1つです。並べて見比べたい人は、アプリをもう1つ起動します(いまと同じ)

== writer と calc を officework に統合する(2026-08-19 設計)

発注者「writerとcalcをofficeworkに統合する設計をして」。
「画面を1つにする」の続きで、実施方針の A-4 以降をこの設計が引き受ける。

=== いまの姿の限界(測った)

いまの officework は「どちらか1つの編集画面を見せて、持ち替えは作り直し」という薄い形である。
使えるようにはなったが、限界が4つある。

. *持ち替え=作り直し。* 開いていたタブごと消えるので、書きかけの断りが要る。文書と表を**同時に**開いておけない
. *ファイルのタブは writer の中にだけ*ある。表の画面にはタブが無い
. *割り当てに穴がある(実測)。* officework は `bindings_for("writer")` しか読んでいない。しかも両画面が同じ文脈 `jo_edit` なので、**表の画面で calc 専用のキーが効かない**。両方の表を読むだけでは、同じキーが別の意味を持つ組で衝突する
. *受け口の宛先が「いま見ている画面」だけ。* 裏に開いている物へは届かない

=== 統合の形 — 何が officework の持ち物になるか

[cols="1,2"]
|===
|所 |持ち物

|*officework* |ウィンドウ・**開いた物の一覧(タブ)**・どの画面で開くかの決め(名前)・受け口・起動の形・(後の段で)フォルダの一覧
|*編集画面(writer / calc)* |リボンの描画・下のタブ(文書/シート)・右パネル・状態行・開く保存や式の中身
|*エンジン* |変わらない
|===

*核心は「タブ1つ=ファイル1つ=編集画面1つ」。*
開いたファイルごとに編集画面(`Entity<Writer>` か `Entity<Calc>`)を1つ作り、officework が並べて持つ。
切り替えは**見せる物と焦点を替えるだけ**で、作り直しをやめる。

これで:

* *持ち替えの断りが要らなくなる。* 書きかけはタブの中に生きたまま残る(確認が要るのは**閉じる**時だけ — いまの writer のタブと同じ)
* 文書と表を**混ぜて**何枚も開ける。Zed と同じ形
* writer の中のタブの仕組みは**単体起動の物として残す**。officework の中では1画面1ファイルなので、自然に出番が無くなる(`file_count() == 1` ならタブの行は出ない — 既にそう作ってある)

=== 一覧のクリックは「開いてほしい」に一本化する

いまは writer の一覧が「文書なら自分で開き、表なら渡す」、calc の一覧が「表なら自分で開き、文書なら渡す」と、**半分ずつ自分で開いている**。
タブの持ち主が officework になったら、これは全部「officework に開いてほしい」になる。

* 編集画面に**埋め込みの印**(`embedded: bool`)を1つ足す。officework が作るときに立てる
* 印が立っていたら、一覧のクリックは種類を問わず `open_request`(いまの `hand_off` を改名)に置く。officework が受け取り、**開いているタブがあればそこへ、無ければ新しいタブで**開く
* 印が無ければ(単体起動)今までどおり自分で開く

=== 割り当ては文脈で分ける

* 文脈を `jo_edit` の1つから **`jo_doc`(文章)と `jo_sheet`(表)**の2つにする
* officework は**両方の表を読む** — writer の表を `jo_doc` に、calc の表を `jo_sheet` に結ぶ。共通の表(`KEYS_COMMON`)は両方に入る
* 単体起動も同じ形にする(writer は `jo_doc` だけ読む)。**同じキーが画面ごとに別の意味を持てる**ようになり、衝突の芽が消える

=== 受け口

* `officework.sock` はいままでどおり「いま見ているタブ」へ渡す
* 後の段で **`path` の宛先指定**を足す(`{"cmd":"…","path":"…"}` で裏のタブにも届く)。道具(MCP・Python)が「開いてから操作」を1往復でできるようになる

ここには前は7段の一覧があったが、詳細設計の一覧と**番号の指す物が食い違って**いた
