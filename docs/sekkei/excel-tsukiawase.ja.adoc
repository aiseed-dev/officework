起動し直すのは最初の1回だけにするので、1枚あたり 30 秒ほど縮みます
(55 枚で 30 分が 5 分になりました)。

=== 直した1: 列の幅の物差しを、名指しの書体で・点で数える [大]

**いちばん大きな原因でした。** 表全体が横に 3〜4 割広がっていました。

xlsx の列幅は「標準の書体の数字が何文字ぶん入るか」で書いてあり、
長さに直す式は OOXML の仕様書にあります。

....
px = trunc(((256 × 幅 + trunc(128 / MDW)) / 256) × MDW)
....

`MDW` は標準の書体の数字1文字の幅です。ここに2つ穴がありました。

**穴1: 置き替えた書体で測っていた。** ファイルは ＭＳ Ｐゴシック 11pt と
名乗りますが、この Mac にその書体はありません(Office のアプリの中には
あります)。こちらはヒラギノ角ゴシックで描くので、ヒラギノの数字
(7.23pt)で数えていました。ＭＳ Ｐゴシックの数字は半角(0.5em = 5.5pt)
なので、**列が 3 割広くなります**。Excel は名指しの書体の幅で列を決め、
字だけを別の書体で描きます。こちらもそうしました。

数字の幅は Office が同梱している書体そのものから測って表にしました
(`ops::SUUJI_EM`)。表に無い名前は、この機械で引ける書体で測ります。

**穴2: 96dpi の画素で数えていた。** 式の `MDW` は「その機械が描く一点」で
数えた**整数**です。Windows の Excel は 96dpi の画素で数えるので
ＭＳ Ｐゴシック 11pt は `round(5.5 × 96 / 72)` = 7、macOS の Excel は
72dpi(点そのもの)なので `round(5.5)` = 6 になります。**同じファイルでも
列幅が機械で変わります** — 幅 3.125 の列は Windows で 22 画素(16.5pt)、
Mac で 19pt です。officework は PDF を点で書くので、Mac の Excel と同じ
72dpi で数えます。

確かめ方は Excel が出した PDF の罫線です。倍率も「紙に合わせる」も掛かって
いないシートを選び、縦の罫線の間隔を測りました。

[cols="1,1,1,1"]
|===
|ファイル |列幅 |Excel の PDF |新しい式(MDW=6)

|000785764.xlsx |2.125 |13pt |13pt
|002668148.xlsx |3.125 |19pt |19pt
|002668148.xlsx |5.75 |34pt |34pt
|r6daicho_itaku.xlsx |7 |42pt |42pt
|r6daicho_itaku.xlsx |12.5 |75pt |75pt
|===

試験は `paper::grid` の「列の幅は Excel の式で出す」(この5通り)と、
`ops` の「列幅の物差しは、名指しの書体で数える」です。

`paper::grid::PrintSetup` の `mdw_px` は `mdw_pt` に替えました(単位が
画素から点に変わったので、名前も直します)。

=== 直した2: 上下の中央に置く指定が効いていなかった

`printOptions@verticalCentered` は読んでいましたが、紙に置く所で見て
いませんでした。集めた 148 シートのうち 11 シートがこの指定つきで、
行の少ない申請書が紙の上に寄っていました。どの行がどの紙に載るかを
先に数え、紙ごとの中身の高さの余りの半分だけ下げます。

試験は「上下の中央に置く指定が紙に効く」(`paper::grid`)。

=== 直した3: 幅を書いていない列は 26mm ではなく、基準の 8 文字ぶん

`<col>` にも `sheetFormatPr@defaultColWidth` にも幅の無い列を、26mm
(73.7 点)の決め打ちにしていました。ECMA-376 は
`sheetFormatPr@defaultColWidth` の所で、書いていないときの既定をこう
決めています。

....
幅 = trunc((基準の文字数 × MDW + 余白 5) / MDW × 256) / 256
....

基準の文字数(`baseColWidth`)の既定は 8 です。ＭＳ Ｐゴシック 11pt
(数字 6 点)なら 8 × 6 + 5 = 53 点になります。日野市の労務台帳
(r6daicho_itaku.xlsx)は A 列に `<col>` が無く、Excel の PDF の1本目の
縦罫線がちょうど 50(左余白 0.7 インチ)+ 53 = 103 点でした。こちらは
1列で 21 点広げていました。

=== 直した4: 行の高さと余白を、点に切り捨てる

Excel は行の高さも余白も、**その機械が描く一点に切り捨ててから**紙に
置きます(macOS では 1 点 = 1pt)。切り捨てないと、20 行の表で 15 点
ずれます。

[cols="1,1,1"]
|===
|xlsx の値 |Excel の PDF |こちら(前)

|行 18.75pt |18pt |18.75pt
|行 22.5pt |22pt |22.5pt
|行 37.5pt |37pt |37.5pt
|行 16.5pt |16pt |16.5pt
|左余白 0.7 インチ(50.4pt) |50pt |50.4pt
|左余白 0.787 インチ(56.66pt) |56pt |56.66pt
|===

余白の確かめ方は列と同じで、Excel の PDF の1本目の縦罫線です。日野市の
労務台帳は 50 + 53(A 列)= 103 点、岐阜労働局の 002668148.xlsx は
56 + 34(A 列)= 90 点でした。どちらも切り捨てた余白で一致します。

=== 直した5: 用紙の番号 12・13 は JIS の B

ECMA-376(`ST_PaperSize`)は 12 を「B4 (JIS) 257mm × 364mm」、13 を
「B5 (JIS) 182mm × 257mm」と決めています。ISO の B4(250×353)と
B5(176×250)を入れていました。岐阜労働局の様式(001823803.xlsx)で、
Excel の 1032×729 点に対してこちらは 1001×709 点の紙になり、1枚に入る
行が減って紙が増えていました。試験は `ops` の
「用紙の番号 12・13 は JIS の B」。

=== 直した6: 紙に収める倍率は 1% きざみの整数

集めた 55 枚のうち 41 枚が「拡大縮小」か「紙に収める」を使っていました。
Excel の「拡大縮小」の欄は整数のパーセントで、紙に収める倍率もそこに入る
整数です。こちらは端数まで使っていました。

北海道の請負代金内訳書(A4 横、縦横1枚に収める指定)で測りました。
使える高さは 489 点、中身は 496 点なので、ちょうどの倍率は 0.9859 です。
Excel の PDF の罫線の間隔は、幅 9.75 の列(58 点)が 56.84 点、
高さ 24.75 の行(24 点)が 23.5 点でした。どちらも 98% です。

こちらは 94% で刷っていました。端数まで使ったうえに、
「いちばん高い行のぶんだけ余分に縮める」という当て推量を掛けていた
ためです。切り捨てれば行の高さの端数で最後の1行が押し出されることは
無いので、この当て推量は外しました。試験は `paper::grid` の
「紙に収める倍率は、1% きざみの整数」です。

=== 直した7: 「Ｐ」つきのＭＳ の書体の、行の高さ

ＭＳ Ｐ明朝とＭＳ 明朝は同じファイル(`msmincho.ttc`)に入っていて、
縦の寸法は同じです(1em = 256、上 220、下 36)。ＭＳ ＰゴシックとＭＳ
ゴシックも同じです。「Ｐ」は字の幅が字ごとに変わるという意味で、行の
高さには関わりません。

組版が持っている行の高さの表(`kumihan::font::OKURI_EM`)には「Ｐ」の
無い名前しかありません。「Ｐ」つきの名前は表を外れて、この機械の
置き替え先(梅明朝・梅ゴシック)の寸法 1.0em に落ちていました。集めた
xlsx の 43 枚がＭＳ ＰゴシックかＭＳ Ｐ明朝なので、セルの中の行の間隔が
そのぶん詰まっていました。`paper::grid` で「Ｐ」の無い名前に読み替えて
から表を引きます(1.292em)。

**engine 側で直す方が筋です。** `engine/src/font.rs` の `OKURI_EM` に
「Ｐ」つきの名前を足せば、docx の側にも効きます。engine は別の作業者の
受け持ちなので、こちらでは読み替えだけにしました。

=== 直した8: 空のセルを指す式は 0

日野市の労務台帳(r6daicho_itaku.xlsx)は、入力用のシートを指す式
(`=基本情報入力!D5`)ばかりです。指す先が空のとき、Excel は 0 と出し、
こちらは空のまま出していました。商号・所在地・担当者名など 25 か所の 0 が
抜け、日付の欄も「1900年1月0日」になりませんでした。

式のあるセルは、答えが空になっても空のセルにはなりません。式の答えが
空なら 0 にします(`book::calc::run`)。空の文字列を返す式
(`IF(A1="","",…)`)は文字列なので、そのままです。試験は
「空のセルを指す式は 0 になります」。

=== 直した9: セルの中の行と行の間隔

Excel はセルの中で行を折り返すときも、縦書き(`textRotation="255"`)で
字を縦に並べるときも、書体の行の高さより広く取ります。Excel の PDF で
測った間隔です(倍率の掛かっている物は等倍に戻した値)。

[cols="2,1,1,1"]
|===
|書体 |大きさ |Excel |書体の高さ

|ＭＳ Ｐ明朝 |6pt |10pt |7.8pt
|ＭＳ Ｐ明朝 |8pt |12pt |10.3pt
|ＭＳ 明朝 |9pt |13pt |11.6pt
|ＭＳ Ｐ明朝 |10pt |14pt |12.9pt
|ＭＳ Ｐゴシック |11pt |14pt |14.2pt
|メイリオ |12pt |20pt |18.0pt
|===

差は大きさによらず 4 点前後です。行と行の間隔を「書体の高さ」と
「字の大きさ + 4 点」の広い方にしました(`paper::grid` の
`MASU_OKURI_SITAJI_PT`)。**1行だけのセルには効かせません** — 測ったのは
行と行の間隔で、行の箱そのものの高さではないためです。

縦書きは 55 枚のうち 26 枚が使っています。岐阜労働局の兼務役員雇用実態
証明書(000785764.xlsx)の「服務態様」は、Excel が 14 点おきに1字ずつ
置くのに対し、こちらは 10 点おきでした。

紙の枚数が Excel と合う 31 枚で見ると、違いは 1435 件から 1384 件に
減ります。55 枚の合計では 6842 件から 6872 件に増えますが、増えるのは
もともと紙の枚数が合っていない枚で、行がずれた巻き添えです。

== まだ残っている物

* **セルの中の行の間隔の、本当の決め方が分かっていません。** 上の
  「+ 4 点」は測った値に合わせた当てはめです。11pt のＭＳ Ｐゴシックは
  Excel が 14 点なのにこの式では 15 点、メイリオ 12pt は 20 点なのに
  18 点になります。Excel に下調べ用のブックを開かせて、書体と大きさの
  組ごとに測る道を作りかけましたが、AppleScript が返らずに終わりました
  (`~/Documents/officework-cmp/probe/okuri.xlsx`)
* **紙の枚数が合わない 24 枚。** 19 枚はこちらが少なく、5 枚は多いです。
  上の行の間隔と、行の高さを書いていない行(`ht` の無い行)の扱いが
  絡んでいると見ています。Excel は中身に合わせて高さを決め直しますが、
  こちらは `defaultRowHeight` を使います
* **横に割る位置。** 北海道の留意事項及び記載例(留意事項及び記載例.xlsx)は
  Excel が横に2枚・縦に2枚の4枚に割るのに、こちらは縦に2枚だけです
* **Windows の Excel では列幅も行の高さも違うはず。** 上の切り捨てはどれも
  「その機械が描く一点」の単位に効きます。Windows は 96dpi なので、
  幅 3.125 の列は 22 画素(16.5 点)、行 18.75pt は 25 画素(18.75 点)に
  なります。**Windows の Excel で確かめる物**です
* **ＭＳ 明朝 10.5pt の列幅。** 2026-08-31 に国税庁の酒税の総括表で測った
  値(幅 9.109375 → 17.00mm)は、新しい式(数字 5 点)では 16.23mm に
  なります。現物が手元に無いので、取り直して確かめる物です
