# SEKKEI — builder(4本目の製品)

2026-08-11 発注者確定。**名前は `builder`。**

    officework   writer(docx)・calc(xlsx)   ← いまのまま守る
    builder      Web サイト・アプリ          ← 新しい殻

**writer と calc は現状に近いまま**にする(発注者確定)。後から「calc に
組み込めば早い」という誘惑が必ず来るので、先に書いておく — **組み込まない。**

## 決まっていること

| | |
|---|---|
| 名前 | **builder** |
| 作るもの | Web サイト・アプリ(画像・映像も同じ名前の下) |
| 模型 | **セルに分割する** — だから `sheet` の模型でよい |
| 汎用 AI | **作成だけ。実行はしない** |
| モバイル対応 | **AI にやらせる** |

## セルを基礎にする、という選び方

**紙面をセルの格子として持つ。** 中身・書式・結合・幅と高さ・画像・図形は
`sheet` が既に持っている。Web に写すとき:

    列の幅 → 桁の幅        結合 → colspan / rowspan
    セルの書式 → CSS       画像・図形 → そのまま

officework の方針は「**画面も紙も、同じ紙面を別の面に写すだけ**」。
すでに `paper` が PDF へ、`engine/src/html.rs` が HTML から読む側を持っている。
**builder は写す先が増えるだけ**、という形に収まる。

**この選び方には既知の弱点がある。** 固定の格子は**流し込み直しができない** —
HTML の表組みレイアウトが捨てられたのはそれが理由だった。狭い画面に入らない。

## 横幅は固定(2026-08-11 発注者確定)

**calc との一番大きな違い。** calc の紙面は右へ無限に伸びるが、builder の紙面は
**幅が決まっている**(紙と同じ)。

**これが、セルの模型が Web で成り立つ理由**でもある。幅が決まっていれば、
列の幅は**絶対の値ではなく割合**になる:

    calc      A列 8.43字・B列 12字 …  右へ無限に続く
    builder   A列 25%・B列 50%・C列 25%  合計は必ず 100%

割合なら**別の幅へ写すのは掛け算だけ**で済む。1024px の紙面を 390px に
写すのに、組み直しは要らない。**モバイル対応で AI に頼むのは「入らない所」
だけになる** — 全部を組み直させるのではなく。

**列を足すと、隣から幅を貰う。** calc のように右へ伸びない。これは画面の
作りの違いではなく**模型の違い**なので、`sheet` をそのまま使うと
「無限に伸びる」が付いてくる。ここは builder 側で押さえる所。

### 横スクロールするものは作る

幅が決まっている以上、**どうしても縮まない中身**がある — 幅の広い表、
コード、図。それを潰すと読めなくなる。

**逃げ道は1つだけ用意する。**

> **紙面そのものは横に流れない。中身のほうが、自分の枠の中で流れる。**

広い表は表だけが横スクロールし、その周りの本文はいつも画面に収まる。
**「全体を横スクロールさせる」は作らない** — 一度それを許すと、
狭い画面での見え方を誰も確かめなくなる。

## 何を出すか — **アプリから。宣言で書く。JS は含めない**(2026-08-11 発注者確定)

    順番      **アプリが先**(Web・画像・映像は後)
    書き方    Flet / Flutter の**宣言型**
    JS        **含めない**

### AI は**プログラムではなく宣言**を書く

これが「作成だけ、実行はしない」の**一番強い形**になる。AI が書くのが
コードなら「走らせない」は運用の約束にすぎないが、**AI が書くのが宣言なら、
そもそも走る物が出てこない。**

宣言を絵にするのは builder の仕事で、そちらは人が書いたコードが読む。

### 語彙は絞る — **数えた**

Flet の語彙は **約250**(コントロールとサービス)。`Cupertino…` だけで20以上、
センサー・広告・地図・グラフ…と続く。**「普通の人がわかる範囲」とは桁が違う。**

だから builder が扱うのは**その部分集合**になる。どれを採るかは未確定だが、
選び方の筋はもう見えている:

**語彙を絞ると、AI の出力が機械で確かめられるようになる。**

自由なコードは「正しいか」を人が読むしかない。決まった語彙の宣言なら、
**名前も属性も表と突き合わせられる** — 知らない名前が出たら、その場で撥ねる。
Flet には機械が読める型録があり(`get_api`)、**「見つからない」は決定的な否定**
として使える。

今日ずっと出てきた話の続き。**確かめられる形で受け取るのが、いちばん効く。**

### 基本の3つ — **文章・フォーム・データの表示**(2026-08-11 発注者確定)

**Flet の250から削って選んだのではない。** この3つは、officework が
**既に模型として持っている物**とそのまま重なる:

| 基本 | officework にある物 | Flet で言うと |
|---|---|---|
| **文章** | 段落・ラン・文字書式(`kumihan`) | `Text` `Markdown` `Divider` |
| **フォーム** | 記入欄(writer のコンテンツコントロール)、入力規則とチェックボックス(calc)、`html.rs` の `Form` / `Field` | `TextField` `Dropdown` `Checkbox` `RadioGroup` `Switch` `DatePicker` `Button` |
| **データの表示** | セル・表・結合・書式(`sheet`) | `DataTable` `ListView` `ListTile` |
| (入れ物) | 紙面の格子 | `Column` `Row` `Container` `Card` |

**20 前後**。これなら覚えられるし、**表と突き合わせられる**。

**上から削るのではなく、下から積む。** 選び方をそう置くと、最初の版で
新しい模型がほとんど要らない — 文章は `kumihan`、データは `sheet`、
フォームは `html.rs` の `Form` が既にある。

業務のアプリは、たいてい**説明の文章・入力のフォーム・一覧の表**の3つで
できている。「基本」と言われたのは、そういう意味だと受け取った。

**幅の広い表はここで効く。** `DataTable` は縮まない代表で、
前に決めた「**紙面は横に流れない。中身が自分の枠の中で流れる**」が
そのまま当てはまる。

### 押したら何が起きるか — **スクリプトも要る**(2026-08-11 発注者確定)

**3つとも「見せる」もの。** 見せる以外が要るのは、**フォームのボタンを
押したとき**。ここは宣言だけでは足りない。**スクリプトを持つ。**

#### 方針とは衝突しない — 方針は「コードを持たない」ではなかった

VBA を作らなかった理由を読み直すと、罪は**コードであること**ではなく
**開いただけで走ること**だった。しかも 2026-08-09 に線はさらに強くなって
いる — **ブックはコードを運ばない**(正は
[python.ja.md](python.ja.md) の「↑をさらに狭めて」の節。コードは plugins の
.py にだけ住み、受け取ったファイルに走る物が入っていることが無い)。
(この項は当初、改訂前の README を引用していた — 引用元が 2026-08-12 に
実態へ直されたので、生きている節への参照に差し替えた。結論は変わらない。)

だから builder がスクリプトを持っても、**次の3つを守れば線は動かない**:

1. **開いても走らない。** 走るのは人が「動かす」と言ったときだけ
2. **走る場所と扱いは calc の plugins と同じ。** 素の .py を見える所に置き、
   **置く前に読める**形にする(囲いの実物は python.ja.md の「2本の道」の表)
3. **AI が書いた物も、人が書いた物も、扱いは同じ。** 出どころで緩めない

**変わったのは、安全が「形」ではなく「作法」で守られるようになったこと。**
宣言だけなら走る物が存在しなかった。いまは存在するので、**上の3つを実装で
守り切る必要がある。** 楽なほうから難しいほうへ移った、と正直に書いておく。

#### 言葉は Python(当方の見立て、未確定)

Flet は Python で、calc の `=PY` も plugins も Python で、サンドボックスの
仕掛けも Python のために既にある。**JS は含めないと決めた**ので、
別の言葉を持ち込む理由が無い。

#### スクリプトは**見える所に、ひと塊で**置く

散らして書けるようにしない。理由は2つ:

- **宣言でない部分がどれだけあるかが、見て分かる。** 全部が同じ見た目だと、
  確かめられる部分と確かめられない部分の境が消える
- **そこが、人が手で書く場所になる。** つまり**AI に作り直させたとき、
  いちばん失われては困る場所**

2つめが重い。「壊さずに作り直せる」が芯だとすれば、**その芯が一番効くのが
スクリプト**ということになる。宣言は AI が何度でも書き直してよく、
**手で書いたスクリプトは残る** — この線引きなら、両方が成り立つ。

#### 宣言で済む物は宣言のまま

スクリプトを持てるからといって、**どこへ送るか・どの画面へ行くか・どの表に
足すか**まで書かせない。それらは `html.rs` の `Form` が既に持っている形
(action と GET/POST)で足りる。

**一覧から選べる物は選ばせる。スクリプトは、選べない物のためにある。**

### 「JS を含めない」の意味

こちらが**書き出す物に JS を置かない**、ということ。Flutter が動くために何を
使うかは枠組みの話で、こちらが生成した物ではない。**生成した物の中に、
読めない・確かめられない実行体を混ぜない**、と読むのが正しい。

`engine/src/html.rs` の今の線(「**JS は実行しない** — script は丸ごと読み飛ばす」)
とも揃う。

## だから、AI が担ぐのは「飾り」ではない

**モバイル対応を AI にやらせる、というのは、模型の弱点を AI で埋めるということ。**
つまり AI は付け足しの機能ではなく、**構造の一部**になる。

そこから直ちに出る決め:

**AI に繋がらないとき、狭い画面用の出力を「それらしく」出さない。**
「モバイル版は作れません」と言って止める。校正が繋がらないときに
「校正できません」と出して、黙って「指摘なし」にしないのと同じ作法
(README の「繋がらなければ…」)。**壊れた狭い版を黙って出すのが一番悪い。**

## 「作成だけ。実行はしない」の線

方針の「**開く=実行という攻撃経路を最初から持たない**」(VBA を作らなかった
理由)は、builder でも守る。AI が書いた物を**こちらの機械で走らせない**。

**ただし線が1本ぶん違う。** calc の Python は「**自分の機械で**回す」話
(いまの姿は python.ja.md — コードは plugins に住み、置く前に読むのが門)。
builder が作るのは**配る物**で、
JS は**見に来た人の browser** で動く。**同じ「実行」ではない。**

この2つを混ぜないこと。決めるべきは:

1. builder 自身が AI の出力を走らせるか → **走らせない**(確定)
2. 作った物に JS を含められるか → **未確定**。含めれば Web らしくなり、
   含めなければ「JS なしの閲覧と記入」(`html.rs` の今の線)に留まる

## 芯は「壊さずに作り直せる」だと思う(当方の見立て、未確定)

**AI が作る**は誰でも言える。officework が既に解いていて、たいていの
生成道具ができていないのは:

> **何度 AI に触らせても、人が手で直した所は残る。**

docx を壊さずに書き戻すのと**同じ問題**で、`write_with`(原本を正として
変えた所だけ書き戻す)と `raw_copy_file`(触っていない部品は圧縮済みのまま
写す)は、その答えとして既にある。

セルの模型なら手が届く — **どのセルが人の手か**を持てばよい。

**実現の形の見立て(2026-08-12)**: 「どのセルが人の手か」は、`sheet` に
編集の言葉(`sheet::Edit` + `apply(&[Edit]) -> Undo` — SEKKEI「操作の
言葉を1本に」)を立てて、Edit に**誰の手か**(人 / AI / 取り込み)を1つ
持たせる形で出る。いまの calc の undo(シート丸ごとの控え)では原理的に
持てない — builder の前に undo の作り直しが並ぶのはこのため。

## 置き場(2026-08-12)

**写し先は `paper` と対の位置の新クレート**(紙面 → Web / 宣言)。
**calc にも sheet にも入れない** — 冒頭の「組み込まない」を、気持ちでは
なく置き場で守る。SEKKEI「層は6つ」の写し先の欄がこれ。

## 決まっていないこと

- どの AI に、どういう形で頼むか(officework は OpenAI 互換の
  `/v1/chat/completions` を話す相手なら何でもよい、という作りが既にある)
- 芯を「壊さずに作り直せる」に置くか

## いつ作るか — **calc と writer を仕上げてから**(2026-08-11 発注者確定)

**具体は、作りながら考える。** ここまでの決めは「作る前に決めておくと後で
効く物」だけで、残りは手を動かしながらでよい。

**先に calc と writer を完成させる。** builder はそのあと。

理由は書かなくても分かるが、1つだけ記しておく — **builder は
`kumihan` と `sheet` の上に立つ**。土台が揺れている間に上物を建てると、
どちらの都合で直したのか分からなくなる。
