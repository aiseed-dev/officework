# SEKKEI — builder(4本目の製品)

2026-08-11 発注者確定。**名前は `builder`。**

    officework   writer(docx)・calc(xlsx)   ← いまのまま守る
    builder      Web サイト・アプリ          ← 新しい殻

**writer と calc は現状に近いまま**にする(発注者確定)。後から「calc に
組み込めば早い」という誘惑が必ず来るので、先に書いておく — **組み込まない。**

## 決まっていること

| | |
|---|---|
| 名前 | **builder** |
| 作るもの | Web サイト・アプリ(画像・映像も同じ名前の下) |
| 模型 | **セルに分割する** — だから `sheet` の模型でよい |
| 汎用 AI | **作成だけ。実行はしない** |
| モバイル対応 | **AI にやらせる** |

## セルを基礎にする、という選び方

**紙面をセルの格子として持つ。** 中身・書式・結合・幅と高さ・画像・図形は
`sheet` が既に持っている。Web に写すとき:

    列の幅 → 桁の幅        結合 → colspan / rowspan
    セルの書式 → CSS       画像・図形 → そのまま

officework の家訓は「**画面も紙も、同じ紙面を別の面に写すだけ**」。
すでに `paper` が PDF へ、`engine/src/html.rs` が HTML から読む側を持っている。
**builder は写す先が増えるだけ**、という形に収まる。

**この選び方には既知の弱点がある。** 固定の格子は**流し込み直しができない** —
HTML の表組みレイアウトが捨てられたのはそれが理由だった。狭い画面に入らない。

## 横幅は固定(2026-08-11 発注者確定)

**calc との一番大きな違い。** calc の紙面は右へ無限に伸びるが、builder の紙面は
**幅が決まっている**(紙と同じ)。

**これが、セルの模型が Web で成り立つ理由**でもある。幅が決まっていれば、
列の幅は**絶対の値ではなく割合**になる:

    calc      A列 8.43字・B列 12字 …  右へ無限に続く
    builder   A列 25%・B列 50%・C列 25%  合計は必ず 100%

割合なら**別の幅へ写すのは掛け算だけ**で済む。1024px の紙面を 390px に
写すのに、組み直しは要らない。**モバイル対応で AI に頼むのは「入らない所」
だけになる** — 全部を組み直させるのではなく。

**列を足すと、隣から幅を貰う。** calc のように右へ伸びない。これは画面の
作りの違いではなく**模型の違い**なので、`sheet` をそのまま使うと
「無限に伸びる」が付いてくる。ここは builder 側で押さえる所。

### 横スクロールするものは作る

幅が決まっている以上、**どうしても縮まない中身**がある — 幅の広い表、
コード、図。それを潰すと読めなくなる。

**逃げ道は1つだけ用意する。**

> **紙面そのものは横に流れない。中身のほうが、自分の枠の中で流れる。**

広い表は表だけが横スクロールし、その周りの本文はいつも画面に収まる。
**「全体を横スクロールさせる」は作らない** — 一度それを許すと、
狭い画面での見え方を誰も確かめなくなる。

## 何を出すか — **アプリから。宣言で書く。JS は含めない**(2026-08-11 発注者確定)

    順番      **アプリが先**(Web・画像・映像は後)
    書き方    Flet / Flutter の**宣言型**
    JS        **含めない**

### AI は**プログラムではなく宣言**を書く

これが「作成だけ、実行はしない」の**一番強い形**になる。AI が書くのが
コードなら「走らせない」は運用の約束にすぎないが、**AI が書くのが宣言なら、
そもそも走る物が出てこない。**

宣言を絵にするのは builder の仕事で、そちらは人が書いたコードが読む。

### 語彙は絞る — **数えた**

Flet の語彙は **約250**(コントロールとサービス)。`Cupertino…` だけで20以上、
センサー・広告・地図・グラフ…と続く。**「普通の人がわかる範囲」とは桁が違う。**

だから builder が扱うのは**その部分集合**になる。どれを採るかは未確定だが、
選び方の筋はもう見えている:

**語彙を絞ると、AI の出力が機械で確かめられるようになる。**

自由なコードは「正しいか」を人が読むしかない。決まった語彙の宣言なら、
**名前も属性も表と突き合わせられる** — 知らない名前が出たら、その場で撥ねる。
Flet には機械が読める型録があり(`get_api`)、**「見つからない」は決定的な否定**
として使える。

今日ずっと出てきた話の続き。**確かめられる形で受け取るのが、いちばん効く。**

### 「JS を含めない」の意味

こちらが**書き出す物に JS を置かない**、ということ。Flutter が動くために何を
使うかは枠組みの話で、こちらが生成した物ではない。**生成した物の中に、
読めない・確かめられない実行体を混ぜない**、と読むのが正しい。

`engine/src/html.rs` の今の線(「**JS は実行しない** — script は丸ごと読み飛ばす」)
とも揃う。

## だから、AI が担ぐのは「飾り」ではない

**モバイル対応を AI にやらせる、というのは、模型の弱点を AI で埋めるということ。**
つまり AI は付け足しの機能ではなく、**構造の一部**になる。

そこから直ちに出る決め:

**AI に繋がらないとき、狭い画面用の出力を「それらしく」出さない。**
「モバイル版は作れません」と言って止める。校正が繋がらないときに
「校正できません」と出して、黙って「指摘なし」にしないのと同じ作法
(README の「繋がらなければ…」)。**壊れた狭い版を黙って出すのが一番悪い。**

## 「作成だけ。実行はしない」の線

家訓の「**開く=実行という攻撃経路を最初から持たない**」(VBA を作らなかった
理由)は、builder でも守る。AI が書いた物を**こちらの機械で走らせない**。

**ただし線が1本ぶん違う。** calc の `=PY` は「**自分の機械で**回す」話だから
サンドボックス(bubblewrap)に閉じた。builder が作るのは**配る物**で、
JS は**見に来た人の browser** で動く。**同じ「実行」ではない。**

この2つを混ぜないこと。決めるべきは:

1. builder 自身が AI の出力を走らせるか → **走らせない**(確定)
2. 作った物に JS を含められるか → **未確定**。含めれば Web らしくなり、
   含めなければ「JS なしの閲覧と記入」(`html.rs` の今の線)に留まる

## 芯は「壊さずに作り直せる」だと思う(当方の見立て、未確定)

**AI が作る**は誰でも言える。officework が既に解いていて、たいていの
生成道具ができていないのは:

> **何度 AI に触らせても、人が手で直した所は残る。**

docx を壊さずに書き戻すのと**同じ問題**で、`write_with`(原本を正として
変えた所だけ書き戻す)と `raw_copy_file`(触っていない部品は圧縮済みのまま
写す)は、その答えとして既にある。

セルの模型なら手が届く — **どのセルが人の手か**を持てばよい。
