=== なぜ堀を越えられたか — VBA の前提の崩し方(2026-08-04 発注者の振り返り)

Microsoft の堀は「*競合には VBA が作れない*」だった。
実際、互換で挑んだものは全部この堀に落ちた — 30年物の実行系のバグまで含めた再現は終わらない仕事で、追いつく頃には本家が先にいる。

崩し方は互換ではなく**置き換え**だった。
堀の実体は VBA という言語ではなく「*コードが帳票と一緒に旅をし、ファイルコピーで配れる*」という性質で、それは joPython.xml が再現した。
しかも本家が構造的に直せない欠陥(開く=実行、サンドボックスなし)を**最初から持たずに**。
言語は Python — VBA より広い公共財(polars・scipy・matplotlib)ごと手に入り、書ける人も多い。

これを可能にした技術の柱が2本:

* *Rust で書いたこと。* 核(kumihan / sheet)が UI から独立した安全な部品になり、GPUI で速さは構造から出る。そして *PyO3* — sheet をそのまま Python の束縛(crate は pysheet、配る名は officework)にする橋が安く架かった。「Rust が帳票の形を守り、Python が中身を作る」分業は、この橋の安さが前提。グラフ・ピボット・ソルバー・方程式が日単位で入ったのは、重い仕事を Python の公共財に投げ、Rust 側はボタンとサンドボックスだけ持ったから
* *AI(Fable)が開発者だったこと。* この構え(小さい Rust の核+ボタンの裏の Python+サンドボックス)は、1ボタン=1台本+結線という**小さく検査できる単位**の積み重ねで、AI の開発と相性がよい。発注者+Fable 2人でこの速度が出たのは偶然ではなく、構造の帰結

残りの正直な注記: 堀を越えたのは**構造**で、現場の移行には既存 VBA の移し替えの手間が残る — *これも AI の仕事にする*(発注者 2026-08-04。

=== AI は聞かれたときだけ答える(2026-08-09 発注者確定)

AI タブの**外枠**を決めた。
発注者の言葉:「AIが事前に候補は出さない。
常駐のエージェントは使わない」「AI への自然言語の操作指示も代行はしない」「詳しいことはやらなくていい。
指示が出せたらいいので、チャット形式だけ」。

三つとも「*AI を主語にしない*」という一つの決めから出ている:

* *勧めない。* 中身を見て「この形はどうですか」と先回りしない。おすすめグラフ・おすすめピボット・インサイトの類は**作らない**。勧めが外れたとき、帳票は静かに歪む。誰が決めたのか分からなくなるのがいちばん悪い
* *住み着かない。* 裏で走り続けて見張る常駐のエージェントは置かない。呼ばれたときに動いて、終わる
* *代わりに操作しない。* 「この表を売上順に並べて」と言われても、AI が並べ替えを実行することはしない。*人が押す*
* *形はチャットだけで足りる。* 凝った画面は要らない。聞いて、答えが返って、人がそれを見て自分で操作する

*例外は既にある「変換と生成の道具箱」*(下の節)。
VBA の移し替え・要約・翻訳・式の説明は、**人が呼んで、結果を人が読んで確かめてから使う**形なので、この決めと矛盾しない。
境目は「*AI が先に動くか、人が先に呼ぶか*」。

=== K4 の見立て — 縦書き・ルビ・均等割付は作れる(2026-08-04 発注者)

発注者「作れるでしょう」— 同意。
ソースで裏を取った現在地と道順:

* *土台は最初から用意してある。* kumihan の冒頭に「縦書き・ルビ・均等割付・ぶら下げは K4(モデルはそれを妨げない形にする)」と宣言済みで、核は「置かれた文字の座標」を返すだけ — 画面・PDF は写すだけなので、組みの拡張は核の中に閉じる
* *① 均等割付(いちばん近い)*: `Align::Justify` は enum も docx 往復(`both` / `distribute`)も**既にある**。無いのは描画の字間配分だけ(今の Justify は左寄せと同じに描いている)。実装は「禁則で折った後の行の余りを字間に配る」一つの関数 — 和欧の境や約物の前後の配り方(JIS X 4051)は段階的に細かくすればよい。段落の distribute と、run 単位の「◯字取り」(docx の w:fitText)は同じ道具の2つの使い口
* *② ルビ*: docx の `w:ruby`(rubyBase + rt)の読み書きと、**半分の大きさの副行**を親文字の上に置く組み。読みが親より長いときの配りは①の字間配分がそのまま道具になる。行の高さはルビの分だけ持ち上げる。そして**読みの自動付与は既に資産がある** — furigana の道具と青空文庫での実測(読みが割れる語 561種)。Word の「ルビ」より良いものにできる場所(ローカルのモデルが文脈で読みを選ぶ)
* *③ 縦書き(いちばん重い・いちばんの存在理由)*: 行組みは1次元の詰め込み問題なので、**軸の入れ替え**で核の禁則・字幅の道具は全部生き残る。新しく要るのは (a) 約物の縦書き字形(、。ー「」等 — OpenType の vert。無ければ常用の約物だけの対応表で始める家風)、(b) 欧文の回転と**縦中横**(2桁の数字を横に寝かせる — ②の副行と親戚の「行の中の小さな別軸」)、(c) 段=列が右から左へ進む紙面。docx とは sectPr の textDirection(tbRl)で往復
* *順序が道具を作る*: ①の字間配分 → ②の副行と字取り → ③の軸の入れ替え、と各段が次の材料になる。実装は writer / engine 側(相方)—受入の物差しは「JIS X 4051 に従う縦組みの実物(通知文・賞状の類)が画面と PDF で同じに組めること」

=== pywashi との関係 — K4 の教師と、記法の合流(2026-08-04 発注者)

https://github.com/aiseed-dev/pywashi[pywashi](発注者の既存プロジェクト。
MIT)は「Markdown から美しい日本語文書(HTML / PDF)を作る `washi`」で、*K4 が目指すものが既に動く形である*: 禁則・約物の行頭詰め・句読点のぶら下げ・両端揃え・段落頭一字下げ、ルビ(でんでん記法 —グループ `{漢字|かんじ}` / モノ `{東京|とう|きょう}`)、縦書き(`--vertical` 右→左)、原稿用紙(`--genko`)、傍点・傍線。
PDF は Chrome ヘッドレスで刷る。
ここから4つ:

=== 訂正: 免許の壁は *Apple だけ*。Microsoft は明文で FOSS を許している(2026-08-15)

上の 08-14 の節で「GPL は Apple/Microsoft のストアの EULA と衝突する」と**Apple と Microsoft を一括りにしたのは誤り**。
08-09 の表の方(「Store はAGPL も明文で可」)が正しかった。
一次資料で確かめた:

Microsoft の App Developer Agreement は、開発者が独自の免許を添えることを認めたうえで、その独自の免許が Standard Application License Terms の第3節(逆コンパイルの禁止・複製数の上限)と**衝突してよい**と明記している— 「*but only to the extent required by the FOSS that you use*」。
5台までの上限も独自免許で上書きされる。
VLC の JB Kempf の分析(<https://jbkempf.com/blog/Windows-Store-and-the-GPL/>)の結論は「FOSS を Windows ストアに出すのは、いまはかなり安全」。

Apple はここが違う。
**Usage Rules が EULA と独立に掛かる**ので独自免許で外せない — だから Mac App Store が駄目という 08-14 の判断は**そのまま生きている**。
誤っていたのは Microsoft を巻き添えにした所だけ。

つまり Windows は *ストアに出せる*(GPL の3クレートを抱えたまま)。

*署名の細部*(直配布でも要る): 同梱 Python の Mach-O(`python3`・`libpython3.x.dylib`・`lib-dynload/*.so`)は**全部が署名の対象**。

== マニュアルは Excel の課題の並びを蒸留する(2026-08-08 発注者)

発注者が Excel Copilot コネクタの発表文(基幹のデータを Microsoft Graph に索引させてグリッドへ)を示して「これは間違っていないか。
Excel のマニュアルを蒸留して officework のマニュアルを作らないか」。

* **課題認識は正しく、答えの建て方が違う**と見る: 「データは他のシステムにある。取り込みは価値の一部」はうちの問い合わせ台帳・受注台帳がやってきた仕事そのもの。MS の答えは組織のデータをクラウドに索引させて AI と束ねる —基幹網の外に出ない・AI 無しでも成立する、といううちの線とは逆
