# SEKKEI — pyoffice(genoffice に officework エンジンを載せる)

2026-08-09 発注者確定。**製品は2本・エンジンは1つ**(`office-two-shells` の線):

| | officework | pyoffice |
|---|---|---|
| 殻 | GPUI(ネイティブ)。いま作っているもの | [genoffice](https://github.com/genspark-ai/genoffice)(Electron) |
| 中身 | **共通の officework エンジン**(`sheet`) | 同じ |

出来上がりは AGPL-3.0(Apache-2.0 は AGPL に片道で取り込める)。`ee/` は
別免許なので**必ず外す**。`LICENSE` / `NOTICE` を残し、変えた所を記す。

## 向こうの作り(2026-08-09 調査)

xlsx サイドカーは `apps/sheets/native/xlsx-engine/`(Rust 7,070行)。
TypeScript とは **stdin/stdout の JSON 1行ずつ**で話す
(`apps/sheets/src/main/xlsx-sidecar-client.ts:178-185` が `spawn`)。

要求は `{version, requestId, command, …}`、答えは `{version, requestId, ok,
result|error}`。時間切れは 30 秒(書庫の操作だけ 180 秒)。

**要点: 向こうの Rust は xlsx を「書か」ない。**

- 読み: サイドカーが解いて、セル・書式・結合・条件付き書式・入力規則・
  図形・グラフ・スパークライン・コメント・名前の定義まで返す
- 書き: **TypeScript が XML のパッチ計画を作り**(`planCellEditsToXlsx`)、
  Rust は `save_archive(source, target, replacements, removals, additions)` で
  **ZIP の差分を当てるだけ**。変えないエントリは圧縮済みのまま丸ごと写し、
  前後のマニフェストを CRC32 と大きさで照合する
- 計算: `recalc_cells` が `ironcalc`。セッションに Model を residents させる

## だから、そのままでは嵌まらない

officework の `sheet` は**モデルを持って自分で書き戻す**作り(`write_with` で
原本を据え置き)。向こうの「TypeScript がパッチを決め、Rust は ZIP を差し替える」
とは**書き手が違う**。ここを見ずに「エンジンを載せる」と言うと詰む。

## 切る場所 — 12 のコマンドを3つに分ける

| 組 | コマンド | 扱い |
|---|---|---|
| **エンジンの仕事** | `open` `read_range` `read_formula_cells` `read_media` `recalc_cells` | **`sheet` に差し替える**(ここが本題) |
| セッションの世話 | `close` `cancel` | そのまま(`sheet::Book` を id で持つだけ) |
| **ZIP の配管** | `archive_manifest` `read_entries` `scan_entries` `save_archive` `convert_workbook` | **触らない**。エンジンの仕事ではない |

**12 のうち置き換えるのは 5 つだけ。** 残り 7 つは ZIP とセッションの世話で、
向こうの実装が既に堅い(マニフェスト照合まである)。ここを書き直す理由はない。

## 進め方 — 通信の言葉は1文字も変えない

**同じ 12 コマンドを、同じ JSON の形で喋る。** そうすればサイドカーの
実行ファイルを差し替えるだけで済み、TypeScript 側は何も知らなくていい。
A/B で戻せるのも大きい(環境変数でどちらを起動するか切り替える)。

1. **読みから**。`open` / `read_range` / `read_formula_cells` を `sheet` で
   実装し、向こうの実装と**同じ入力に同じ答えを返すか**を突き合わせる
   (実物の xlsx を何十枚か通して JSON を diff する試験を先に作る)
2. **計算**。`recalc_cells` を `sheet::calc` に。ironcalc が外れる
3. **書き**は最後。ここだけは TypeScript 側の作り替えが要るので、1と2で
   エンジンの信用ができてから。**急がない** — 向こうの ZIP 差分保存は
   よく出来ていて、当面そのままで困らない

## 埋まっていない穴(先に知っておく)

1. **リッチテキスト**。向こうは共有文字列の中で色が変わる run を読んで返す。
   officework は**セルの中で書式が変わることをモデルに持たない**
   (2026-08-09 の決定 — 代わりにマークダウンで描く)。ここは
   「読んで返すだけ」の形で足すか、平文に潰して報告するかを決める必要がある
2. **グラフとドローイングの深さ**。向こうは chart XML の系列まで構造化して
   返す。officework は図形・画像は持つが、グラフは matplotlib で画像として
   置く作りなので、**返せる中身が違う**
3. **セッションの居座り**。向こうは Model をセッションに残し、ファイルの
   mtime と大きさで自動的に捨てる。officework 側も同じ仕組みを用意する

この3つは「難しい」のではなく「**返す中身が違う**」問題。1 は正直に潰し、
2 は当面向こうの実装を残す(ZIP 配管の組に置いてよい)、3 は素直に作る。

## 訂正: 「埋まっていない穴」は3つより狭い(2026-08-09 当方)

↑の節を狭めた。両側のモデルを並べたら、**注釈のほうが古かった**。

`sheet/src/model.rs` の「条件付き書式(cellIs だけ)」「入力規則(list だけ)」は
嘘で、実際は条件付き書式 **9 種**(比較・間・含む・重複・上位N・平均比・
データバー・カラースケール・アイコン)、入力規則は **知らない種類も落とさず
持ち越す**。向こうが返す欄のほとんどは既にモデルにある。

| 向こうが返す欄 | officework | |
|---|---|---|
| 結合・列幅・行高・アウトライン・隠し行列・表・コメント・リンク・条件付き書式・入力規則・名前の定義・耳の色・隠しシート・保護・RTL | **ある** | そのまま出せる |
| **固定枠**(`freeze`) | **ある**(2026-08-09 に足した) | `Sheet::freeze` = `FreezePane { frozen_rows, frozen_columns }`。**向こうと同じ形**にしてあるので、欄を並べ替えずに出せる |
| リッチテキストの run / スパークライン / グラフの系列 | 無い | 「返す中身が違う」の組。正直に潰すか、向こうの実装を残す |
| `styleIndex` + `styles[]` の索引表 | **形が違う** | 向こうは索引を返す。こちらは `CellFormat` を直に持ち、`style_of` に原本の索引を控えている。**変換で埋まる**(新しい設計は要らない) |

**残る穴は3つ** — リッチテキスト・スパークライン・グラフの系列。
固定枠は塞いだ(下の節)。
セッションの居座り(旧3)は素直に作るだけなので穴ではなく仕事。

### 固定枠が抜けていた(2026-08-09 当方。**保存で落ちる欠陥だった → 塞いだ**)

`sheet` は `sheetViews` を **`rtl` のときだけ**書いていた。`pane`(固定枠)は
**読んでもいないし書いてもいなかった**。つまり Excel で見出し行を固定した台帳を
calc で開いて保存すると、**固定が黙って消えていた**。

pyoffice の話より先に **calc 側の欠陥**だったので、先に直した。

**直した中身。**

- `Sheet::freeze: Option<FreezePane>`(`frozen_rows` / `frozen_columns`)。
  **止める行数・列数**で持つ = Excel の「先頭の行を固定」と同じ数え方で、
  genoffice のサイドカーが返す形と同じ。突き合わせで欄を組み替えずに済む
- `sheetViews` は **常に**書く。rtl だけの条件を外したので、右から左と固定枠が
  同じ `sheetView` に同居する
- `showGridLines` / `showFormulas` / `zoomScale` も**併せて往復させた**。
  同じ元素の属性で、書く場所が要る話でもないのに落ちていた。
  いずれも `Option` で持ち、**原文に無かったものは書き足さない** —
  既定を書き足すと、触っていない帳票にまで差分が出る
- `state="split"`(掴んで動かす分割)は固定ではないので読みで撥ねる。
  分割の `xSplit` は列数ではなく **1/20 ポイントの座標**なので、固定として
  読むと途方もない列数になる

**calc も繋いだ。** `sheet` だけ直すと、ファイルの往復は直る(モデルを素通しで
書き戻すため)が、**画面とファイルが別のことを言う**状態が残る。calc の固定枠は
`App::frozen` という画面の状態で、モデルに触れていなかったので:

- ファイルが「見出し行を固定」と言っていても、**固定なしで開く**
- calc の「ウィンドウ枠の固定」で固定しても、**ファイルに載らない**

`freeze_from_book`(開いた直後)と `freeze_into_book`(書く直前)の2つで繋いだ。
数え方は 1対1 —`App::frozen = Pos::new(1, 0)` がそのまま
`FreezePane { frozen_rows: 1, frozen_columns: 0 }`。**いま見ていないシートの固定も
落とさない**ように、集める先は `sheet_ui`(シートごとの控え)にしてある。

**併せて見つかった地雷(こちらの方が根が深い)。** 読みは `sheetView` を
`Event::Empty` の枝でしか見ていなかった。**Excel が書く `sheetView` は
`<selection/>` や `<pane/>` を抱えるので Start で来る。** つまり実物の xlsx では
`rtl` すら読めていなかった — 往復の試験が自分で書いた(子の無い)`sheetView` だけを
見ていたので気付けなかった。**自分の書き出しだけで往復を確かめると、この型の穴は
必ず見落とす。** 実物の形を型紙にした試験を足してある
(`見出し行を固定した実物の形を読める`)。

## 数から中身へ(2026-08-09 当方。`pyoffice_diff.py` を深くした)

4 つの数の比べから、**中身の突き合わせ**に替えた。いま見ているのは

- シート名の並びと**使っている範囲**
- **セルの値そのもの**(数は丸めの揺れだけ許す)
- **式の文字列そのもの**(両側とも `=` 付きで返る)
- **結合の座標**

結果は **9 枚・664 セルで一致**。値も式も結合も、1 つも違わない。今度は
中身を見ているので、これは信号として意味がある。ただし**まだうちが書いた
xlsx** — 他人の xlsx を通すまでは「壊れていない」以上のことは言わない。

差し違えたときに本当に鳴るかは、食い違う組を作って確かめた(範囲・欠けた
セル・値・式・結合の 5 種類が全部鳴る)。**鳴らない検査は無いより悪い。**

### Python の窓が天井(2026-08-09 当方)

「比べる項目を増やす」で書式・罫線・条件付き書式・入力規則まで行きたかったが、
**`officework.sheet` の Python の窓が返さない**。出ているのは
`Book`(`open` `save` `sheet_names` `unsupported` `recalc` `add_sheet`)と
`Sheet`(`[]` `formula` `display` `shape` `values` `merges` 行列の出し入れ)で全部。
モデルには**ある**のに、窓が無いので比べられない。

**窓を太らせるのは筋が悪い。** pysheet は配っている製品で、比べるための穴を
開けるために API を増やすのは順序が逆。**本番のサイドカーは Rust で `sheet`
クレートを直に使う**のだから、比べる側も Rust から出すのが正道。

→ **次の一手 1 を書き換えた**(下)。Python の窓は値・式・結合の突き合わせに
使い続ける(配った wheel をそのまま動かす検査にもなっている)。

## 段階索引 — ここが一番大きい構造差(2026-08-09 当方)

向こうの `read_range` は `indexedThroughRow` / `indexingComplete` を返す。
**全部読み終わる前に答える**作りで、だから `cancel` があり、時間切れが 30 秒で足りる。
officework の `Book::open` は**全部読んでから返す**。

### `indexingComplete` を読み違えていた(2026-08-09 に踏んだ)

`indexingComplete` は「**シートの索引が終わったか**」であって、
「**要求した範囲が揃ったか**」ではない。8 行の帳面で `indexedThroughRow: 7`
(= 全部揃っている)なのに `indexingComplete: false` が返った。索引は別の走りで
進んでいて、読みが先回りしただけ。

**当てになるのは `indexedThroughRow >= 要求の最終行`。** `indexingComplete` を
「まだ読めていない」と読むと、揃っている答えを毎回疑うことになる。

**副作用がある**(向こうの `lib.rs:749-764`): **条件付き書式・絞り込み・
入力規則・シートの保護は `indexingComplete` のときだけ返る**。早く読むと
これらは**黙って空で返る**。呼ぶ側は後でもう一度読んで埋める前提の作り。

**決め:**

1. 最初は `indexingComplete: true` を返して全部読む。実物で 30 秒に触ってから
   段階化する。触る前に作らない
2. ただし**「空で返る」の真似はしない**。officework は全部読んでから答えるので、
   条件付き書式も入力規則も**最初から入っている**。呼ぶ側(TypeScript)は
   「後で埋まる」を許す作りなので、**先に埋まっている分には壊れない**

## genoffice はどうするか(2026-08-09 当方の見立て)

**上流を触らない。パッチ 0 で始められる。**

`apps/sheets/src/main/sheets-main.ts:2881` に **`XLSX_SIDECAR_PATH` が既にある**。
環境変数で起動する実行ファイルを選べる。A/B の切り替えのために書こうとしていた
ものが、**向こうに最初から入っていた**。

だから当面の genoffice の扱いは:

1. **fork は追随用のまま。** `package.json` の `repository` が本家を指しているのも
   直さない — 直すと差分が生まれ、取り込みのたびに喧嘩になる
2. **`ee/` を外す・免許を AGPL にする・名前を変える**のは、**製品として配るとき**。
   今やる理由がない。先に名と免許を変えると上流の取り込みが毎回衝突する
3. **分岐が要るのは「書き」の段(進め方の3)から。** 読みと計算は
   実行ファイルの差し替えだけで終わる

要するに、**しばらく genoffice には何もしない**。手を入れるのは officework 側だけ。

## 他人の xlsx を通した(2026-08-09 発注者の指示で第1便)

発注者 2026-08-09:「**国は csv に移した物が多いので、日銀などの外郭から

**うちが書いた 9 枚では 664 セル全部一致していたのに、他人の物を通した
とたんに 10 枚中 8 枚で落ちた。** 56,487 セルを比べた結果。

落ち方は**きれいに2種類**で、しかも境目が「**シートが 10 枚あるか**」で割れた。

1. **ふりがなの連結**(7枚。**向こうの欠陥**)。向こうは `<rPh>` の中の `<t>` を
   本文と繋げて返す — `実` が `実ジツ` になる。**日本語の xlsx でふりがなの
   無い物のほうが珍しい**ので、向こうは日本の帳票で必ず踏む。officework は
   `phonetics` に別に持っていて正しい。**うちの穴に数えない**
2. **シートの取り違え**(3枚。**うちの欠陥。[大]**)。`xl/_rels/workbook.xml.rels`
   を読まず、部品名を**文字列で並べ替えて位置で対にしていた**。`sheet10.xml`
   が `sheet2.xml` より前に来るので、**シートが 10 枚以上ある帳面は必ず狂う**。
   黙って別のシートの中身を返す。台帳へ回した。
   **2026-08-09 に直した** — `r:id` を rels で解き、`<sheet>` の並びを
   ブックの並びにする。**書き出しにも同じ穴があった**(部品を並び順に
   振り直すのに、原本の rels と宣言をそのまま持ち越していた)。3枚とも
   取り違えの差が消え、往復しても中身が動かない。詳しくは
   [corpus.ja.md](../corpus.ja.md) の「シートの取り違えを直した後」

**設計への効き。**

- **1 は pyoffice の売りになる。** 「同じ答えを返す」を目標にしてきたが、
  ここは**違う答えのほうが正しい**。突き合わせの道具に「向こうが間違って
  いると分かっている差」の枠を作り、うちの宿題と混ぜない
- **2 は、突き合わせを始める前に読みの土台が抜けていたということ。**
  進め方の「1. 読みから」は正しかった。**計算にも書きにも進まなくてよかった**
- **corpus はこの1件で元が取れた。** 自分で書く xlsx は `sheet1..9` しか
  作らないので、この穴は自分の答案では**永久に出なかった**

## サイドカーの骨を立てた(2026-08-09 当方。次の一手3)

`sidecar/`(実行ファイル名は**向こうと同じ `xlsx-sidecar`**)。
`XLSX_SIDECAR_PATH` で差し替えられるので、genoffice には**手を入れていない**。

**喋れるのは `open` / `read_range` / `close` / `cancel`。** 残りは
`unsupported_command` で**断る** — それらしい空の答えを返さない。
`recalc_cells` は次(進め方の2)、ZIP の配管は触らない(「切る場所」)。

突き合わせも Python 経由をやめて**サイドカー同士**にできる
(`pyoffice_diff.py --ours-sidecar …`)。**本番と同じ道で比べるのが正しい。**
corpus 24 枚 + sample 6 枚で、Python 経由と同じ判定になることを確かめた。

### 返せるようになった欄(Python の窓では見えなかった物)

固定枠・列幅/隠し列/アウトライン・行の高さ/隠し行・コメント・
ハイパーリンク・条件付き書式・入力規則(文言まで)・シートの保護・表・
耳の色・隠しシート・名前の定義・CSE の範囲。

### 作法(この骨で決めたこと)

1. **断る所は断る。** 喋れない命令に空の成功を返さない
2. **埋めていない欄は名前で言う。** 答えに `xNotFilled` を添える
   (styles の索引表・リッチテキスト・グラフ・絞り込みなど)。
   向こうに無い欄だが、知らない欄は無視される作りなので邪魔にならない
3. **読めなかった物は `xUnsupported` に載せ、突き合わせが拾う。**
   これを繋ぐ前は `make_cond.xlsx` が○に見えていた(実際に踏んで直した) —
   **道具が緑を作ってしまう**型の失敗で、いちばん危ない
4. **原本が変わったらセッションを捨てる。** 黙って読み直さない —
   読み直すと、その間の編集がどちらの物か分からなくなる
5. **JSON だけは `serde_json` を使う。** 通信の言葉は向こうが決めた物で、
   こちらに直す権利がない。手書きの parser は静かに間違える場所そのもの。
   **核(`sheet`)には入れない** — 末端の実行ファイルだけの依存

### まだ揃っていない所(名前で言う)

| 欄 | どうする |
|---|---|
| `styles` / `dxfStyles` と `cells.styleIndex` | **次の便。** `CellFormat` から索引表を組み直す。設計は要らない、手を動かすだけ |
| `cells.rich` | モデルが持たない。潰すか断るかの決めが先(「埋まっていない穴」1) |
| `visuals` / `sparklines` / `pivotTables` | 当面向こうの実装を残す |
| `entryCount` / `defaultRowHeight` / `autoFilter` | モデルが持たない。**0 で誤魔化さず null** |
| `comments.author` | モデルが持たない(コメントは本文だけ) |
| シートの `id` | 向こうは `sheet-{sheetId}`、こちらは `sheet-{番号}`。モデルが `sheetId` を持たない。**呼ぶ側は open で受けた物を返すだけ**なので実害は無いが、一致はしない |
| `rowCount` / `columnCount` | 向こうは `<dimension>` の宣言、こちらは**実際に中身のある範囲**。家計調査で 108 対 106 の差が出た。`max(宣言, 実際)` に寄せるのが安全(宣言を当てにしない書き手がいる) |

## 書式を突き合わせて出た3件(2026-08-10)

`styles` の索引表を作ったので、初めて**書式を比べられる**ようになった。
日銀の帳面で出た3種類を、生の XML で裏を取って仕分けた。

### 1. 罫線の色 — **欠陥ではなかった(当方の読み違い)**

`向こう {'style':'thin','color':'000000'} / うち {'style':'thin'}` が大量に出たので
「うちが色を落としている」と書いたが、**誤り**。赤い罫線の xlsx を作って通したら、
**両方とも `FF0000` を返した**。`sheet` は罫線の色を読んでいる。

差が出ていたのは `<color indexed="64"/>` の場合だけ。**64 は「自動」で色ではない**
(標準パレットは 0〜63)。うちは「色の指定なし」として返し、向こうは `000000` に
解決して返す。**画面ではどちらも黒**なので、実害は無い。

**これは決めの違いとして残す。** 揃える必要はない — 設計の「向こうが間違って
いると分かっている差」の枠と同じ扱いで、うちの宿題には数えない。

**教訓**: 読み違いをコミットの説明に書いてしまった。**実物で裏を取ってから
書く**。今回は corpus に1枚足すだけで済んだ。

### 2. 表示形式 — **うちが正しい**

原本 `#,##0_);[Red](#,##0)` を、うちはそのまま返し、向こうは `_)` を空白に
変える。`_)` は「`)` の幅だけ空ける」の意味で、**向こうは画面に出すために
潰している**。ファイルに書いてある文字列を返すのが読みの仕事なので、
うちの答えを変えない。

### 3. 横位置 — **うちが落としている。ただし直しは calc に及ぶ**

`HAlign` に `centerContinuous` が無く、`center` に潰れる
(`sheet/src/model.rs:264`)。`centerContinuous` は「選択範囲の中央」で、
**結合していないセルにまたがって中央に置く**書き方。日銀の表題で使われている。
潰すと、表題が自分のセルの中で中央に寄ってしまう。

**同じ行で `distributed` も `Justify` に潰れている。** こちらのほうが重い —
**均等割付は日本語一級の看板**(SEKKEI 日本語 K4)なのに、xlsx から読むと
両端揃えになる。

直すには `HAlign` に変種を足すことになり、**calc の描画(`view.rs`)と
リボン(`cmds.rs`)まで 49 箇所に及ぶ**。pyoffice の都合で calc の見た目を
変える話になるので、**別の作業として切り出す**。
