= 文書の画面の表示を、紙と同じ頁の絵にする(hyouji-e)

作る側の資料です。検討と段取りを書きます。作った後の「いまの真実」は
link:../dev/README.ja.adoc[開発者マニュアル]に移します。

== 決めたこと(2026-09-27 発注者)

* aiseed office を早く出すため、**表示は完全に近く、編集は限定でも特定の用途に使える**形を
  目指します
* 表示は、Word や互換の Office と並べて機械で確かめます。編集は、人が確かめます
* 変更が大きいので、ブランチ `hyouji-e` で進めます。`main` には区切りごとに見てもらってから
  混ぜます

元になった調べは、発注者が貼った gpui と Vello の現状です。出典は確かめました(2026-09-27)。

* Zed は 2026-02-13 に、Linux の描き手を Blade から wgpu に替えました(zed PR #46758)。
  macOS は Metal、Windows は DirectX のままです
* 画面を出さずに wgpu で描く仕組みは、Linux と Windows 向けに取り込まれました
  (zed PR #62341 を作り直した #64718)
* gpui の画面に自分の GPU 描画を差し込む口について、Zed の人の答えはまだありません
  (zed discussion #45996)
* Vello は 2026-09-02 に、CPU と GPU を併せて使う版を `vello_gpu` として表に出し、元の GPU
  計算中心の版を研究扱いにする方針を決めました(vello issue #1871)
* `vello_cpu` は機能がそろい、残る注意は API がまだ変わることです

だから、画面の中に GPU の描き手を差し込むのは待ち、**頁は `vello_cpu` で絵にして、gpui は
それを見せるだけ**にします。officework は既に、紙の 1 頁(`pdfw::Leaf`)を `vello_cpu` で絵に
する口(`paper::e`)を持っています。

== この Mac で測った速さ(2026-09-27)

頁を絵にする時間です。1mm を 7.56 画素(Retina の 100%)で描きました。

[cols="3,1,2",options="header"]
|===
|文書 |頁数 |1 頁を絵にする時間

|Word の飲食店のパンフレット(写真入り) |3 |24 ミリ秒(1 頁目)
|`sample/報告書.docx` |1 |4.7 ミリ秒
|JST の計画書(公的な文書) |32 |平均 7 ミリ秒(全頁で 0.23 秒)
|===

頁に組む時間(0.5〜0.7 秒)は、いまの画面でも同じようにかかっています。画面に見えるのは
1〜2 頁なので、絵にする時間は問題になりません。大きな字はきれいに出ました。本文の
小さな字は、段 2 で画面に出して見ます。

== いまの文書の画面(2026-09-27 に調べた姿)

* **組む。** `Writer::lay`(writer/src/doc.rs)が `paper::compose_doc` と
  `paper::layout_doc` で組み、`self.page`(`kumihan::Sheet`)にします。印刷の
  `paper::doc_laid` と同じ組版ですが、紙の決め方が違います。画面は `self.pg` を 1 枚だけ
  渡し、印刷は節ごとの紙(`section_geometry`)を使います
* **積む。** `refresh_hf` が `kumihan::fold_print`(または見開きの `fold_pages`)で、
  `self.page` の行・罫線・画像の y を、紙を縦に積んだ位置へ書き換えます
* **描く。** 紙、帯と画像、塗り、罫線、字、ヘッダー、脚注、テキストボックス、図形を、
  すべて gpui の要素として 1 つの紙の要素の中に置きます。見えない頁も毎回置きます
* **編集。** カーソル、選択、クリック、IME、上下の移動は、積んだ後の `self.page.lines` を
  読みます
* **紙との違い。**
** ヘッダーとフッターは 1 頁目の番号で描き、節ごとの物や、先頭の頁だけ別の指定
   (`w:titlePg`)に従いません
** 図形(`doc.shapes` と他のソフトの図形)は、積む前の頁の位置で置いています
** PDF のボタンは古い書き手(printpdf)で、図形、浮かぶ写真、塗りが出ず、書体を 1 つしか
   使いません

== 目指す姿

. **紙と同じ頁のデータから描く。** 画面の組んだ結果(積む前の写し)から、`doc_pages` と
  同じ手順(`anchored_pictures`、`foreign_shapes`、`doc_hf_lines`、`sheet_leaves_fonts`)で
  `pdfw::Leaf` を作ります。**この同じ `Leaf` から、画面の絵も PDF も作ります**
. **画面は頁の絵を並べる。** 各頁の絵を、積んだ位置(`page_tops`)に置きます。見えている頁と
  その前後だけを描いて持ちます。拡大や画面の倍率が変わったら描き直します
. **編集は絵の上に重ねる。** カーソル、選択、IME、変更の印は、いまの積んだ後の座標で、
  gpui で絵の上に重ねます。字そのものは絵が見せます
. **PDF のボタンも同じ `Leaf` から。** エンジンの `doc_to_pdf` と同じ書き手(`pdfw`)を
  使います
. **頁の無い表示はそのまま。** 窓の幅で流すテンプレート(頁を持たない adoc)は、いまの
  描き方を残します

== 段取り

各段の終わりに、実機で見てから次へ進みます。

. **段 1: 頁のデータを作る。** 組んだ結果を、積む前の写しとして持ちます(組み立てた文書と、
  使った書体も)。そこから `Leaf` を作る関数を作ります。同じ文書で、この `Leaf` と
  `doc_pages` の `Leaf` を比べる試験を足します。紙の決め方(1 枚か節ごとか)をどちらに
  そろえるかも、ここで決めます
. **段 2: 表示の絵を出す。** 頁の絵を画面に出す形を足します。いまの描き方との切り替えを
  残し、まず docx を開いたときに使います。見えている頁だけを描きます
. **段 3: 編集の重ねを合わせる。** カーソルと選択が、絵の中の字の上に来ることを確かめ、
  ずれを直します
. **段 4: PDF のボタンを替える。** 同じ `Leaf` から `pdfw` で書きます
. **段 5: 機械で確かめる。** 画面の絵と、Word の PDF を絵にした物を並べて比べる道具を
  作ります(tools/)
. **段 6: 限定の編集。** 使う用途を発注者と決め、用途ごとに人が確かめる手順の表を作ります

=== 段 3 で分かったこと(2026-09-27)

* 横のずれ: カーソル、選択、クリックは、どの頁でも最後の節の左の余白(`pg.left_mm`)から
  数えていました。絵は頁ごとの余白で描くので、節で余白が変わる JST の計画書では、1 頁目が
  4.5mm ずれていました。行の y からその頁の余白を引く `left_at` を作り、重ねと、いまの
  描き方の字の両方に使いました
* 縦のずれ: gpui は字を箱の中で約 0.4 字下に置きます。前の描き方のカーソルと選択の帯は、
  それに合わせた値でした。絵の字は本当のベースラインにあるので、絵のときだけ別の値を
  使います(`CARET_TOP_PIC`、`SEL_DROP_PIC`)
* 確かめ方: macOS では、ほかのアプリの前面への切り替えが止められるため、クリックやキーを
  外から送れませんでした。ソケットに `select`(文字の番号で選ぶ命令)を足し、選択と
  カーソルを置いて画面を撮りました。段 5 の道具でも使えます

=== 段 4 で分かったこと(2026-09-27)

* docx の PDF のボタンは、頁の絵と同じ `Leaf` を `pdfw` で書きます。報告書では、
  `paper::doc_to_pdf` とバイトまで同じ PDF になりました。JST の計画書は 32 頁で
  508KB です(前の printpdf の書き出しは約 10MB でした)。印刷用のテンプレートが
  あるときと、この app の文書と、縦書きは、前の書き出しのままです
* 頁の色は組んだ文書に入っていないので、`PageSource.bg` で渡します。手書きの線は
  画面では上に重ねて描くので、PDF にだけ足します(`pdfw::put_ink`)
* 頁の絵の描き手(`paper/src/e.rs`)は、PDF の書き手と重ねる順が違っていました。
  重なりの順(`z`)を見ず、`paths`(曲線と切り抜きのある形)と蛍光ペンを描いて
  いませんでした。飲食店の三つ折りでは、ロゴの入る暗い枠が写真の下に隠れていました
  (Word の PDF では写真の上です)。PDF の書き手と同じ順で描くように直しました

=== 段 5 で作った物(2026-09-28)

`tools/screen_compare.py` です。docx と、Word がその docx から作った PDF を渡すと、両方を
同じ細かさの絵にして、頁ごとに比べます。

 DYLD_FALLBACK_LIBRARY_PATH=.venv/lib .venv/bin/python tools/screen_compare.py 文書.docx Word.pdf --out 出力先

* うちの絵は Python の `Doc.save("x.png")` で作ります。PNG の書き出し(`ops::png::doc`)は
  組んだ紙面だけを描いていて、浮かぶ写真、図形、ヘッダーとフッター、節ごとの紙が
  ありませんでした。PDF と画面と同じ `paper::doc_pages` から描くように直しました
* 絵の 1 画素は、相手の絵の `--mm`(既定 0.5mm)以内に近い色の画素が無いときに
  「違う」と数えます。字の縁の違いと、0.5mm より小さいずれは数えません
* 頁ごとに、紙の大きさ、違う所の割合(うちだけ、Word だけ)、違う所の大きい順に 8 か所
  (頁の左上からの mm)を出します。`--out` を付けると、頁ごとに「うち、Word、重ねた絵」を
  並べた PNG を書きます。重ねた絵では、Word だけの所が赤、うちだけの所が青です
* `--max 2.5` を付けると、2.5% を超える頁があるときか、頁数が違うときに 1 で終わります
* エンジンを直した後は、Python のエンジンを作り直してから使います
  (`env -u VIRTUAL_ENV CONDA_PREFIX=$PWD/.venv PATH=$PWD/.venv/bin:$PATH
  .venv/bin/maturin develop -q -m pysheet/Cargo.toml`)

試した結果です。JST の計画書(32 頁)は 28 秒で比べ終わりました。8 頁目の研究領域構成図は、
うちの方が約 6mm 上に出ていることが、重ねた絵と場所の一覧で分かりました。飲食店の
三つ折りの 1 頁目では、EMF のロゴが無いことと、字の位置のずれが出ました。

=== 段 6: 限定の編集(2026-09-28 発注者)

最初の用途は 2 つです。申請書の欄に書き込むことと、字を直すことです。adoc も扱います。

発注者の考えです。adoc はコードの部分が実体で、内容のある所です。docx と xlsx には、内容の
ほかの物が多く入っています。だから adoc は、コードを直す形にしました。

* *adoc:* 開くと、左にコード、右にそのページが出ます(`writer/src/code.rs`)。左は writer の
  編集画面で、ファイルの字を等幅で窓の幅に流します。保存では字をそのまま書きます。右は、
  コードから PDF と同じ手順(テンプレート、フォーム、表の数式、`paper::page_leaves`)で
  作ったページの絵です。入力が 0.35 秒止まると、別のスレッドで作り直します。PDF の
  ボタンは右のページを書き出します。`adoc_code = "0"` で前の形に戻ります
* *docx:* 手順 2〜4 のページの絵の上で直します。記入欄(コンテンツコントロール)と表のセルに
  書けます

機械の試験(writer/src/tests.rs):

* `an_adoc_is_edited_as_its_text`: コメントと 2 つの空白を含む adoc を開き、1 語を直して
  保存すると、直した所だけが変わる。右のページは直した字を出し、コメントは出さない。PDF が書ける
* `a_form_is_filled_and_a_word_fixed_in_a_docx`: `sample/writer/03_申込書.docx` の氏名の欄に、
  打鍵と同じ処理(`ui::handler::replace`)で名前を入れ、本文の 1 語を直して保存する。開き直すと、
  名前は氏名の欄(`w:alias`)の中にあり、直した語が本文にあり、ほかの記入欄も残っている

人が確かめる手順です。機械の試験では、画面の見た目と Word での開き方を確かめられません。

|===
|用途 |手順 |見る所

==== adoc はコードに慣れてもらう(2026-09-28 発注者)

adoc はビジュアルで直すより、コードに慣れてもらう方針にしました。慣れるために、次の 4 つを
作りました。

* 右のページを押すと、左のその字へカーソルが移る(`code_click`)
* 左のカーソルに合わせて、右のページを送り、その行に黄色の帯を付ける(`code_sync`)
* 早見表 `sample/writer/07_早見表.adoc`。開くと、書き方と出来上がりが並ぶ
* 誤りと、ページに出せない書き方を、ファイルの行の番号と一緒に右の上に出す。エンジンの
  `parse_many_full` は、2 枚目からの文書の行の番号をファイルの行に直すようにした。
  出せない書き方の一覧には、最初の行の番号を付けた

ページとコードの結び付けは、字の並びで探します。ページの字を行ごとに並べ、押した所から
数文字を、左のコードで同じ回数めに出る所に合わせます。コードの印(`*` `|` など)で字の並びが
切れるので、8 字、5 字、3 字、2 字、1 字の順に短くして探します。組版がコードの位置を
持っていないので、この形にしました。

マニュアルの冒頭は、「.adoc はコードを直す」「.docx はページの上で直す」の形に書き直しました。

残っている事:

* adoc のコードの画面で、太字などのボタンを灰色にする(いまは押してもファイルは変わらない)
* adoc を前の形(ページの上で直す)で開くときも、ページの絵で見せる
* 出せない書き方の一覧は、エンジンが日本語で書いている。ほかの言語の画面でも日本語で出る

== 気を付けること

* 絵の頁の字は、そのままでは選べません。選択、写す、探すは、いまの重ねの仕組み
  (`self.page.lines`)で続けます
* Retina の 1 頁は約 14MB の画素です。見えている頁と前後の頁だけを持ちます
* `vello_cpu` の API は変わります。触るのは `paper/src/e.rs` だけに閉じます
* 表の画面(calc)は、文書の画面が固まってから同じ形にします
