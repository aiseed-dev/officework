== 向こうの作り(2026-08-09 調査)

xlsx サイドカーは `apps/sheets/native/xlsx-engine/`(Rust 7,070行)。
TypeScript とは **stdin/stdout の JSON 1行ずつ**で話す(`apps/sheets/src/main/xlsx-sidecar-client.ts:178-185` が `spawn`)。

要求は `{version, requestId, command, …}`、答えは `{version, requestId, ok, result|error}`。
時間切れは 30 秒(書庫の操作だけ 180 秒)。

*要点: 向こうの Rust は xlsx を「書か」ない。*

* 読み: サイドカーが解いて、セル・書式・結合・条件付き書式・入力規則・

  図形・グラフ・スパークライン・コメント・名前の定義まで返す

* 書き: *TypeScript が XML のパッチ計画を作り*(`planCellEditsToXlsx`)、

  Rust は `save_archive(source, target, replacements, removals, additions)` で  *ZIP の差分を当てるだけ*。
変えないエントリは圧縮済みのまま丸ごと写し、  前後のマニフェストを CRC32 と大きさで照合する

* 計算: `recalc_cells` が `ironcalc`。セッションに Model を residents させる

== だから、そのままでは嵌まらない

officework の `sheet` は**モデルを持って自分で書き戻す**作り(`write_with` で原本を据え置き)。
向こうの「TypeScript がパッチを決め、Rust は ZIP を差し替える」とは**書き手が違う**。
ここを見ずに「エンジンを載せる」と言うと詰む。

== 切る場所 — 12 のコマンドを3つに分ける

[cols="1,1,1"]
|===
|組 |コマンド |扱い
|*エンジンの仕事* |`open` `read_range` `read_formula_cells` `read_media` `recalc_cells` |*`sheet` に差し替える*(ここが本題)
|セッションの世話 |`close` `cancel` |そのまま(`sheet::Book` を id で持つだけ)
|*ZIP の配管* |`archive_manifest` `read_entries` `scan_entries` `save_archive` `convert_workbook` |*触らない*。エンジンの仕事ではない
|===

*12 のうち置き換えるのは 5 つだけ。* 残り 7 つは ZIP とセッションの世話で、向こうの実装が既に堅い(マニフェスト照合まである)。
ここを書き直す理由はない。

== 進め方 — 通信の言葉は1文字も変えない

*同じ 12 コマンドを、同じ JSON の形で喋る。* そうすればサイドカーの実行ファイルを差し替えるだけで済み、TypeScript 側は何も知らなくていい。
A/B で戻せるのも大きい(環境変数でどちらを起動するか切り替える)。

. *読みから*。`open` / `read_range` / `read_formula_cells` を `sheet` で

   実装し、向こうの実装と**同じ入力に同じ答えを返すか**を突き合わせる   (実物の xlsx を何十枚か通して JSON を diff する試験を先に作る)

. *計算*。`recalc_cells` を `sheet::calc` に。ironcalc が外れる
. **書き**は最後。ここだけは TypeScript 側の作り替えが要るので、1と2で

   エンジンの信用ができてから。
*急がない* — 向こうの ZIP 差分保存は   よく出来ていて、当面そのままで困らない

== 埋まっていない穴(先に知っておく)

. *リッチテキスト*。向こうは共有文字列の中で色が変わる run を読んで返す。

   officework は**セルの中で書式が変わることをモデルに持たない**   (2026-08-09 の決定 — 代わりにマークダウンで描く)。
ここは   「読んで返すだけ」の形で足すか、平文に潰して報告するかを決める必要がある

. *グラフとドローイングの深さ*。向こうは chart XML の系列まで構造化して

   返す。
officework は図形・画像は持つが、グラフは matplotlib で画像として   置く作りなので、*返せる中身が違う*

. *セッションの居座り*。向こうは Model をセッションに残し、ファイルの

   mtime と大きさで自動的に捨てる。
officework 側も同じ仕組みを用意する

この3つは「難しい」のではなく「*返す中身が違う*」問題。
1 は正直に潰し、2 は当面向こうの実装を残す(ZIP 配管の組に置いてよい)、3 は素直に作る。

=== 固定枠が抜けていた(2026-08-09 当方。*保存で落ちる欠陥だった → 塞いだ*)

`sheet` は `sheetViews` を **`rtl` のときだけ**書いていた。
`pane`(固定枠)は**読んでもいないし書いてもいなかった**。
つまり Excel で見出し行を固定した台帳をcalc で開いて保存すると、*固定が黙って消えていた*。

pyoffice の話より先に **calc 側の欠陥**だったので、先に直した。

*直した中身。*

* `Sheet::freeze: Option<FreezePane>`(`frozen_rows` / `frozen_columns`)。

  **止める行数・列数**で持つ = Excel の「先頭の行を固定」と同じ数え方で、  genoffice のサイドカーが返す形と同じ。
突き合わせで欄を組み替えずに済む

* `sheetViews` は **常に**書く。rtl だけの条件を外したので、右から左と固定枠が

  同じ `sheetView` に同居する

* `showGridLines` / `showFormulas` / `zoomScale` も**併せて往復させた**。

  同じ元素の属性で、書く場所が要る話でもないのに落ちていた。
いずれも `Option` で持ち、*原文に無かったものは書き足さない* —   既定を書き足すと、触っていない帳票にまで差分が出る

* `state="split"`(掴んで動かす分割)は固定ではないので読みで撥ねる。

  分割の `xSplit` は列数ではなく **1/20 ポイントの座標**なので、固定として  読むと途方もない列数になる

*calc も繋いだ。* `sheet` だけ直すと、ファイルの往復は直る(モデルを素通しで書き戻すため)が、**画面とファイルが別のことを言う**状態が残る。
calc の固定枠は``App::frozen`` という画面の状態で、モデルに触れていなかったので:

* ファイルが「見出し行を固定」と言っていても、*固定なしで開く*
* calc の「ウィンドウ枠の固定」で固定しても、*ファイルに載らない*

`freeze_from_book`(開いた直後)と `freeze_into_book`(書く直前)の2つで繋いだ。
数え方は 1対1 —`App::frozen = Pos::new(1, 0)` がそのまま``FreezePane { frozen_rows: 1, frozen_columns: 0 }``。
**いま見ていないシートの固定も落とさない**ように、集める先は `sheet_ui`(シートごとの控え)にしてある。

*併せて見つかった地雷(こちらの方が根が深い)。* 読みは `sheetView` を``Event::Empty`` の枝でしか見ていなかった。
*Excel が書く `sheetView` は``<selection/>`` や `<pane/>` を抱えるので Start で来る。* つまり実物の xlsx では``rtl`` すら読めていなかった — 往復の試験が自分で書いた(子の無い)`sheetView` だけを見ていたので気付けなかった。
*自分の書き出しだけで往復を確かめると、この型の穴は必ず見落とす。* 実物の形を型紙にした試験を足してある(`見出し行を固定した実物の形を読める`)。

=== Python の窓が天井(2026-08-09 当方)

「比べる項目を増やす」で書式・罫線・条件付き書式・入力規則まで行きたかったが、*`officework.sheet` の Python の窓が返さない*。
出ているのは``Book``(`open` `save` `sheet_names` `unsupported` `recalc` `add_sheet`)と``Sheet``(`[]` `formula` `display` `shape` `values` `merges` 行列の出し入れ)で全部。
モデルには**ある**のに、窓が無いので比べられない。

*窓を太らせるのは筋が悪い。* pysheet は配っている製品で、比べるための穴を開けるために API を増やすのは順序が逆。
**本番のサイドカーは Rust で ``sheet``クレートを直に使う**のだから、比べる側も Rust から出すのが正道。

→ *次の一手 1 を書き換えた*(下)。

== 段階索引 — ここが一番大きい構造差(2026-08-09 当方)

向こうの `read_range` は `indexedThroughRow` / `indexingComplete` を返す。
**全部読み終わる前に答える**作りで、だから `cancel` があり、時間切れが 30 秒で足りる。
officework の `Book::open` は**全部読んでから返す**。

=== `indexingComplete` を読み違えていた(2026-08-09 に踏んだ)

`indexingComplete` は「*シートの索引が終わったか*」であって、「*要求した範囲が揃ったか*」ではない。
8 行の帳面で `indexedThroughRow: 7 `(= 全部揃っている)なのに `indexingComplete: false` が返った。
索引は別の走りで進んでいて、読みが先回りしただけ。

*当てになるのは `indexedThroughRow >= 要求の最終行`。* `indexingComplete` を「まだ読めていない」と読むと、揃っている答えを毎回疑うことになる。

*副作用がある*(向こうの `lib.rs:749-764`): *条件付き書式・絞り込み・入力規則・シートの保護は `indexingComplete` のときだけ返る*。
早く読むとこれらは**黙って空で返る**。
呼ぶ側は後でもう一度読んで埋める前提の作り。

*決め:*

. 最初は `indexingComplete: true` を返して全部読む。実物で 30 秒に触ってから

   段階化する。
触る前に作らない

. ただし**「空で返る」の真似はしない**。officework は全部読んでから答えるので、

   条件付き書式も入力規則も**最初から入っている**。
呼ぶ側(TypeScript)は   「後で埋まる」を許す作りなので、*先に埋まっている分には壊れない*
