=== calc に残すもの(Python に出さない)

* 帳票の形: 罫線・結合・書式・列幅・行高・印刷 — 様式は見ながら作るもの。印刷の設定(2026-08-03): pageSetup / pageMargins / Print\_Area は**モデルに読む**(向き・用紙・四辺の余白・印刷範囲)。UI とPDF が使い、保存は**原文への属性差し替え**(拡大縮小・印刷機の参照など理解しない属性を消さないため。丸ごと作り直すと「書式は据え置き」が破れる)。用紙コードの B は JIS(ECMA-376 の表は ISO だが日本の実情は JIS —ここは日本の事務様式のためのソフト)
* 式の再計算: 開いた見積書が正しく計算されるのはアプリの責務
* 並べ替え・フィルター: 見ながらやる操作
* データの入力規則・条件付き書式: 入力の現場で効くもの(*済* 2026-08-03。条件付き書式は cellIs、入力規則は list を読み・効かせ・往復。入力規則の候補は formula1 の**原文**で持つ — 範囲参照 `$D$2:$D$5` の中身が変われば候補も追従する。規則に合わない入力はセルに入れず、Esc で戻す。候補が解決できない規則(別のシートへの参照等)では**堰き止めない** —読めない規則で利用者を閉じ込めるより、通して警告しない方を取る。list 以外の型は Report へ(保存で失われる、と言う))

=== 端末のソフトの土台として(2026-08-04 発注者)

「これで端末のソフトはいくらでも作れる」— 二つの意味で正しく、二つ目が本命。

*1. 新しいバイナリの土台として。* 難所は一度だけ解けばいい。
IME・日本語フォント・GPU 描画(GPUI)・印刷/PDF・リボン・ダイアログの別スレッド化・undo の規律・排他ロック・Python 拡張(サンドボックスつき)・仮想画面での自動検証 — 全部が共有クレート(kumihan / sheet / paper / ui)と作法(SEKKEI・方針・wiring\_tests)に貯まっている。
3本目のソフトはこの上に薄く載るだけ。

*2. 多くの業務ソフトは、もう「作らなくていい」。* Python in Calc +サンドボックス + ファイルサーバーで、**xlsx 1つが業務アプリそのもの**になった。
帳票(UI)+ コード(ロジック)+ 運用(状態列と入力規則)が1ファイル —問い合わせ・顧客・在庫・勤怠・日報・検収、事務の台帳系はほぼ全部この形に収まる。
共有フォルダがそのまま配布網で、導入も更新もファイルコピー。
*「いくらでも」の実体は、N 本のバイナリではなく N 個のブック。*

*改訂(2026-08-04 発注者確定): 新しいバイナリは作らない。* writer と calc の2本で打ち止め。
以後の「新しいソフト」はすべてブック(帳票+コード+運用)で作る。
UI が足りなければ、バイナリを増やすのではなく *calc / writer 側を伸ばす*(伸ばした部品は全ブックの共有財産になる — 図形・グラフ・UDF がそうだったように)。
バイナリを増やしたくなったら、それは**範囲の外の合図**(このソフトの仕事ではない)。
バイナリが2本で固定なら、検査・配布・保守の対象も2本で固定 — 「いくらでも作れる」と「保守が貯まらない」が両立する。

*↑の狭め方を改めた(2026-08-12 発注者)。* 固定するのは**バイナリの本数**ではなく**エンジンの本数**だった。
pyoffice(2026-08-09)と builder (2026-08-11 確定)でアプリが2つ増えたが、どちらも**同じエンジンに載る薄いアプリ**で、増えて困る物(エンジン)は増えていない。
正は SEKKEI.adoc「アプリは増える。
エンジンは1つ」。
この節の実務 —「UI が足りなければcalc / writer 側を伸ばす」「新しい業務ソフトはブックで作る」— はそのまま生きている。

限界も書いておく: 保守は貯まる(GPUI の上流追従、この規模を発注者+Fable で回し続ける前提)。
サンドボックスは OS ごとに組む — Linux は bubblewrap(済)、Mac はSeatbelt(「Mac 版」の節。
当初は「Linux 専用」と割り切っていたが2026-08-04 に改めた)。

=== ファイルサーバーの現実に合わせる(2026-08-04 発注者)

多くの現場はクラウドに移れない(閉域網・規程・データ主権)。
基幹は**共有フォルダの xlsx** であり続ける。
この設計はその現実のためにある:

* 帳票・コード・運用が**1つの xlsx** で共有フォルダに置ける(Python in Calc)。サーバーは物置のままでよく、Web アプリも DB も SaaS 契約も要らない
* 共有フォルダ = 他人のファイルが日常、という脅威にはニ重の防壁(自動実行なし+サンドボックス)が正面から答える。VBA が背負っていた危険の置き換え
* *排他*(済): 開くとき `.~lock.名前#`(LibreOffice と同じ場所)を見て、先客が居れば名乗りを見せ、*上書き保存を止める*(名前を付けて保存へ)。居なければ自分のロックを置き、閉じる・別のファイルへ移るときに外す。「二人で開いて後勝ちで潰す」という共有フォルダの定番事故を防ぐ。版の履歴・バックアップはファイルサーバー側の仕事(スナップショット)
* writer も同じ排他が要る(未実装 — 相方の課題として HIKITSUGI へ)

=== Python in Calc(済 2026-08-04 発注者提案。同日、コードの持ち運びまで拡張)

データ > Python。
一行のコードか .py ファイルを、**b(ブック)と s(いまのシート)を束縛して**回す。
裏はいまの表を一時 xlsx へ写し(原本の部品ごと)、officework.sheet(pysheet)で実行し、保存されたものを読み戻して**1手として**適用する(undo は束 — 複数シートに触っても Ctrl+Z 一回で戻る)。
失敗しても表は無傷(実行は複製の上)。

*コードはブックに載せて持ち運べる*(発注者判断 2026-08-04)。
`@save 名前` で .py をブックに載せ(xl/joPython.xml。
この形式の独自部品)、`@名前` で実行、`@list` `@del 名前`。
帳票とコードが一緒に旅をする —マクロの利便はこれで得る。
そのうえで**二重の防壁**が旧原則の核を守る:

. *開いても決して自動実行しない。* 実行は常に明示の操作(@名前)だけ。「開く=実行」という攻撃経路は今までどおり存在しない
. *ブックに載っていたコードは必ずサンドボックス(bubblewrap)の中で回す* —他人のファイル由来かもしれないから。サンドボックス: ネットワーク遮断・実ファイルは読み取り専用・ホームは不可視(tmpfs)・書けるのは交換用の一時領域だけ。サンドボックスの無い機械では載ったコードは**実行しない**(そう言う)。自分で打った/選んだコードも、サンドボックスがあればサンドボックスで回す(深層防御)

*↑を狭めた: ブックが運べるのは関数(UDF)だけ*(発注者確定 2026-08-08)。
同梱 Python を見据えて見直し — 手続きがブックで旅をすると**ファイルが実行の起点**になる(二重の防壁があっても、ブックの文言で「@名前 net と打って」と説得する道が残る = 帳面の中身を外へ送る経路)。
UDF は net の道が無く返せるのはセルの値だけなので、載せてよいのは UDF だと切った:

* *joPython に書くのは「関数」で始まるスクリプトだけ*。@save も関数だけ受ける
* *手続きは全部外部* — ~/.config/officework/plugins の .py を `@名前` で実行(サンドボックス必須・網なし既定・`@名前 net` でその場だけ網あり。従来の @名前 の作法のまま実行元が plugins に変わった)。ファイルを受け取っても手続きは付いて来ない
* 古いブックの手続きは読むが**実行できず、保存で消える**(開くときの報告でそう言う — 黙って落とさない)。`@export 名前` で .py に取り出し、中身を確かめて自分で plugins へ置く — それが取り込みの門
* 問い合わせ台帳のような運用は「1機械1回、plugins に据え付け」に変わる。ブックは帳票と関数だけを運ぶ
* 併せて実行に**時間制限**(手続き60秒・UDF 30秒)。サンドボックスの中の無限ループでも殺せるように、出力は別スレッドで吸い出しつつ try\_wait で見張る(py.rs のrun\_with\_timeout)

**↑をさらに狭めて、ブックからコードを全部外した(発注者確定 2026-08-09)。
**発注者の言い方で言うと、このソフトは *「VS Code と Excel(VBA を除いた)を合体させたもの」= native python excel*。
VBA を除くとは「文書の中にコードを埋める仕組みを持たない」ということで、コードは VS Code と同じく**ファイルシステムの上の .py** にある。

* *交換されるファイルはデータだけ。* データを受け取って、*処理は自分のコードでする* — だから関数(UDF)も手続きも ``~/.config/officework/plugins/*.py``にあり、ブックには1バイトも入らない
* `xl/joPython.xml` は**廃止**(読むだけ・書かない)。古いブックのコードは実行できず保存で消える。開くときに報告し、`@export` で .py に取り出せる
* *セルの式は普通の関数呼び出し*: `=倍(A1)`。plugins に `def 倍(x)` があればそれが呼ばれる(名前は日本語でよい)。`=PY("倍", A1)` も残す。そのために**字句解析で名前の頭を ASCII に限るのをやめた** — 副産物として和文の未知の名前が `#ERROR!` から `#NAME?` に揃った(在庫だった印の不揃い)
* *デコレータは作らない*(`@xw.func` / `@xw.ret(expand='table')` は不要)。あれは xlwings が Excel という他人の家に関数を登録するための仕組みで、こちらには境目が無い。広がり方は**返り値の形**が決める(2次元→表にスピル、1次元→縦)
* *引数が変われば裏で自動計算*(`@計算` は手回しとして残す)。式の評価の中でPython を同期で回すと画面が止まるので、`Sheet::py_stamp`(引数の指紋)が動いたのを 200ms ごとの見張りが見て、別スレッドでまとめて回し、答えが揃ってから**1手として**書き戻す。自動の分は undo の節目を作らない
* *サンドボックスは着せない*(bubblewrap を外した)。あれは「ブックから旅して来たコード」のための鎧で、コードが自分のものだけになった以上、VS Code でスクリプトを走らせるのと同じ扱いでよい。`@名前 net` の区別も消えた(打つと「要らなくなりました」と言う)。**外部データの取り込みには実ファイルが読める必要がある**ので、鎧は用途とも噛み合っていなかった
* *手続きは動いている calc をそのまま操る*(一時ファイルの複製をやめた)。記事の見出し「ファイルではなくて Excel そのものを操作するライブラリー」がそのまま設計になる: 子のプロセスが officework のソケット越しに書く。`Book.caller()` は `Book.attach()` と同じもの。1手続き=1undo は``Calc::rpc_batch``(手続きの頭で節目を1つ置き、その間 rpc は置かない)
* 残る安全は**置く前に読む**の一点。ファイルを受け取っても手続きは付いて来ないので、「開いた瞬間に他人のコードが走る」は原理的に起きない

*↑の「外した」の正確な姿(2026-08-12、コードと突き合わせた)。*「着せない」は言い切り過ぎだった — 消したのは「*組めなければ実行しない*」という必須の条件で、仕掛け(`Cage` — bwrap / flatpak-spawn)はcalc/src/py.rs に生きている。
**Python の道は2本**あり、囲いの扱いが違う:

[cols="1,1,1"]
|===
|道 |何が走る |囲い

|*RPC*(動いている calc をソケット越しに直に操る) |plugins の手続き(`@名前`)・UDF(`=倍(A1)`) |無し(素の Python)。門は**置く前に読む*
|*複製の上で回して読み戻す* |データ > Python の一行・writer のマクロ |*あれば囲う*(深層防御 — py.rs の注記のまま)。無くても走る。失敗しても表は無傷

用途が違うので**2本とも残す**。
マクロは失敗しても表が無傷、RPC は Jupyterから見ながら触れる。
python-manual はこの区別を既に正しく書いている(「データ > Python の一行と writer 側は、いまも複製の上で走る(サンドボックスがあれば使う)」)— 設計のこの節だけが粗かった。

*次に来る大物*: plugins の .py を calc の中で編集する画面(VS Code 側の半分)。
いまパネルに `@名前` と打つのはその代用品。

Python in Excel との違い: あちらはクラウド実行(データが Azure へ出る・従量課金)。
こちらは**手元で動き、基幹網の外に出ない**。
polars・scipy・matplotlib など機械にある物が全部使える。
Excel は未知の部品を保存で落とすことがあるので、Excel で開いて保存し直すと載せたコードは消え得る(コードは消えても値は残る — 劣化は安全側)。

*UDF とスピル*(済 2026-08-04。
発注者の 2018 年の Qiita 記事「Excel に Python が搭載?その後 — xlwings を使おう」が前史。
xlwings の目玉だった「Python で書くセル関数」を、8年後に自分の calc へ本搭載。
*注意: この節は 2026-08-04 の姿* — `@save` と「開いても再計算でも実行されない」は上の 2026-08-09 の節で改まった。
いまは def が plugins に住み、セルは `=関数名(…)`、引数が変われば裏で計算し直す):

* セルに `=PY("関数名", 引数…)`。関数の定義はブックの**「関数」で始まる名前のスクリプト**(@save 関数)にある def
* *PY セルは開いても再計算でも実行されない。* 最後に計算した値を保ち、未計算なら #PY? の印。評価はパネルの `@計算` のときだけ、**網なしサンドボックス**の中で一括 — 「開く=実行を持たない」はセル関数でも破らない
* 2次元の返り値は右下へ**スピル**。展開先に他人のデータや式があれば#SPILL! で止まる(潰さない)。縮んだときは前回の面の残骸を消す
* 引数は式をいま評価した値で渡す(範囲は列数つきの2次元)。式は保たれるので、@計算 を押し直せば新しい引数で再評価される
* Excel で開くと PY は #NAME? になる(値は保存されているので、Excel が再計算するまでは見える)。劣化は正直に

*サンドボックスは段階制*(2026-08-04。
Web の問い合わせ取り込みのため):

* 自分で打った/選んだコード: *網ありサンドボックス*(ファイルは守られたまま、網は通る —自分の道具が Web から取り込むのは普通の仕事)
* ブックに載って旅してきたコード(@名前): **網なしサンドボックス**が既定
* `@名前 net` と**その場で打ったときだけ**網ありサンドボックス — 許可は毎回の明示の操作で、*ブックには決して保存されない*(ファイルが自分に権限を与えることはできない)

*使い所の実例 — Web の問い合わせ台帳*(実証済み): フォームの受信箱(API / CSV)を取り込むコードをブックに載せ、`@取り込み net` で台帳に「受信・名前・用件・状態=未対応」を追記する。
帳票・コード・運用が1つの xlsx で旅をする。
網なしサンドボックスでは同じコードの通信が拒否されることも実証。

配り方: `pip install officework`、または `officework/` パッケージを**calc の隣に**置く(calc は自分の居場所を `sys.path` に足して``from officework import sheet`` する)。
無ければ status がその手順を言う。
*裸の `.so` を置く形は 2026-08-09 に終わった* — docx / pptx が来ても同じ名前空間に入るよう、エンジンを `officework.sheet` へ移したため。

=== 分業の橋 — `pysheet`(済 2026-08-03)

`sheet` を Python から呼べるようにした(pyo3, crate は `pysheet`、配る名は `officework`、エンジンは `officework.sheet`)。
openpyxl と違い、罫線・結合・列幅・図形を保ったまま値を差し込める — *polars で集計 → 帳票の枠を保ったまま差し込む*。
マクロの置き換えがスクリプトになる、という当初の設計と一直線。

== Python の置き場は3つ・契約は2つ(2026-08-16 発注者)

発注者の指摘4つ — 「リボン用のマクロは別にしたほうがいい」「ピボットテーブルやグラフがその例になる」「システム定義とユーザー定義に分ける必要がある」「Python の関数も同じで、システム組み込みの関数と UDF」。

=== 誰が呼ぶか × 誰が定義したか

[cols="1,1,1"]
|===
|誰が呼ぶ |システム定義 |ユーザー定義

|*式* |組み込み関数(`calc/src/funcs.rs`。SUM 等) |`~/.config/officework/funcs/*.py`
|*リボンのボタン* |同梱の台本6本(`pyrun` の `BUNDLED`) |`~/.config/officework/ribbon/*.py`
|*一覧から人が選ぶ* |— |`~/.config/officework/plugins/*.py`
|===

置き場を分けた理由は**危うさが違う**こと。
式に残ったものは人の押す手を通らず、開くたび・再計算のたびに走る。
ボタンは押したときだけ走る。
1つの置き場に混ぜると「マクロの補助関数」が式から呼べてしまう(実際そうなっていた)。

=== 契約は2つあり、揃えない

* *同梱の台本 = 「指図 → 答え」の純関数。* 呼ぶ側(Rust)が選択範囲を読んでJSON に組み、台本はそれだけを見て答え(画像・CSV・数)を返す。*ブックに触れない* — RPC の口も `officework` の取り込みも持たない
* *利用者のマクロ = 「押されたら RPC でブックを操る」。* 引数は無く、動いている calc を `xw.Book.attach()` で掴む

2026-08-16、「同じ形に揃えては」と一度提案して**取り下げた**。
揃えるとは同梱の台本に**今は持っていないブックへの手**を与えること — 見た目のために安全を1段下げる取引になる。
代わりに(1)契約が2つあることをここに書き、(2)同梱の台本を**読む道**(マクロ > リボンのマクロ > 同梱: …)と、(3)正しい契約の**見本を作る道**を置いた。
狙い(読んで自分のを作れる)は、揃えなくても取れる。

=== 名乗り

リボンに出るには札・絵・段を名乗る必要がある。
plugins の .py は何も名乗らなくてよい(一覧に名前が出て人が選ぶ)。
名乗る物と名乗らない物を同じ置き場に混ぜると、「名乗り忘れ」と「名乗る気が無い」が区別できない。

[source,python]
----
リボン = {"札": "月次の締め", "絵": "py-run", "段": "マクロ"}
----

名乗りは**読むだけで走らせない**(`pyrun::ribbon_decls` は行を読む — Python を起こさない)。
ここで走らせたら「押したときだけ走る」が嘘になる。
札は**訳さない**(利用者自身の言葉)。
静的な表にも対訳の表にも入れない — 14言語をボタン単位で突き合わせる門番が数え違えるため。

== 上位互換は API とテストの蒸留で作る — 実装は写さない(2026-08-12 発注者確定)

|*形を変えて保存する* |`.docx` で開いて `.adoc` で保存する、その逆もできる。テンプレートは別のファイル
|===

*入り口を1つにするか、2つにするか*は決めが要ります。
python-docx は開くと新規が同じ `Document()` ですが、
うちは `Doc.open(path)` と `Doc()` に分かれています。
当方の案は*今のまま分ける*です。理由は、開いた文書と白紙の文書では `save` の約束が違うからです。
開いた物は「原本を持ち越す」、白紙は「一から書く」で、同じ名前にすると約束が2つになります。

=== 決めていただきたい事(4つ)

. *`.adoc` の読み書きを Python から出すかどうか。* 当方の案は*出す*で、これを最初にやります。
エンジンには既に `parse` と `write` があり、繋ぐだけです。
これが無いと (b) の道が絵に描いた餅のままで、「本文は AsciiDoc」という設計と、
配っている API が食い違い続けます
. *積み上げの API を残すかどうか。* `add_paragraph` などは既に作ってあり、python-docx から移ってきた人のコードが動きます。
蒸留の筋で言えば要りませんが、消すと互換が壊れます。当方の案は*残すが、手引きでは (b) を先に書く*です
. *「上位互換」という言い方を続けるかどうか。* 正解をうちが決めるなら、「相手より多い」ではなく「相手より少なくて済む」が売りになります。
言い方を変えるなら、README と手引きの書き直しが要ります
. *見た目の 38 個をどう断るか。* テンプレートへ移すと決めたとき、`run.bold = True` を呼ばれたらどうするかです。
当方の案は*受けて効かせる(既にそう動く)が、手引きでは勧めない*です。黙って無視するのは最も悪いと考えます

=== なぜこの分類が良いか

理由は3つあります。

. *リボンは既に蒸留してある。* 本家との突き合わせを4便かけて済ませ、家の方針で採否を決めた結果が今の 11 タブ・124 ボタンです。API の分類を新しく考えるより、この一覧を使うほうが確かです

== 必要な API の一覧(仕様の下書き)

*プログラムを書くには仕様が要ります*(2026-08-24 発注者)。

== 設定とテンプレートをどう分けるか(2026-08-24 発注者)

発注者「設定情報も最近は多い。Template と合わせてどう扱ったらいいと思う」。

まず数えました。
*設定*(`settings.toml`)は 10 個です。
言語・画面の明暗・画面の倍率・開くときのエディタ・探す先のフォルダ・前回のフォルダ・
利用者の名前・キーの割り当て・反復計算・数式の入力支援。
*テンプレート*(`kumihan::Theme`)は 12 種類を持ちます。
組み方・書体・大きさ・ページ設定・送り先・ヘッダー・フッター・透かし・ページの色・縦書き・スタイル・様式。

=== 分ける基準は1つでよい

当方の案は、*「隣の人に渡したとき、同じ結果になってほしいか」*で決めることです。

* *同じになってほしい* → テンプレート。文書と一緒に配る
* *同じでなくてよい* → 設定。その機械とその人の物で、配らない

この1つで足ります。
テンプレートは「指示する人が作って配る」物なので、渡した先で同じに出るのが値打ちです。
設定は「この人がこう使いたい」なので、渡した先で同じになると*かえって困ります*。
画面を暗くしている人の好みが、書類を受け取った人に移っては困ります。

=== この基準で測ると、外れている設定が2つある

*(1) `calc_iter`(反復計算)。*
反復の回数と打ち切りの値です。*これを変えると計算の答えが変わります。*
つまり同じブックを隣の人が開くと、違う数字が出ます。
Excel はこの設定を*ブックの中*に持っており、その理由も同じはずです。
いまは `settings.toml` にあるので、*配る側に移すのが筋*だと考えます。

*(2) `user_name`(利用者の名前)。*
コメントを書いた人として*文書の中に入ります*。
設定に置くこと自体は正しい(人ごとに違う)のですが、
*結果が文書に残る*点が他の9個と違います。
プログラムから使うときは、設定を読まずに*引数で渡せる*ようにしておくべきです。

残り8個は基準どおりで、動かす必要はありません。

=== 言葉が1つ交差している

`Theme` の項目に `setting`(組み方。紙か Web か)があり、
`settings.toml` の項目に `theme`(画面の明暗)があります。
*名前が入れ替わって使われています。*
どちらも通じてはいますが、この節の話をするときに混乱の元になります。
当方の案は、`Theme.setting` を `mode` か `出力`(組み方)に改めることです。

=== プログラムからは、設定を読ませない

ここがいちばん大事だと考えます。

*同じプログラムが、機械によって違う結果を出してはいけません。*
アプリは人が見ながら使うので、設定に従って見た目が変わってよいのです。
プログラムは人が見ていないので、`~/.config` の中身で結果が変わると、
*動かした機械によって出来上がりが違う*ことになります。
しかも違いに気づけません。

したがって Python の側は次のようにします。

. *設定は読まない。* 既定値で動きます
. *必要な物は引数で受ける。* 言語も名前も、呼ぶ側が書きます
. *テンプレートは明示で渡す。* フォルダから拾うのはアプリの作法で、プログラムでは名指しします

....
d.to_html("out.html", template="web")          # 見た目は明示
d.save("報告書.docx", template="社内様式")       # 同上
p.add_comment("確認しました", author="西治")    # 名前は引数。設定を見ない
....

=== 3つに分ける

以上をまとめると、持ち主は3つです。

[cols="1,1,2"]
|===
|物 |置き場 |配るか

|*中身* |文書(`.adoc` / `.docx`) |配る
|*テンプレート* |フォルダの `.tmpl.adoc` |*配る*(文書と一緒に)
|*設定* |`~/.config/officework/settings.toml` |*配らない*(この機械の物)
|===

Python のオブジェクトも同じ3つにします。
`Doc`(中身)と `Template`(見た目)を作り、*設定に当たるオブジェクトは作りません*。
作ると、プログラムがそれを読むようになり、上の決めが崩れるためです。

=== 決めていただきたい事
