= Euro-Office core の問題の記録

ODF の読み書きを作るとき、LibreOffice と並べて Euro-Office core
(github.com/Euro-Office/core)の `OdfFile` を参考にしています
(SEKKEI「決め: ODF を先にする」)。置き場は `vendor/euro-office-core` です。

読んでいて見つけた問題をここに控えます。まとめて issue に投稿するためです
(2026-10-05 発注者)。issue の本文は英語で書いておきます。

投稿する形(本文と再現用の ods)は `euro-office-issues/` にあります
(2026-10-06)。英語の本文は、そちらが新しい版です。

各項目には、どう確かめたかを書きます。

* 「コードを読んだ」は、Euro-Office を動かしてはいません。
* 「動かした」は、変換器で実際に変換して確かめました。Euro-Office は配布用の
  版が無いので、元になった ONLYOFFICE Desktop Editors 9.4.0(flatpak)の
  x2t を `tools/oo_pdf.py` で動かしました。同じ所を Euro-Office core の
  コードでも確かめ、同じ書き方であることを見ています。

見たのは main の 4d2c0365(2026-09-30)です。

== 1. 条件付き書式の値の中の「top」「bottom」「duplicate」で、規則の種類を取り違える

確かめ方:: コードを読んだ。動かした(2026-10-05。`="Desktop"` の規則が
  xlsx で `<cfRule type="top10"/>` になった)
場所:: `OdfFile/Reader/Converter/xlsx_conditionalFormatting.cpp` の
  `xlsx_conditionalFormatting_context::set_formula`

規則の種類を、値の文字列のどこかにその語があるか(`find`)で決めています。
語が値の頭にあるかは見ていません。普通の比較(`cellIs`)の判定は最後です。
そのため、文字列と比べる規則の値に「top」などの語が入っていると、
別の種類の規則として読みます。

例:「セルの値が "Desktop" に等しい」。LibreOffice はこれを
`calcext:value="=&quot;Desktop&quot;"` と書きます。`f.find(L"top")` が
当たるので、上位 10 項目(`top10`)の規則に変わります。「laptop」「stop」
「bottom line」「duplicate」を含む文字列でも同じです。

[source,text]
----
Title: ODF→XLSX: conditional formatting values containing "top", "bottom" or "duplicate" are converted to the wrong rule type

In OdfFile/Reader/Converter/xlsx_conditionalFormatting.cpp,
xlsx_conditionalFormatting_context::set_formula() picks the rule type by
searching for keywords anywhere in the calcext:value string (f.find(...)),
and only falls back to cellIs at the end. A plain comparison with a text
value that happens to contain one of the keywords is therefore taken for
another rule type.

Example: "cell value is equal to "Desktop"" is written by LibreOffice as
  <calcext:condition calcext:value="=&quot;Desktop&quot;" .../>
f.find(L"top") matches, so the rule becomes a top10 rule. The same
happens for values containing "bottom", "duplicate", "begins-with",
"contains-text", etc.

Suggested fix: match the function names only at the start of the value
(e.g. value starts with "top-elements(" / "bottom-elements(" /
"top-percent(" / ...), and treat values starting with an operator
(<, >, <=, >=, =, !=) as cellIs comparisons.

Found by reading the code at 4d2c0365 (2026-09-30), and reproduced with
the x2t of ONLYOFFICE Desktop Editors 9.4.0: an ods whose rule is
calcext:value="=&quot;Desktop&quot;" converts to <cfRule type="top10"/>.
----

== 2. ODF から xlsx への変換で、numFmts に count ではなく formatCode を書く

確かめ方:: 動かした。コードを読んだ
場所:: `OdfFile/Reader/Converter/xlsx_numFmts.cpp` の
  `xlsx_num_fmts::Impl::serialize`(168 行目)

ods を xlsx に変えると、styles.xml に `<numFmts formatCode="6">` が出ます。
`numFmts` が持つ属性は `count` で、`formatCode` は子の `numFmt` の属性です。
LibreOffice も `count` を書きます(`sc/source/filter/excel/xestyle.cxx` 1389 行目)。
規約は ECMA-376 Part 1 の 18.8.31 numFmts で、属性は count(numFmt の数)だけです
(2026-10-06 に Microsoft の [MS-OI29500] 2.1.713 と c-rex.net の規約の写しで確かめた)。
比べるための ods 49 個を
変換すると、どの xlsx にもこの形が出ました。openpyxl はこの xlsx を開けず、
`NumberFormatList.__init__() got an unexpected keyword argument 'formatCode'`
で止まります。

[source,text]
----
Title: ODF→XLSX: <numFmts> is written with a formatCode attribute instead of count

OdfFile/Reader/Converter/xlsx_numFmts.cpp, xlsx_num_fmts::Impl::serialize():

    CP_XML_NODE (L"numFmts")
    {
        CP_XML_ATTR (L"formatCode", arrFormats.size());

ECMA-376 Part 1, 18.8.31 numFmts defines the attribute count (the number
of numFmt children); formatCode is an attribute of numFmt, not numFmts.
LibreOffice writes count (sc/source/filter/excel/xestyle.cxx).
Every xlsx converted from an ods gets e.g. <numFmts formatCode="6">.
Strict readers refuse the file: openpyxl stops with
"NumberFormatList.__init__() got an unexpected keyword argument 'formatCode'".

Fix: CP_XML_ATTR(L"count", arrFormats.size());

Reproduced with the x2t of ONLYOFFICE Desktop Editors 9.4.0 (ods → xlsx);
the same line is in Euro-Office core at 4d2c0365 (2026-09-30).
----

== 3. 入力規則の「空白を無視する」を読まない(属性の名前の書き違い)

確かめ方:: コードを読んだ。動かした(2026-10-05。`table:allow-empty-cell="true"` の
  規則が、xlsx ですべて `allowBlank="0"` になった)
場所:: `OdfFile/Reader/Format/table.cpp` の
  `table_content_validation::add_attributes`(825 行目)

ODF の属性の名前は `table:allow-empty-cell` です。読む側のコードは
`table:allowempty-cell` と書いていて、属性を読みません。読んだ値を xlsx に
渡す処理もありません。そのため、ods から xlsx に変えると、すべての規則が
`allowBlank="0"` になります。書く側(`OdfFile/Writer/Format/table.cpp` 992 行目)は
正しい名前で書いています。

[source,text]
----
Title: ODF→XLSX: table:allow-empty-cell of a content validation is never read

OdfFile/Reader/Format/table.cpp, table_content_validation::add_attributes():

    CP_APPLY_ATTR(L"table:allowempty-cell", table_allowempty_cell_);

The attribute is table:allow-empty-cell (with a hyphen), as the writer in
OdfFile/Writer/Format/table.cpp spells it. The reader never sees it, and
table_content_validation::xlsx_convert() does not pass it on either, so
every rule converted from an ods gets allowBlank="0".

Fix: read L"table:allow-empty-cell", and set allowBlank from it in
xlsx_convert() (through xlsx_dataValidations_context).

Reproduced with the x2t of ONLYOFFICE Desktop Editors 9.4.0: rules written
by LibreOffice 24.2 with table:allow-empty-cell="true" all convert to
allowBlank="0". The same code is in Euro-Office core at 4d2c0365.
----

== 4. 入力規則の「等しい」を `=` で書くと値を失い、書くときは `==` を使う

確かめ方:: コードを読んだ。動かした(2026-10-05)
場所:: `OdfFile/Reader/Converter/xlsx_data_validation.cpp` の
  `xlsx_dataValidations_context::add_formula`、
  `OdfFile/Writer/Format/ods_table_context.cpp`(352 行目付近)

LibreOffice は「等しい」の規則を `cell-content()=5` と書きます
(`sc/source/filter/xml/XMLStylesExportHelper.cxx`)。x2t は `()==` だけを探すので、
`=` の規則は演算子と値を失います。たとえば「整数で 5 に等しい」は、xlsx で
`type="whole"` だけが残り、`operator` と `formula1` がありません。文字数の規則
(`cell-content-text-length()=3`)も同じです。

逆に xlsx から ods に変えるとき、x2t は `cell-content()==5` と書きます。
LibreOffice の読み込み(`sc/source/filter/xml/XMLConverter.cxx` の
`lclGetConditionOperator`)は `=` を演算子として読み、残りの `=5` を式として
読むので、結果としては通ります。ODF の規約(1.2 Part 1 の 19.596 table:condition)の
演算子は `<` `>` `<=` `>=` `=` `!=` の 6 つで、`==` はありません
(2026-10-06 に確かめた)。

[source,text]
----
Title: ODF→XLSX: content validation "equal" written as cell-content()=5 loses its operator and value

LibreOffice writes an "equal to" validation as
  table:condition="of:cell-content-is-whole-number() and cell-content()=5"
(sc/source/filter/xml/XMLStylesExportHelper.cxx). In
OdfFile/Reader/Converter/xlsx_data_validation.cpp, add_formula() only looks
for "()==", so the rule is converted with type="whole" and no operator and
no formula1. Text length rules (cell-content-text-length()=3) lose their
value the same way.

The ODS writer (OdfFile/Writer/Format/ods_table_context.cpp) writes "()=="
for equal. LibreOffice happens to read it, because it takes "=" as the
operator and "=5" as the expression. Writing "=" would match LibreOffice.

The condition grammar (ODF 1.2 Part 1, 19.596 table:condition) has the
operators '<' | '>' | '<=' | '>=' | '=' | '!='; "==" is not one of them.

Suggested fix: in add_formula(), accept "()=" (after testing "()<=",
"()>=", "()!=" and "()=="), and write "()=" in ods_table_context.cpp.

Reproduced with the x2t of ONLYOFFICE Desktop Editors 9.4.0. The same code
is in Euro-Office core at 4d2c0365.
----

== 5. 入力規則の条件を「and」の字のすべての所で切る

確かめ方:: コードを読んだ。動かした(2026-10-05。一覧の項目「Grand」「Hand」「Stand」が
  xlsx で `""G"` になった)
場所:: `OdfFile/Reader/Converter/xlsx_data_validation.cpp` の
  `xlsx_dataValidations_context::add_formula`

`boost::algorithm::split_regex(arrFormula, formula, boost::wregex(L"and"))` で、
条件を「and」という字の所で切っています。前後の空白も、引用符の中かどうかも
見ていません。そのため、一覧の項目や数式の中の文字列に「and」が入っていると、
条件が途中で切れます。

例:`of:cell-content-is-in-list("Grand";"Hand";"Stand")` の一覧は、xlsx で
`formula1` が `""G"` になります。`is-true-formula([.A1]<>"Brand")` のような数式も
同じように切れます。

[source,text]
----
Title: ODF→XLSX: content validation conditions are split at every "and", breaking lists and formulas

OdfFile/Reader/Converter/xlsx_data_validation.cpp, add_formula():

    boost::algorithm::split_regex(arrFormula, formula, boost::wregex(L"and"));

This splits at the letters "and" anywhere, including inside quoted list
items and string literals. A list rule
  of:cell-content-is-in-list("Grand";"Hand";"Stand")
converts to <formula1>""G"</formula1>. A formula rule such as
is-true-formula([.A1]<>"Brand") is cut the same way.

Suggested fix: split only at " and " outside quotes and brackets, or
better, match the leading type function (cell-content-is-whole-number()
etc.) and take the rest after " and " once.

Reproduced with the x2t of ONLYOFFICE Desktop Editors 9.4.0. The same code
is in Euro-Office core at 4d2c0365.
----

== 6. シートの終わりの空のセルの行を、入力規則と行の高さを見ないで1つにまとめる

確かめ方:: コードを読んだ。動かした(2026-10-05)
場所:: `OdfFile/Reader/Format/table_xlsx.cpp` の `table_rows::xlsx_convert`
  (282〜294 行目)と、`OdfFile/Reader/Format/table.cpp` の `table_table_cell::empty`

シートの最後の行から上へ、空の行を前の行の繰り返しに足してまとめています。
ここに問題が2つあります。

* 空かどうかを決める `table_table_cell::empty` は、`table:content-validation-name` を
  見ません。そのため、入力規則だけがあるセルの行もまとめられます。まとめた後は
  上の行の規則が下の行にも付き、下の行の規則は消えます。A1・A2・A3 に別々の
  規則がある ods は、xlsx で A1 の規則が A1:A3 に付き、残りの2つが消えました。
  同じ行に値があれば、3つとも残ります。
* 行のスタイルを比べる所で、`style` と `style_1` の両方を `row_last` から取って
  います。2つ目は `row_last_1` のはずです。そのため、高さが違う行もまとめられます。
  高さ 0.5cm の値のある行の下に、高さ 2cm と 4cm の空の行がある ods は、xlsx で
  4cm の行の高さを失いました。LibreOffice は3つの高さを残します。

[source,text]
----
Title: ODF→XLSX: trailing empty rows are merged even when they carry validations or different heights

OdfFile/Reader/Format/table_xlsx.cpp, table_rows::xlsx_convert(), folds
empty rows at the end of a table into the row before them. Two problems:

1. table_table_cell::empty() (table.cpp) ignores
   table:content-validation-name, so rows whose cells only carry a
   validation are folded too. The rule of the first row then covers all
   the folded rows and the other rules are lost. An ods with three
   different rules on empty cells A1, A2 and A3 converts to one rule on
   A1:A3. With a value in each of those rows, all three rules survive.

2. Both styles are taken from the last row:

       std::wstring style   = row_last->attlist_.table_style_name_.get_value_or(L"");
       std::wstring style_1 = row_last->attlist_.table_style_name_.get_value_or(L"");

   The second should read row_last_1. Rows with different row styles
   (heights) are folded. An ods with a 0.5cm row holding a value followed
   by empty rows of 2cm and 4cm converts to an xlsx where the 4cm row
   has lost its height. LibreOffice keeps all three heights.

Suggested fix: use row_last_1 for style_1, and treat a cell with
table:content-validation-name as not empty in this check.

Reproduced with the x2t of ONLYOFFICE Desktop Editors 9.4.0 on small
hand-written ods files. The same code is in Euro-Office core at 4d2c0365.
----
