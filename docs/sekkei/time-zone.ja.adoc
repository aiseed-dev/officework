= 日付・時刻とタイムゾーン
:toc:

== 方針(2026-09-24 発注者)

officework は、時刻を正しく扱える Office を特徴にします。
旅行の日程表のように、場所ごとの時刻が混ざる表を作れるようにします。

* 日付と時刻は、中では UNIX 時間(UTC)で持ちます。
* 表示には、既定のタイムゾーンを使います。
* xlsx の読み書きのたびに、タイムゾーンで換算します。
* タイムゾーンの計算には、Polars と同じ `chrono` と `chrono-tz` を使います。
  同じデータベースを使うので、エンジンと Polars で換算の結果が同じになります。
* 夏時間で時刻が存在しない時間帯や、2 回ある時間帯の扱いは、Polars の
  `replace_time_zone` の選び方(`ambiguous`、`non_existent`)に合わせます。

== OOXML に書いてあること(ECMA-376 第 5 版、2016 年)

規約の本文と schema で確かめた内容です。

=== セルの型 `d` は Strict にしかない

* Part 1 の 18.18.11 `ST_CellType` には `d`(Date)があります。
  説明は「ISO 8601 の形式の日付を持つセル」です。
* Strict の schema(`sml.xsd`)の `ST_CellType` には `d` があります。
* Transitional の schema の `ST_CellType` には `d` がありません
  (b, n, e, s, str, inlineStr の 6 つ)。
* Excel がふだん書くのは Transitional です。このため、Excel と
  やり取りする xlsx では、日時はシリアル値(`t="n"`)で書くことになります。

=== シリアル値はその場所の時刻

* Part 1 の 18.17.4.1 に「基準の日付とシリアル値は、その場所の日付と
  時刻を表す」(The base dates and the related serial date-times represent
  local date and time)と書いてあります。
* Part 4 の 15.3.4 は、Transitional のときの 18.17.4.1 の置き換えです。
  ここにも同じ文があります。
* つまり、xlsx のシリアル値はタイムゾーンを持ちません。どこの時刻かは、
  ファイルからは分かりません。

=== ISO 8601 の文字の日時

* Part 1 の 18.17.4 は、セルの日時を ISO 8601 の文字で持つと書いています
  (Strict の `d` のことです)。
* 日付と時刻の両方を持つ値は、ISO 8601 の B.1.3 と B.2.3 の書き方です。
  例はどれも時差を付けていません(`1976-11-22T08:30` など)。例の説明には
  「その場所の時刻 08:30」とあります。
* B.1.3 に時差の付いた書き方が含まれるかどうかは、ISO 8601 の本文が
  手元に無いので、まだ確かめていません。

=== 付属書 L は本文と食い違っている

* Part 1 の付属書 L(参考。規定ではありません)の L.2.16.9 は、
  「日時は日付、時刻、タイムゾーンの 3 つから成る ISO 8601 の文字で持つ」
  「シリアル値は UTC の日時を表す」と書いています。
* 本文(18.17.4.1)は「その場所の時刻」です。付属書 L とは逆です。
  規定なのは本文なので、本文に従います。

=== 1900 年起点の数え方も、Strict と Transitional で違う

* Strict(Part 1 の 18.17.4.1):1900 年起点の基準は 1899-12-30 で、
  シリアル値 0 です。1 は 1899-12-31 になります。
* Transitional(Part 4 の 15.3.4):1900 年起点の基準は 1899-12-31 で、
  シリアル値 0 です。1 は 1900-01-01 になります。これは Excel と同じ
  数え方で、シリアル値 60 が実在しない 1900-02-29 に当たります。
  ただし同じ節の例は「基準は 1899 年 12 月 30 日」と書いていて、
  節の中でも食い違っています。
* 前の版にあった `dateCompatibility` 属性は、第 5 版の schema には
  ありません。

== 今回作った物(2026-09-24)

* ブックがタイムゾーンを持ちます(`Book::time_zone`。IANA の名前。
  空はこのパソコンの設定)。
* `NOW()` と `TODAY()` は、ブックのタイムゾーンの時刻を返します。
  前は日本の時差(+9 時間)に決め打ちでした。
* xlsx を開くときのオプション(`sheet::xlsx::ReadOptions`)に
  `time_zone` を足しました。表計算の画面では、ファイルの
  「詳細設定」で次の 3 つを選べます。値は settings.toml に残り、
  次に xlsx を開くときから使います。
** xlsx を作った Excel(`xlsx_platform`。Windows か Mac)
** 日付の起点(`xlsx_dates`。ファイルのとおり、1900、1904)
** タイムゾーン(`time_zone`。IANA の名前。空欄はこのパソコンの設定)
* Python では `Book.open(path, platform=..., time_zone=...)` と
  `Book.time_zone` で指定します。

== カスタム関数で持つ(2026-09-24 発注者)

Excel では、VBA でカスタム関数を作れます。officework ではファイルに
コードを入れないので、カスタム関数は Rust と Python で作ります。
セルごとのタイムゾーンは、このカスタム関数で持ちます。

* Rust のカスタム関数は `book::calc::custom` に登録します。officework に
  付いてくる物は `BUILT_IN` の一覧にあり、動いている間に `register` で
  足すこともできます。組み込みの関数と同じ名前の物は使われません。
* Python のカスタム関数は、今までどおり `~/.config/officework/funcs/*.py`
  の `def` です。
* どちらも、セルには式の文字として残ります。このため、xlsx にも adoc にも
  そのまま保存でき、開いたときに計算し直すとタイムゾーンも戻ります。

=== ZONED と TO_ZONE

[source]
----
=ZONED("2026-10-01 10:00", "Asia/Tokyo")          出発(東京の時刻)
=ZONED("2026-10-01 04:30", "America/Los_Angeles") 到着(ロサンゼルスの時刻)
=B2-B1                                           0.4375(10 時間 30 分)
=TO_ZONE(B2, "Asia/Tokyo")                       到着を東京の時刻で
----

* 値は `Value::Zoned` です。UTC の時点(UNIX 秒)、ブックの日付の方式での
  シリアル値(UTC)、タイムゾーンの名前を持ちます。
* 足し算や引き算は UTC のシリアル値で計算します。
* 表示は、そのタイムゾーンの時計の時刻です。表示形式が標準のときは
  `2026-10-01 04:30 America/Los_Angeles` のように名前も出します。
  表示形式を指定したときは、時計の時刻にその表示形式を当てます。
* `YEAR`・`MONTH`・`DAY`・`WEEKDAY`・`HOUR`・`MINUTE`・`SECOND`・`TEXT`
  などは、そのタイムゾーンの時計の時刻で答えます。
* 夏時間で時計が進むときに存在しない時刻は `#VALUE!` です。時計が戻る
  ときに 2 回ある時刻は、先の方を取ります。Polars の
  `replace_time_zone(ambiguous="earliest", non_existent="null")` と同じです。
* xlsx のセルの値(`<v>`)には、そのタイムゾーンの時計の時刻を書きます。
  18.17.4.1 のとおり「その場所の時刻」です。Excel で開いた人にも、
  再計算するまでは正しい時刻が見えます。Excel が再計算すると、
  `ZONED` を知らないので `#NAME?` になります。
* Python の関数との受け渡しでは、タイムゾーン付きの `datetime`
  (`zoneinfo.ZoneInfo`)になります。Python の関数がタイムゾーン付きの
  `datetime` を返すと、セルにはタイムゾーン付きの日時が入ります。
  `officework.sheet` でセルを読んだときも、`officework.calc` で動いている
  アプリから読んだときも同じです(API の JSON では `\x1d<UNIX 秒>[<名前>]`
  の印付きの文字で渡します)。
* 「関数の挿入」の一覧と説明には、ZONED と TO_ZONE を「日付/時刻」の分類で
  載せました。説明は calc/gen_funcs.py の HAND_JA と calc/funcs_hand.json
  にあり、15 言語あります。

=== Polars の列(2026-09-24 発注者)

Polars の `Datetime` の列は、タイムゾーンを 1 つしか持てません。

* 列の日時が全部同じタイムゾーンなら、そのタイムゾーンの列にします。
* タイムゾーンが混ざった列は、UTC の列にします。時点は正しく残り、
  どの場所の時刻だったかは落ちます。
* 表の SQL(`table_query`)では、Rust の Polars がこの決め方で列を作ります
  (`pivot::to_frame`)。答えの日時は、セルと同じ書き方の文字で返します。
* `officework.calc` で DataFrame にするときも、同じ決め方にします
  (`_moment_series`)。
