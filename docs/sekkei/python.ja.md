### calc に残すもの(Python に出さない)

- 帳票の形: 罫線・結合・書式・列幅・行高・印刷 — 様式は見ながら作るもの。
  印刷の設定(2026-08-03): pageSetup / pageMargins / Print_Area は
  **モデルに読む**(向き・用紙・四辺の余白・印刷範囲)。UI とPDF が使い、
  保存は**原文への属性差し替え**(拡大縮小・印刷機の参照など理解しない属性を
  消さないため。丸ごと作り直すと「書式は据え置き」が破れる)。
  用紙コードの B は JIS(ECMA-376 の表は ISO だが日本の実情は JIS —
  ここは日本の事務様式のためのソフト)
- 式の再計算: 開いた見積書が正しく計算されるのはアプリの責務
- 並べ替え・フィルター: 見ながらやる操作
- データの入力規則・条件付き書式: 入力の現場で効くもの(**済** 2026-08-03。
  条件付き書式は cellIs、入力規則は list を読み・効かせ・往復。
  入力規則の候補は formula1 の**原文**で持つ — 範囲参照 `$D$2:$D$5` の中身が
  変われば候補も追従する。規則に合わない入力はセルに入れず、Esc で戻す。
  候補が解決できない規則(別のシートへの参照等)では**堰き止めない** —
  読めない規則で利用者を閉じ込めるより、通して警告しない方を取る。
  list 以外の型は Report へ(保存で失われる、と言う))

### 端末のソフトの土台として(2026-08-04 発注者)

「これで端末のソフトはいくらでも作れる」— 二つの意味で正しく、二つ目が本命。

**1. 新しいバイナリの土台として。** 難所は一度だけ解けばいい。IME・日本語
フォント・GPU 描画(GPUI)・印刷/PDF・リボン・ダイアログの別スレッド化・undo の
規律・排他ロック・Python 拡張(サンドボックスつき)・仮想画面での自動検証 — 全部が
共有クレート(kumihan / sheet / paper / ui)と作法(SEKKEI・方針・
wiring_tests)に貯まっている。3本目のソフトはこの上に薄く載るだけ。

**2. 多くの業務ソフトは、もう「作らなくていい」。** Python in Calc +
サンドボックス + ファイルサーバーで、**xlsx 1つが業務アプリそのもの**になった。
帳票(UI)+ コード(ロジック)+ 運用(状態列と入力規則)が1ファイル —
問い合わせ・顧客・在庫・勤怠・日報・検収、事務の台帳系はほぼ全部この形に
収まる。共有フォルダがそのまま配布網で、導入も更新もファイルコピー。
**「いくらでも」の実体は、N 本のバイナリではなく N 個のブック。**

**改訂(2026-08-04 発注者確定): 新しいバイナリは作らない。** writer と calc の
2本で打ち止め。以後の「新しいソフト」はすべてブック(帳票+コード+運用)で
作る。UI が足りなければ、バイナリを増やすのではなく **calc / writer 側を
伸ばす**(伸ばした部品は全ブックの共有財産になる — 図形・グラフ・UDF が
そうだったように)。バイナリを増やしたくなったら、それは**範囲の外の合図**
(このソフトの仕事ではない)。バイナリが2本で固定なら、検査・配布・保守の
対象も2本で固定 — 「いくらでも作れる」と「保守が貯まらない」が両立する。

**↑の狭め方を改めた(2026-08-12 発注者)。** 固定するのは**バイナリの本数**
ではなく**エンジンの本数**だった。pyoffice(2026-08-09)と builder
(2026-08-11 確定)でアプリが2つ増えたが、どちらも**同じエンジンに載る
薄いアプリ**で、増えて困る物(エンジン)は増えていない。正は SEKKEI.md
「アプリは増える。エンジンは1つ」。この節の実務 —「UI が足りなければ
calc / writer 側を伸ばす」「新しい業務ソフトはブックで作る」— は
そのまま生きている。

限界も書いておく: 保守は貯まる(GPUI の上流追従、この規模を発注者+Fable で
回し続ける前提)。サンドボックスは OS ごとに組む — Linux は bubblewrap(済)、Mac は
Seatbelt(「Mac 版」の節。当初は「Linux 専用」と割り切っていたが
2026-08-04 に改めた)。サンドボックスが組めない環境ではブック搭載コードを実行しない、
という規律が両方を守る。様式と業務知識は結局それぞれの現場の仕事。

### ファイルサーバーの現実に合わせる(2026-08-04 発注者)

多くの現場はクラウドに移れない(閉域網・規程・データ主権)。基幹は
**共有フォルダの xlsx** であり続ける。この設計はその現実のためにある:

- 帳票・コード・運用が**1つの xlsx** で共有フォルダに置ける(Python in Calc)。
  サーバーは物置のままでよく、Web アプリも DB も SaaS 契約も要らない
- 共有フォルダ = 他人のファイルが日常、という脅威にはニ重の防壁
  (自動実行なし+サンドボックス)が正面から答える。VBA が背負っていた危険の置き換え
- **排他**(済): 開くとき `.~lock.名前#`(LibreOffice と同じ場所)を見て、
  先客が居れば名乗りを見せ、**上書き保存を止める**(名前を付けて保存へ)。
  居なければ自分のロックを置き、閉じる・別のファイルへ移るときに外す。
  「二人で開いて後勝ちで潰す」という共有フォルダの定番事故を防ぐ。
  版の履歴・バックアップはファイルサーバー側の仕事(スナップショット)
- writer も同じ排他が要る(未実装 — 相方の課題として HIKITSUGI へ)

### Python in Calc(済 2026-08-04 発注者提案。同日、コードの持ち運びまで拡張)

データ > Python。一行のコードか .py ファイルを、**b(ブック)と s(いまの
シート)を束縛して**回す。裏はいまの表を一時 xlsx へ写し(原本の部品ごと)、
officework.sheet(pysheet)で実行し、保存されたものを読み戻して**1手として**
適用する(undo は束 — 複数シートに触っても Ctrl+Z 一回で戻る)。
失敗しても表は無傷(実行は複製の上)。

**コードはブックに載せて持ち運べる**(発注者判断 2026-08-04)。
`@save 名前` で .py をブックに載せ(xl/joPython.xml。この形式の独自部品)、
`@名前` で実行、`@list` `@del 名前`。帳票とコードが一緒に旅をする —
マクロの利便はこれで得る。そのうえで**二重の防壁**が旧原則の核を守る:

1. **開いても決して自動実行しない。** 実行は常に明示の操作(@名前)だけ。
   「開く=実行」という攻撃経路は今までどおり存在しない
2. **ブックに載っていたコードは必ずサンドボックス(bubblewrap)の中で回す** —
   他人のファイル由来かもしれないから。サンドボックス: ネットワーク遮断・実ファイルは
   読み取り専用・ホームは不可視(tmpfs)・書けるのは交換用の一時領域だけ。
   サンドボックスの無い機械では載ったコードは**実行しない**(そう言う)。
   自分で打った/選んだコードも、サンドボックスがあればサンドボックスで回す(深層防御)

**↑を狭めた: ブックが運べるのは関数(UDF)だけ**(発注者確定 2026-08-08)。
同梱 Python を見据えて見直し — 手続きがブックで旅をすると**ファイルが実行の
起点**になる(二重の防壁があっても、ブックの文言で「@名前 net と打って」と
説得する道が残る = 帳面の中身を外へ送る経路)。UDF は net の道が無く返せるのは
セルの値だけなので、載せてよいのは UDF だと切った:

- **joPython に書くのは「関数」で始まるスクリプトだけ**。@save も関数だけ受ける
- **手続きは全部外部** — ~/.config/office/plugins の .py を `@名前` で実行
  (サンドボックス必須・網なし既定・`@名前 net` でその場だけ網あり。従来の @名前 の作法のまま
  実行元が plugins に変わった)。ファイルを受け取っても手続きは付いて来ない
- 古いブックの手続きは読むが**実行できず、保存で消える**(開くときの報告で
  そう言う — 黙って落とさない)。`@export 名前` で .py に取り出し、中身を
  確かめて自分で plugins へ置く — それが取り込みの門
- 問い合わせ台帳のような運用は「1機械1回、plugins に据え付け」に変わる。
  ブックは帳票と関数だけを運ぶ
- 併せて実行に**時間制限**(手続き60秒・UDF 30秒)。サンドボックスの中の無限ループでも
  殺せるように、出力は別スレッドで吸い出しつつ try_wait で見張る(py.rs の
  run_with_timeout)

**↑をさらに狭めて、ブックからコードを全部外した(発注者確定 2026-08-09)。**
発注者の言い方で言うと、このソフトは **「VS Code と Excel(VBA を除いた)を
合体させたもの」= native python excel**。VBA を除くとは「文書の中にコードを
埋める仕組みを持たない」ということで、コードは VS Code と同じく
**ファイルシステムの上の .py** にある。

- **交換されるファイルはデータだけ。** データを受け取って、**処理は自分の
  コードでする** — だから関数(UDF)も手続きも `~/.config/office/plugins/*.py`
  にあり、ブックには1バイトも入らない
- `xl/joPython.xml` は**廃止**(読むだけ・書かない)。古いブックのコードは
  実行できず保存で消える。開くときに報告し、`@export` で .py に取り出せる
- **セルの式は普通の関数呼び出し**: `=倍(A1)`。plugins に `def 倍(x)` が
  あればそれが呼ばれる(名前は日本語でよい)。`=PY("倍", A1)` も残す。
  そのために**字句解析で名前の頭を ASCII に限るのをやめた** — 副産物として
  和文の未知の名前が `#ERROR!` から `#NAME?` に揃った(在庫だった印の不揃い)
- **デコレータは作らない**(`@xw.func` / `@xw.ret(expand='table')` は不要)。
  あれは xlwings が Excel という他人の家に関数を登録するための仕組みで、
  こちらには境目が無い。広がり方は**返り値の形**が決める
  (2次元→表にスピル、1次元→縦)
- **引数が変われば裏で自動計算**(`@計算` は手回しとして残す)。式の評価の中で
  Python を同期で回すと画面が止まるので、`Sheet::py_stamp`(引数の指紋)が
  動いたのを 200ms ごとの見張りが見て、別スレッドでまとめて回し、答えが
  揃ってから**1手として**書き戻す。自動の分は undo の節目を作らない
- **サンドボックスは着せない**(bubblewrap を外した)。あれは「ブックから
  旅して来たコード」のための鎧で、コードが自分のものだけになった以上、
  VS Code でスクリプトを走らせるのと同じ扱いでよい。`@名前 net` の区別も
  消えた(打つと「要らなくなりました」と言う)。**外部データの取り込みには
  実ファイルが読める必要がある**ので、鎧は用途とも噛み合っていなかった
- **手続きは動いている calc をそのまま操る**(一時ファイルの複製をやめた)。
  記事の見出し「ファイルではなくて Excel そのものを操作するライブラリー」が
  そのまま設計になる: 子のプロセスが officework のソケット越しに書く。
  `Book.caller()` は `Book.attach()` と同じもの。1手続き=1undo は
  `Calc::rpc_batch`(手続きの頭で節目を1つ置き、その間 rpc は置かない)
- 残る安全は**置く前に読む**の一点。ファイルを受け取っても手続きは付いて
  来ないので、「開いた瞬間に他人のコードが走る」は原理的に起きない

**↑の「外した」の正確な姿(2026-08-12、コードと突き合わせた)。**
「着せない」は言い切り過ぎだった — 消したのは「**組めなければ実行しない**」
という必須の条件で、仕掛け(`Cage` — bwrap / flatpak-spawn)は
calc/src/py.rs に生きている。**Python の道は2本**あり、囲いの扱いが違う:

| 道 | 何が走る | 囲い |
|---|---|---|
| **RPC**(動いている calc をソケット越しに直に操る) | plugins の手続き(`@名前`)・UDF(`=倍(A1)`) | 無し(素の Python)。門は**置く前に読む** |
| **複製の上で回して読み戻す** | データ > Python の一行・writer のマクロ | **あれば囲う**(深層防御 — py.rs の注記のまま)。無くても走る。失敗しても表は無傷 |

用途が違うので**2本とも残す**。マクロは失敗しても表が無傷、RPC は Jupyter
から見ながら触れる。python-manual はこの区別を既に正しく書いている
(「データ > Python の一行と writer 側は、いまも複製の上で走る
(サンドボックスがあれば使う)」)— 設計のこの節だけが粗かった。

**次に来る大物**: plugins の .py を calc の中で編集する画面(VS Code 側の
半分)。いまパネルに `@名前` と打つのはその代用品。

Python in Excel との違い: あちらはクラウド実行(データが Azure へ出る・
従量課金)。こちらは**手元で動き、基幹網の外に出ない**。polars・scipy・
matplotlib など機械にある物が全部使える。Excel は未知の部品を保存で
落とすことがあるので、Excel で開いて保存し直すと載せたコードは消え得る
(コードは消えても値は残る — 劣化は安全側)。

**UDF とスピル**(済 2026-08-04。発注者の 2018 年の Qiita 記事
「Excel に Python が搭載?その後 — xlwings を使おう」が前史。xlwings の
目玉だった「Python で書くセル関数」を、8年後に自分の calc へ本搭載。
**注意: この節は 2026-08-04 の姿** — `@save` と「開いても再計算でも実行
されない」は上の 2026-08-09 の節で改まった。いまは def が plugins に住み、
セルは `=関数名(…)`、引数が変われば裏で計算し直す):
- セルに `=PY("関数名", 引数…)`。関数の定義はブックの**「関数」で始まる
  名前のスクリプト**(@save 関数)にある def
- **PY セルは開いても再計算でも実行されない。** 最後に計算した値を保ち、
  未計算なら #PY? の印。評価はパネルの `@計算` のときだけ、**網なしサンドボックス**の中で
  一括 — 「開く=実行を持たない」はセル関数でも破らない
- 2次元の返り値は右下へ**スピル**。展開先に他人のデータや式があれば
  #SPILL! で止まる(潰さない)。縮んだときは前回の面の残骸を消す
- 引数は式をいま評価した値で渡す(範囲は列数つきの2次元)。式は保たれる
  ので、@計算 を押し直せば新しい引数で再評価される
- Excel で開くと PY は #NAME? になる(値は保存されているので、Excel が
  再計算するまでは見える)。劣化は正直に

**サンドボックスは段階制**(2026-08-04。Web の問い合わせ取り込みのため):
- 自分で打った/選んだコード: **網ありサンドボックス**(ファイルは守られたまま、網は通る —
  自分の道具が Web から取り込むのは普通の仕事)
- ブックに載って旅してきたコード(@名前): **網なしサンドボックス**が既定
- `@名前 net` と**その場で打ったときだけ**網ありサンドボックス — 許可は毎回の明示の
  操作で、**ブックには決して保存されない**(ファイルが自分に権限を
  与えることはできない)

**使い所の実例 — Web の問い合わせ台帳**(実証済み): フォームの受信箱
(API / CSV)を取り込むコードをブックに載せ、`@取り込み net` で台帳に
「受信・名前・用件・状態=未対応」を追記する。帳票・コード・運用が
1つの xlsx で旅をする。網なしサンドボックスでは同じコードの通信が拒否されることも実証。

配り方: `pip install officework`、または `officework/` パッケージを
**calc の隣に**置く(calc は自分の居場所を `sys.path` に足して
`from officework import sheet` する)。無ければ status がその手順を言う。
**裸の `.so` を置く形は 2026-08-09 に終わった** — docx / pptx が来ても
同じ名前空間に入るよう、エンジンを `officework.sheet` へ移したため。

### 分業の橋 — `pysheet`(済 2026-08-03)

`sheet` を Python から呼べるようにした(pyo3, crate は `pysheet`、
配る名は `officework`、エンジンは `officework.sheet`)。openpyxl と違い、罫線・結合・列幅・図形を
保ったまま値を差し込める — **polars で集計 → 帳票の枠を保ったまま差し込む**。
マクロの置き換えがスクリプトになる、という当初の設計と一直線。

```python
from officework import sheet
b = sheet.Book.open("様式7.xlsx")
s = b["提案見積書"]              # b[0] でも
s["A30"] = "日本フネン株式会社"   # 書式は据え置き。文字列は「打ったのと同じ」解釈
s["C30"] = "=B30*100"            # 式。置いた時点で再計算される
s.insert_row(30)                 # 明細行を増やす。残った式の参照も動く
b.save("out.xlsx")               # 原本から図形・印刷設定を持ち越す
```

- 値は Python の型のまま(数=float, 文字=str, bool, 空=None)。
  `s.values()` は行ごとの list[list] — `polars.DataFrame(…, orient="row")` でそのまま表になる
- `b.unsupported` に読めなかったものの帳簿が出る。**黙って落とさない**はここでも
- 配る .so は `cargo build -p pysheet --release --features extension-module`
  (abi3-py310: libpython 非依存で、どの Python 3.10+ でも同じ .so が動く)。
  extension-module を既定にしないのは cargo test がリンクできなくなるため(pyo3 の FAQ)
- 検査は `pysheet/test.py` を Rust の試験(`tests/python_smoke.rs`)が回す。
  実物の様式7で「差し込んでも結合が崩れない」ことまで見る
- polars 連携は実地で確認済み(2026-08-03): miniforge の `.venv`(Python 3.14 +
  polars 1.43)で、**3.12 で組んだ abi3 の .so がそのまま動く** — group_by の集計を
  実物の様式7に差し込み、保存しても結合・元の中身は無傷。test.py の polars の節は
  polars がある環境でだけ回る(無ければ飛ばしたと言う)

### writer(docx)には橋を作らない(2026-08-03 確定)

**全部 Rust で書く必要はない**(ユーザー判断)。xlsx に pysheet が要ったのは
openpyxl が帳票の枠(罫線・結合・列幅)を壊すからで、docx は事情が違う —
**python-docx は XML の木をその場で書き換える**作りなので、
理解しない部品(画像・スタイル・ヘッダー・フッター)を最初から壊さない。
公共財が既にあるところには作らない(hunspell と同じ論理)。

実物の様式1(参加表明)で確認済み:
- python-docx 1.2.0 で記入して保存 → 本当に変わったのは word/document.xml
  (編集した本文)だけ。styles・footer・settings は再直列化で字面が変わるが
  **中身は同一**(C14N で比較)。[Content_Types].xml も宣言の集合は同一
- **相互運用**: python-docx で埋めた様式を、こちらの ooxml(writer)が
  そのまま読める(unsupported 空)
- 記入の作法: **先頭ランに書き、残りのランを空にする**(段落の書式・書体が残る)

```python
import docx
d = docx.Document("様式1.docx")
p = d.paragraphs[12]
p.runs[0].text = "商号または名称　日本フネン株式会社"
for r in p.runs[1:]: r.text = ""
d.save("記入済.docx")
```

## officework — 事務の道具一式の Python 連携(2026-08-08 発注者。旧名 jocalc → jooffice)

発注者の Qiita 記事(xlwings で Jupyter から Excel を操る)の車線を calc に。
「xlwings から calc」は xlwings 本体が Excel(COM/AppleScript)に固定なので、
**同じ使い勝手の互換パッケージ officework** を用意した —
`from officework import calc as xw` の1行差し替えで、記事の Book / Range /
.value / options(pd.DataFrame, expand='table') / save がそのまま動く。
**calc 専用にしない**(発注者 2026-08-08)— 共有部(ソケット+JSON)は
officework/__init__.py にあり、アプリごとのソケットは officework/<app>.sock。
writer 側の API(文書・記入欄・差し込み)は今後 officework.writer として増やす。

- **ソケット**: calc が起動時にユニックスソケットを開く(calc/src/rpc.rs)。
  径路は `$XDG_RUNTIME_DIR/jo-office/calc.sock`、AF_UNIX の 108 字上限を
  超えるときは `/tmp/jo-office-UID/`(Python 側と同じ規則)。**この機械の
  中だけ** — TCP は開かない(ネイティブファースト)
- **スレッドの作法**: ソケットのスレッドは状態に触らない。要求を溜め、GPUI の泵が
  30ms ごとにメインスレッドで捌く(答えは要求ごとの mpsc で返す。5秒で諦める)
- **語彙**(JSON 1行ずつ): ping / book_info / new / open / save / get /
  get_formula / set / expand。set は 1回=1手(Ctrl+Z)・書式は据え置き・
  保護中は断る。new/open は未保存の変更があれば断る(黙って捨てない)
- **JSON は自前の浅い読み書き**(rpc.rs 内)— 依存を増やさない(crypt と
  同じ流儀)。語彙が浅いので足りる
- **Python 側**: pysheet/officework/(純 Python、依存なし。pandas は使う時だけ)。
  .venv には officework.pth で結線(コピーしない — 常に最新)
- **未対応と正直に言う物**: @xw.func / @xw.sub / Book.caller()(Excel の
  アドイン機構)— calc では AI タブのマクロ(plugins/*.py)が同じ役目

## `officework.doc` — docx の束縛(2026-08-10 発注者「writer も読み書き両方」)

`officework.sheet` と**同じ作り**で docx を出す。発注者 2026-08-10:
「xlsx エンジンだけでなくて docx エンジンも必要でしょう」「writer も読み書き
両方です。calc と同じやり方ができるようになるでしょう」。

材料は揃っている — `ooxml`(4,744行・試験79件)が `read` / `write` /
`write_with`(原本据え置き)を持ち、模型は `kumihan::Document`
(段落・表・ヘッダー・フッター・用紙・変更履歴・しおり・透かし)。

### 売り文句は sheet と同じ論法

`python-docx` は理解できない部品の扱いが弱い。`write_with` は**原本を正として
変えた所だけ書き戻す**ので、様式・ヘッダー・図形・変更履歴が壊れない。
読めなかった物は `unsupported` に出る(黙って落とさない)。

**これは xlsx で証明済みの主張である。** 他人の xlsx 30枚で「中身の食い違い
ゼロ」まで持っていったのと同じことを、docx でもやる。

### 作法(sheet から引き継ぐ)

1. **名前は `officework.doc`。** `_sheet` と同じく `officework._doc` を
   pyo3 で作り、`officework/__init__.py` から見せる。1つの wheel に同居させる
   (利用者に2つ入れさせない)
2. **原本を持ち歩く。** `Doc.open` で読んだ元のバイトを抱え、`save` は
   `write_with` に渡す。**これをしないと売り文句が成り立たない**
3. **`unsupported` を最初の見本に出す。** README の例に必ず入れる
   (2026-08-10 の 0.1.2 で、見本が動かないまま配っていたのを踏んだ)
4. **読めない物は読めないと言う。** 黙って空を返さない

### 何を出すか — **模型をそのまま見せない**

`kumihan::Document` は組版の模型で、Python から触るには細かすぎる
(`Run` の `size_pt`・`CharFormat`・`anchors`)。`sheet` が
`Book` / `Sheet` の2階建てで済ませたのと同じく、**docx も薄い層をかぶせる**。

    d = doc.Doc.open("報告書.docx")
    d.paragraphs            # 段落の一覧
    d[3].text               # 段落の字(run をつないだもの)
    d[3].text = "差し替え"   # 書式は据え置き(run の書式を保って字だけ替える)
    d.tables[0][1][2]       # 表・行・セル
    d.find("旧社名")         # 置換の下ごしらえ
    d.unsupported
    d.save("out.docx")

**`text` の代入が肝。** 帳票の差し込みは「書式を保ったまま字を替える」で、
これは `sheet` の `s["A30"] = …` と同じ仕草。run が複数に割れている段落で
書式をどう保つかは実装の判断が要る(先頭 run の書式を継ぐのが素直)。

### 範囲 — 読み書き両方を一度に出す

発注者確定。`sheet` のときも読み書き両方で出した。`ooxml` は `writer` で
使い込まれているので、同じ条件が揃っている。

**ただし出す前に実物で測る。** xlsx で学んだとおり、**自分で書いた docx だけで
往復を確かめると、環境依存と実物特有の形を必ず見落とす**(2026-08-09 に
`sheetView` を Empty の枝でしか読んでいなかったのを踏んだ)。
比較の相手は **genoffice の `packages/docx-engine`(TypeScript 20,762行)**。
xlsx で `pyoffice_diff.py` がやったことを docx でやる。

### genoffice への載せ替えは**別の話**(2026-08-10 当方)

docx には**継ぎ目が無い**。向こうの docx エンジンは TypeScript で同一プロセス、
xlsx のようなサイドカーも `XLSX_SIDECAR_PATH` に当たる環境変数も無い。
載せ替えるには**継ぎ目そのものを作る**ことになり、上流にパッチが要る
(「genoffice には何もしない」の方針から外れる)。

**判断は先送りする。** `officework.doc` を出して実物で穴を測れば、
「載せ替える価値があるか」が数で出る。それを見てから決める。
pptx は officework に1行も無いので、そもそも移植ではなく新規開発 — 当面やらない。


### 作った(2026-08-10)— 面と、実物で測った結果

**出した面。** `kumihan::Document` は見せず、文書 / 段落 / 表・行・セルの
4階建てだけを出した(`pysheet/src/doc.rs`)。

    d = doc.Doc.open("報告書.docx")
    d.unsupported            # 読めなかった物の帳簿(最初に見せる)
    d.paragraphs / d[3] / len(d) / d.text
    d[3].text = "差し替え"    # 段落の性質は据え置き
    d[3].runs                # 書式のまとまり(読むだけ。差し込みの結果を確かめる)
    d.find("旧社名") / d.replace("旧社名", "新社名")
    d.tables[0][1][2].text   # 表・行・セル
    d.header / d.footer      # 読むだけ
    d.save("out.docx")       # write_with。原本を正として書き戻す

**`text` の代入は先頭 run の書式を継ぐ。** 判断の決め手は「素直だから」ではなく、
**kumihan の `set_paras_text` が既にその規則で、writer のセル編集とヘッダー編集が
それで動いている**こと。Python から触ったときとアプリで打ったときで結果が変わる方が
害が大きい。`CharFormat` は丸ごと継ぐ — 記入欄(`sdt`)も継ぐので、**帳票の記入欄が
記入欄のまま残る**(差し込みの本題はそこ)。

**ただし `text` の代入は鈍器である。** 「請求先: 」が明朝で「□□□」が太字の段落に
代入すると、全部が明朝になる。書式の分かれ目を残したまま字を替えるのが
`replace()` で、**帳票の差し込みはこちらが本筋**。run を跨いだ語も拾う
(Word は「旧社名」を平気で 旧/社名 に割る)。

**1つの wheel への同居のやり方。** maturin が組める拡張は1つなので、
`officework._doc` を別の .so にはできない。docx の pyo3 は `_sheet` の
**副モジュール**として同じ .so に入れ、`officework/_doc.py`(名前だけを受ける
薄い層)が `officework.doc` として見せる。利用者から見た形は設計どおり。

## 上位互換は API とテストの蒸留で作る — 実装は写さない(2026-08-12 発注者確定)

発注者「officework エンジンを openpyxl・xlwings・python-docx の上位互換に。
3つは公開されているから、Python で蒸留のコードが書けないか」。
書ける — ただし**蒸留するのは API(名前と形)とテスト(挙動)で、実装コードは
写さない**(当方の見立てを発注者了承)。理由は3つ:

1. **エンジンはもうある。** pysheet が3つの口(sheet / doc / calc)で3つの
   ライブラリと同じ役を張っている。openpyxl の実装を Python に写すと
   エンジンが2つになり、「製品は2本・エンジンは1つ」が崩れる
2. **3つの弱点こそ、こちらの売り。** openpyxl は式を再計算できない。
   xlwings は Excel 本体が要る。python-docx は読めない要素を落とすことがある。
   実装を蒸留すると、この弱点ごと写る
3. **ライセンスは全部通るが、写す価値があるのは仕様の側。** openpyxl は MIT、
   xlwings は BSD-3、python-docx は MIT — どれも AGPL と両立。API を揃えるのも
   テストを移植するのも問題ない(移植したら NOTICE.md に出所を書く)

やり方:

- **互換台帳** [docs/pysheet-gokan.ja.md](../pysheet-gokan.ja.md) に3つの
  中核クラスの公開メンバー全量(324)を並べ、1つずつ
  「ある/互換層/足す/要らない/作らない」を判定した。
  在庫台帳なので、消し込みは行頭 ✔(guide-tsukiawase-2 と同じ作法)
- **名前の差は互換層で吸収** — pysheet/officework/*.py に薄い写像を書く。
  エンジン(Rust)に手を入れるのは、機能そのものが無いときだけ
- **挙動の蒸留はテストの移植** — 3つのテストから実務部分を pysheet/tests/ に
  移植して officework に対して回す(適合テスト)。「上位互換」を名乗る根拠
  (**実測で形が変わった 2026-08-13**: 本家のテストは配り物に入っていない —
  openpyxl は sdist にも無い。代わりに python-docx の**受け入れ仕様**
  `features/*.feature` 67本を的に test_shiyou.py を起こし、openpyxl の側は
  **本家を実際に動かして結果を突き合わせる** test_gokan.py がその役
  (試験を写すより強い — 実物の xlsx で照合する)。出所は NOTICE.md)

**開いた問題(発注者判断待ち): 書式の書き込み。** border・font・fill・
number_format・列幅などを Python から**書く** API を作るか。うちの哲学は
「様式はアプリで見ながら作る、Python はデータの差し込み係」だが、openpyxl から
の移行者は書式を書くコードを持っている。読みは害がないので足す。書きは
台帳で「判断待ち」(13件)にして発注者に諮った。

**↑の判断が出た(2026-08-12 発注者確定): 書きも作る。合否の基準は
「定義どおり動作するか」。** 「様式はアプリで」の哲学は**入り方の順番**の話で
あって、API を狭める理由にしない — 上位互換を名乗る以上、相手の定義
(公開ドキュメントとテストが定める挙動)どおりに動くことが合否の線。
定義どおりの証明は適合テスト(相手のテストの移植)で立てる — つまり
書式の書き込みも、テストの蒸留の的に含める。台帳では「足す(書式)」。

**↑に発注者の指摘を2件足した(2026-08-12)。**

1. **「控え(後回し)」という判定は置かない。** 的の中の物は**作るか、
   作らないか**をその場で決める — 「要望が出たら」は決定ではない。
   台帳の控え 84 件を仕分け直し、全量の内訳は
   ある 38・互換層 78・足す 99・足す(書式)24・要らない 57・作らない 28
   になった。作らない 28 件は全部に理由が付いている
2. **xlwings の Range.height / width / left / top を「画面のピクセル」として
   要らないに入れたのは読み違い。** xlwings の定義は画面の状態ではなく
   **レイアウトの座標(ポイント)**で、モデルの列幅・行高から計算で出せる。
   画像・図形の置き場所の計算に使う実務の値なので「足す」に移した

**台帳は 2026-08-13 に全量を閉じた。** 324 件すべてに ✔ が付き、
「足す」「足す(書式)」の実装・両方向の適合検査・実機(calc)での検分まで済み。
道中で塞いだ黙って壊す穴は7つ(shared strings・core.xml の名前空間・様式名・
