## writer の挿入系 — Python で描いて画像として貼る(2026-08-03 確定)

calc の分業と同じ線を writer にも引く(発注者確認済み)。
**文書の中で描く道具は作らない。絵は Python で描き、画像として貼る。**
このソフトは事務様式**専用ではない**(2026-08-03 発注者)— 汎用の
ワープロとして考える。ただし絵を描く場所は文書の外(Python)でよい。

| リボンにあるもの | ボタンの動き |
|---|---|
| 図形・SmartArt・グラフ | 画像を選んで貼る(matplotlib / PIL で描いた PNG を想定) |
| テキストアート(飾り文字)・方程式 | 同上(方程式は matplotlib の mathtext 等) |
| テキストボックス | 1×1 の表を挿す(枠の中に文字が書ける。セル編集は実装済み) |
| ドロップキャップ・コンテンツコントロール | 未実装(灰色のまま。作らないと決めたわけではない) |

- **きちんと動作するボタンは灰色で残さない**(2026-08-03 発注者)。
  挿入系は上の表のとおり「画像として貼る」「表を挿す」で実際に動くので、
  普通のボタンとして配線した。並びは Euro-Office のまま
- 貼る道: 「画像を挿入」が PNG/JPEG を受け、docx の部品
  (media/rels/[Content_Types])ごと書き出す。撮って出しの寸法は 96dpi、
  行長に収まらなければ比例で縮む
- 開いた文書にある図形・テキストボックス・グラフは**原文持ち越しで保存で
  壊れない**(画面には出ない。帳簿に「保存では残る」と出す)
- 実地検証(2026-08-03): PIL で描いた棒グラフの PNG を「画像を挿入」と
  同じ道で貼り、保存 → 開き直しで画像が残り、LibreOffice が PDF に
  画像入りで変換できることを確認(matplotlib はこの機械に無いが、
  PNG を作って渡す流れは同じ)

## writer の編集モデル — run 粒度(2026-08-04)

**1回の編集は、連続した1箇所の置き換え**(打鍵・削除・貼り付け・IME の
確定・undo の1手、すべてそう)。この不変条件が編集モデルの土台。

- `set_body_text` は、編集前後の本文の頭と尻尾の共通部分を除いて
  「その1箇所」を特定し、`splice_text` が run の構造へ正確に写す。
  旧方式(段落番号で段落をまるごと写す)は廃止 —
  **run の境(部分書式)・段落の性質・表の位置が、編集で流されなくなった**
  (旧方式の持病: 段落の増減で下の段落の性質がずれる/打鍵のたびに
  表が末尾へ動く — どちらも解消。テストで固定)
- 書式の適用(`apply_char_format` / `apply_size` / `apply_font`)は
  選択範囲の境で run を割り、**選択の字にだけ**掛かる。選択が空なら
  従来どおり段落まるごと(方向の癖を変えない)。端が字の途中なら
  その字はまるごと含める
- 段落を割る(Enter)と、両方の半分が段落の性質を持つ(Word と同じ)。
  合流(改行の削除)では頭の段落の性質が残る
- 差し込む字の書式は「置き換えの直前の字」のもの(打つとその書式に
  なる、の慣習)。`normalize_runs` が空の run を除き、同じ書式の隣を
  繋ぐので、編集で run が際限なく増えない
- 描画(画面・PDF)は**同じ書式の連なり**ごとに描く。Cell が書体も
  持ったので、行の中で太字・大きさ・書体・色が混ざってもその通りに出る
- **注意**: 一括の複数箇所置き換え(すべて置換)は「1箇所」の前提から
  外れるため、頭と尻尾の間の書式が均されうる。置換のたびに写せば
  避けられる(今後の改善点)
- これで**相互参照(REF フィールド)を本文で持つ土台**ができた —
  フィールドを run として持てば、編集で流されない

## writer の相互参照 — run が持つ参照(2026-08-04)

run 粒度の編集モデルの最初の応用。**run 1つが1つの参照**(REF / PAGEREF)で、
run の text が「いま見えている値」。

- 参照は書式(CharFormat.field)に持つ — run の分割・結合・描画の既存の
  道具立てがそのまま効く(field が違えば normalize で繋がらない、
  描画は連なりの境で切れる)
- **編集の規則**: 参照の中を割ったら普通の字に降りる(半分ずつが参照を
  名乗ると更新で二重になる)。参照の直後に打った字は参照を継がない。
  参照ごと太字にはできる(全体を覆う適用は分割しないので残る)
- 挿入はパネル(しおり一覧 → 文字/ページ)。値は挿した時点で計算し、
  「参照を更新」で計算し直す(更新は run の text を直に書き換えるので
  編集の平文を作り直す = **undo の控えが失われる。そう言う**)。
  保存時は写し(doc_for_save)でも更新するので docx の値は常に新しい
- docx とは fldSimple / fldChar の REF・PAGEREF で往復。見えている値は
  キャッシュとして入るので、Word/LibreOffice はそのまま表示も再計算もできる
  (LibreOffice が実際に再計算することを確認済み)
- 画面では参照にうっすら網掛け(Word の作法 — 「計算された値」と分かる)

## writer の変更履歴 — 差分を保存で刻む(2026-08-03)

編集モデル(平文+段落持ち越し)に操作の記録を足すのではなく、
**保存のときに「記録開始時点との差分」を計算して w:ins / w:del にする**。
編集中は普通に打てて(モデル無変更)、Word には本物の変更履歴として届く。

- レビュー > 変更履歴 = 記録の開始/停止。開始時点の段落の写しを持ち、
  画面では変わった段落の左に橙の棒(Word の変更バー)
- 差分は2段: 段落の列を LCS で突き合わせ(変更/新規/削除の段落を出す)、
  変わった段落の中は共通の頭・尻尾を残して間を del + ins に
- 印は私用領域の字(TRK_INS_S 等)で保存用の写しに埋め、ooxml が
  w:ins / w:del(著者つき)に変換する — PAGE フィールドと同じ作法
- 読みは**確定後の姿**(挿入は本文、削除は見せない)。履歴そのものは
  モデルに持たないので、**保存すると履歴は確定される — 帳簿でそう言う**。
  履歴の中身の閲覧・個別の採否は今後の課題
- 消えた段落は「全部削除の段落」としてその場所に置く(Word では
  取り消し線の段落として見える)

## writer の描画(ペン)— ページに固定した筆(2026-08-03)

- 筆(Stroke)は**ページ番号 + ページの中の mm 座標**で持つ。本文を編集しても
  動かない — Word のページ固定の図形と同じ性質。画面と紙の対応は
  paper::paginate の折り方(ページの繰り上げ量)で取る
- docx では**自由曲線の図形**(DrawingML custGeom、ページ基準の anchor)。
  ページ番号は図形の名前(joink{id}p{page})で持つ — XML の座標は
  ページの中の位置しか持てないため。開くときは原文控えから筆へ読み戻す
  ので、このアプリ同士なら消しゴムも効き続ける。Word/LibreOffice でも
  普通の図形として見える(LibreOffice の描画を画素で確認済み)
- 蛍光ペンは太く・薄く(alpha 45%)・文字の下(behindDoc)。ペンは細く・
  濃く・文字の上。画面の描画は gpui の Path(塗り)で、折れ線を
  「幅のある四角形の連なり」として塗る
- 保存は**写し**に差し込む(doc_for_save)— モデル本体に足すと
  保存のたびに図形が増える。undo は筆の一手ずつ(道具を持っている間の
  Ctrl+Z は筆の取り消し)

## writer の見出しと目次(2026-08-03)

- 段落の役割は `ParaStyle`(Body / Heading 1〜3 / Toc 1〜3)。
  docx の `w:pStyle` と往復する。見出しの style id は日本語版 Word が「1」、
  英語版が「Heading1」— 読みは両方受け、書きは `Heading{n}` + `outlineLvl`
  (スタイル定義の無い文書でも見出しとして扱われるように)
- **スタイル定義(styles.xml)は持たない。** 見出しを付けるとき、見た目
  (太字・大きさ)は直接書式で付ける。開いた文書の styles.xml は今まで通り
  原文で持ち越す
- 目次は**静的な本文**として挿す(TOC フィールドは書かない — 開いた側に
  「フィールドを更新してください」を出させない)。目次の行は
  `ParaStyle::Toc` の印(docx では pStyle TOC1〜3)を持ち、
  「目次」「目次の更新」はどちらも Toc の連続を丸ごと作り直す。
  挿すときは**編集(undo の1手)と blocks を同じ形で揃える** —
  揃えないと set_body_text の性質の持ち越し(段落番号ベース)がずれる
- ページ番号は `paper::paginate`(to_pdf と同じ折り方に一本化)から出す —
  **目次の番号と印刷した紙が食い違わない**

## writer のヘッダー・フッター(2026-08-03)

- **モデル**: `Document.header / .footer = HeadFoot`(段落の列 + 読み込んだ部品名)。
  **paragraphs が空 = 持っていない/持てなかった**。空のヘッダーは空の段落1つで表す。
  この区別で「触っていない部品を保存で書き潰さない」を守る
- **ページ番号**は私用領域の1字 `PAGE_MARK`(U+E000)として文中に持ち、
  docx とは PAGE フィールドで相互変換する(fldSimple と fldChar の両方を読む。
  separate〜end の「計算済みの見た目」は捨てる — 開く側が計算し直すもので、
  持ち越すと古い番号が本文に化ける)。PAGE 以外のフィールドは報告して落とす
- **編集はパネル方式**(writer の検索欄と同じ)。紙面の上で直接編集しないのは、
  番号への置き換えでバイト位置が変わり、キャレットが嘘をつくため。
  パネルでは印を《ページ番号》と見せる
- **描画**: 画面の紙は巻物なので、ヘッダーは紙の頭・フッターは末尾の頁の位置に
  灰色で出す(番号は1ページ目のもの)。**本当の番号は紙(PDF)で入る** —
  `paper::to_pdf_with(page_decor)` が頁ごとに `kumihan::layout_hf` の行を置く
- **保存**: 原本に部品(headerN.xml)があれば**同じ名前へ書き戻す**
  (参照・rels・[Content_Types] は原本のまま)。無ければ johdr1/joftr1 を作り、
  sectPr に参照を差し込む。**表入りのヘッダーは編集の対象にしない**
  (モデルが表を持てるようになるまで、壊すより原文を生かす。開いたとき報告する)

## writer の保護と共同編集(2026-08-04)

発注者確定: コラボレーション・保護・プラグインのボタンも灰色のままにしない。
順に実装する。まず「保護」と「共同編集モード」。

- **保護(prot-doc)** = docx の `documentProtection`(settings.xml)の
  `w:edit="readOnly"` と往復する読み取り専用。効き目は本物:
  打鍵は on_edited の入口で取り消され(undo で文書と一致するまで戻す)、
  文書を変えるボタンは run_cmd の白表(READONLY_OK)で断る。
  見る・出す・保存・検索は通す。Tab のインデントは run_cmd を通らないので
  para() にも同じ番人を置いた
- **パスワードは掛けない(掛けた振りもしない)**。Word のパスワード無し
  「編集の制限」と同じで、解除は誰でも同じボタン1手。ハッシュ照合だけの
  保護は錠前ではなく注意書き — そう見せる
- **バージョン履歴(co-history)** = 上書き保存の前に直前の中身を
  `.jo-history/<名前>/<mtimeの日時>.docx` へ控える(9世代)。パネルから押すと
  **名無しの複製**として開く — 元のファイルを黙って書き戻さない
  (戻すなら同じ名前で保存する、を人に選ばせる)
- **チャット(co-chat)** = 文書の隣の申し送り帳 `名前.docx.chat.txt` に
  名乗り(user@host)と日時つきで追記する言伝。サーバーは無いので
  生放送ではない — そう見せもしない
- **マクロ(plug-macros)** = calc の Python と同じサンドボックス(bubblewrap)の中で、
  python-docx が文書の**複製**を直し、直った複製を読み込む(台本の `d` が
  文書)。文書にコードは載せない — 「開く=実行」を作らない設計はそのまま。
  戻すのは Ctrl+Z の1手(doc_undo に直前の文書を控える)
- **プラグインの管理(plug-manage)** = `~/.config/officework/plugins` の .py を
  一覧し、マクロと同じサンドボックスで実行するだけの素直な置き場方式
- **暗号化(prot-encrypt)** = ECMA-376 Standard Encryption(AES-128・
  SHA-1 50000回・CFB 容れ物)を `ooxml::crypt` に自作。Word 2007 以来の
  「標準」方式で、書いたものは msoffcrypto-tool(実物の Word 暗号を解く
  道具)で解けることを実地で確認済み = 形式が本物。Word 2013+ の既定の
  Agile 方式は**まだ読めない — 読めないと言う**(黙って壊さない)。
  開くときはパスワードのパネル(伏せ字)で聞き、保存も同じ鍵で包み直す。
  原本の部品持ち越し・マクロ・バージョン履歴も解いた平文で回す
- **デジタル署名(prot-sign)** = **隣の .sig への添え書き**(Ed25519。
  鍵は ~/.config/officework/sign.key に自動生成・0600)。押すと 有効なら報告、
  無い・中身が変わったなら署名し(直し)。Word の署名欄に出る XML-DSig
  ではない — そう言って出す(改ざん検知と名乗りが実体。本人確認の
  基盤は持たない)。書式は外部の道具でも検証できることを確認済み
- **共同編集モード(coauth-mode)** = 新しい仕組みは作らず、既にある
  ファイルの錠(`.~lock.名前#`)の顔。押すと錠の今を名乗り付きで見せ、
  先客が去っていれば編集権を取り直す。サーバーの無い共同編集は
  「早い者勝ちの編集権 + 後の人は読むだけ」が正直な形

**calc も同じ機構で全部実装済み(2026-08-04)。** 違いは2つだけ:
保護は docx の documentProtection ではなく **xlsx の sheetProtection**
(シート単位。編集の堰は commit / fmt / 貼り付け / Del / run_cmd の白表
PROTECTED_OK)。マクロは python-docx ではなく **Python in Calc と同実体**
(b=ブック s=シート)。暗号化・署名・履歴・チャット・錠の顔は共通の
仕組み(ooxml::crypt / .sig / .jo-history / .chat.txt)をそのまま使う。

## writer の HTML — JS なしの閲覧と記入(2026-08-04 発注者)

Web の原型(文書+フォーム+サーバー側ロジック)を writer で受ける。
狙いは公開 Web のブラウザ代替ではなく、**閉域・社内の業務 Web と
自作サーバーの「閲覧と記入」側**。実装は writer 側(相方)。

- **開く**: .html(ローカル)と、サーバーが返す HTML。構造(見出し・段落・
  リスト・表・画像・フォーム)+ごく基本の CSS を kumihan の紙面に写す。
  目標は「文書として読める・刷れる」で、ブラウザの再現ではない。
  理解しない要素は帳簿へ(黙って落とさない)
- **JS は実行しない(読み飛ばす)。** 「開く=実行」を持たない方針の適用。
  JS 前提のページは動かない — 読めないものは読めないと言う
- **記入**: フォーム(input / select / textarea)を記入欄として見せ、
  送信は GET / POST の往復。表計算の入力規則と同じで、書いて・送って・
  返ってきた文書を読む、の繰り返し
- **コードは文書と一緒に旅をしない**(発注者確定)。サーバーがコードを
  配って手元で実行させる形(Web の JS の形)は作らない。サーバー側の
  ロジックは運用者が Python で別途書き・別途配る。手元の補助が要る場合も
  Python in Calc と同じ別経路(明示の操作+サンドボックス)— **文書の配布路と
  コードの配布路を分けたまま保つ**
- **網の線引き(2026-08-04 改訂: 公開 Web も見える)**: 発注者「インターネットの
  Web が見えるのでも悪くない」。http と https の両方を開き、リンクも辿る
  (rustls + webpki-roots。転送 3xx は5回まで)。**ただし JS は不変で
  実行しない**ので、動くのは「JS なしで完結するページ」だけ。
  **記入の送り先は開いた起点だけ**(別ホストの action へは送らない)—
  読みは広く、書きは狭く。ページ内の別ホストの画像・CSS はまだ取りに
  行かない(次の磨き)。Cookie は持たない
- **保存は docx、印刷は PDF**(HTML 書き出しは作らない — 互換は書式の
  境界で守る)。開いた HTML を docx で保存すれば HTML→Word の変換にもなる
- **ブラウザ化の坂には登らない**: タブ・履歴・キャッシュ・拡張は作らない。
  Cookie・認証は最小限をどうするか、実装の相談事項として残す
- **読み側は実装済み(2026-08-04)**: 自作の部分集合パーサ
  `kumihan::html`(見出し・段落・b/i/u/a・ul/ol・表・HTML の ruby →
  うちのルビ・title → 文書の情報・実体参照・p/li/tr/td の閉じ忘れの癒し・
  script/style は丸ごと読み飛ばし・知らない要素は帳簿)。writer で
  .html を開くと文書として読め、docx 保存も PDF もそのまま効く。
  文字コードは UTF-8 → CP932(encoding_rs)。受入 sample/html の
  11件が全部読める(閉じ忘れの表も同じ形に癒えるのを試験で固定)。
  **記入も実装済み(同日)**: form の欄(input/select/textarea)は
  記入のパネルに並び、押して打って Enter、送信で GET/POST(urlencoded)。
  答えの HTML をまた読む、の往復。**リンクのパネル**からリンクを辿れる。
  URL は ファイル > URLを開く(http と https。転送も追う)。
  検証は catalog_server.py 相手に実地(注文書の form 22欄・リンク辿り・
  POST → 答えの HTML)。本文中の記入欄は下線の空欄のまま =
  記入はパネルで行う(本文の欄の直接編集は次の課題)
- 実装の見立て(2026-08-04 発注者「それほど難しくない」— 同意):
  HTML→モデルの写像はほぼ1対1で受け皿が既にあり、**モデルに乗れば
  画面・PDF・docx 保存はタダで付いてくる**。対象が閉域の業務 Web なので
  パーサも**部分集合の自作で足りる見込み**(html5ever は「公開 Web を
  何でも読む」と約束する場合だけ)。段階と注意点は HIKITSUGI の申し送りに

### Web を作る側も簡単になる(2026-08-04 発注者)

「JS なし・form まで」という線は、読む側(writer)だけでなく**作る側も
軽くする**。JS を捨てると Web 開発の重さの根源 — ビルド鎖・フレームワーク・
クライアントとの状態同期 — が丸ごと消え、残るのは「HTML を組んで返す・
form を受ける」だけ。これは Python の標準ライブラリで足りる仕事で、
実測もある: sample/catalog_server.py は**1ファイル・約170行・依存ゼロ**で、
カタログ配信(HTML と CSV の1ソース2形態)+注文フォーム+受付+台帳まで持つ。

これで「業務ソフトはもう作らなくていい」(端末のソフトの土台の節)の
第3の形が揃う:

1. **ブック**(xlsx = 帳票+サンドボックスつきコード+運用)— 共有フォルダで配る
2. **文書**(docx = 様式・カタログ。python-docx で生成)— 同上
3. **閉域の小さな Web**(JS なし HTML + form + Python サーバー)—
   複数人が同時に書き込む台帳・受付がここに収まる(排他ロックの xlsx では
   足りない、同時受付の仕事)

どれも**配布物は文書、コードの配布路は別**(サーバーは運用者の持ち物、
ブックのコードはサンドボックスの中)。手元に実行コードが配られる形が無いので、
クライアント側の攻撃面がそもそも生まれない(サーバー側は html.escape を
守るだけ)。**JS が欲しくなったら、それは「文書でない Web」の合図** —
このソフトの範囲の外(「バイナリを増やしたくなったら範囲の外」と同型)。

**公開用の「動き」も2層で作れる(2026-08-04 発注者)。**
①照会→応答の動き(検索・絞り込み・ページ送り・受付)は**サーバー側の
Python がページを組み直す** — form の GET/POST の往復で、JS は要らない。
②手元の見た目の動き(分類の開閉・行の強調・畳み)は **HTML/CSS の宣言**
(details/summary・:hover・CSS アニメーション・フォームの検証属性)—
どれも「実行コード」ではないので方針に触れない。実測は
sample/catalog_server.py の catalog.html(検索=①、分類の開閉=②)。
②の宣言的な部品を writer がどこまで読むかは実装時の判断
(details は「開いた文書」として読めれば足りる)。

**商品は絵で選ぶ(2026-08-04 発注者)。** form は受付の底であって、
カタログの本業は**選ばせる**こと — 商品が見えて、どれがいいか分かること。
これも実行コードなしで作れる(見本 catalog.html で実測):

- **絵**: サーバーが商品ごとの SVG を配る(生成も標準ライブラリで足りる —
  文字だけの SVG は組み立てるだけ。写真ならファイルを置いて配るだけ)。
  陳列は CSS grid のカード(絵・品名・値段が一目)
- **選ぶ**: カード全体が label = 押すと札が入る。選んだ札が光るのは
  CSS の `:has(:checked)` — ここまで宣言だけ
- **比べる**: 選んだ札を「比べる」で送ると、**サーバーの Python が
  比較表を組み、いちばん安い列に印を付けて返す** — 「どれがいいか」の
  判断材料を出すのはサーバー側の仕事にできる
- **writer への含意**: HTML 読みで **img は後回しにできない**(カタログは
  絵が本体。文字が読めても絵が出ないカタログでは選べない)。段階①の
  部分集合に img(同一サーバー / ローカル相対のみ)を含めること

**改訂(2026-08-04 発注者確定): Pyodide / PyScript はやる。**
①②だけでは「押していないのに画面が動く」類が作れず、**受け入れられない**
— 採用されなければ、この安全設計は誰のことも守れない。当初「ブラウザで
Python を動かす形はやらない」と書いたが、同日に改めた。筋はこう通す:

- **ページの動きも Python で書く**(JS は書かない。PyScript / Pyodide の
  ランタイムは既製品として使う — 自分たちが JS を書くのは今後も無い)。
  ブラウザでの実行環境は **WASM の砂箱** — Web が既に受け入れているサンドボックス
- **writer で開いたときは自動実行しない。** ページに載った Python は
  Python in Calc のブック搭載コードと**同じ扱い** — 明示の操作+
  bubblewrap のサンドボックス(網なし既定・`net` は都度明示)。「開く=実行を持たない」
  は writer では不変。実行しなくても文書として読める作りを求める
  (動きは飾り、中身は文書 — 劣化は正直に)
- **線引きの言い直し**: 「配ったコードは実行しない」ではなく
  **「配ったコードは砂箱の外で実行しない」**。ブック(Python in Calc)が
  既にこの形で運用されている — HTML の Python も同じ線に揃えるだけで、
  方針の核(裸の実行経路を持たない)は動かない
- 閉域は CDN に出られない — PyScript / Pyodide の**ランタイムはサーバーが
  自前で配る**(同梱。Pyodide は十数MB)。公開用は CDN でもよい
- **どこまでのブラウザで動くか(2026-08-04 に確認)**: 条件は
  WebAssembly + JS 有効。ここ数年の Chrome / Edge / Firefox / Safari なら
  全部動くが、「すべて」ではない — IE・古い WebView・JS を切った環境では
  動かない。だから **form の素の往復が全ブラウザの底**(動きは上乗せ。
  PyScript が動かなくても記入と送信は完結する作りを求める — writer の
  「実行しなくても文書として読める」と同じ規律)。PyScript には
  **MicroPython ランタイム(約170KB・即起動)**もあり、numpy 等が要らない
  動きはこちらが向く(閉域の同梱も軽い)。Pyodide のスレッド系だけ
  COOP/COEP ヘッダが要る — 使わなければ不要

**補正(2026-08-04 発注者): PyScript にはこだわらない。**
約束するのは「**ページに Python を載せてよい・砂箱の外で実行しない**」の
線だけで、PyScript は実行環境の一つに降ろす:

- **writer はネイティブで回す。** ページの `<script type="py">` は、
  writer では WASM もランタイムも経由せず、**機械の Python + bubblewrap のサンドボックス**
  で直接回す(Python in Calc の run_python_inner がそのまま実行部。
  明示の操作・網なし既定は不変)。PyScript の API 互換は目標にしない —
  ページに要るのは**記入欄の値の出入り**だけ: calc の `b`/`s` に相当する
  束縛として `form`(記入欄の名前→値の辞書)を渡し、返った値を writer が
  紙面に書き戻す。DOM は持ち込まない
- **閉域は writer が動きの器。** ランタイム同梱(十数MB)の話は閉域からは
  消える — サーバーは HTML を配るだけでよい
- **ブラウザ向けは任意の上乗せ。** 公開用で手元の動きが欲しければ
  PyScript / MicroPython を足せる(その時も form の往復が底)。
  約束はしない — 「全ブラウザの底は form」の規律が正

## 数式を原文で持ち越した(2026-08-10。上の順の 1)

**「理解はしないが捨てない」だけをやった。組版はしていない。**
`<m:oMath>`(文の中)と `<m:oMathPara>`(独立した数式)を read_to_end で
丸ごと控え、`Paragraph::anchors` に入れて保存でそのまま返す。
`sect_raw`・画像と同じ作法。

同時に**中の字が本文へ漏れるのが止まった**。`local()` は接頭辞を落とすので
`<m:t>` が `<w:t>` の枝に落ちていて、それが「平文になる」の正体だった。
部分木を読み飛ばせば漏れも消える(図形の `a:t` と同じ形の穴)。

### 数で(現物2枚 = pandoc・LibreOffice Writer)

| | 前 | 後 |
|---|---|---|
| `m:oMath` が保存後に残る数 | **0 / 8** | **8 / 8** |
| `m:oMathPara` | **0 / 4** | **4 / 4** |
| zip の部品が欠けた文書 | 0 枚 | 0 枚 |

保存した物を LibreOffice に開かせ直すと、**8つとも数式の物体として読み直す**
(平文ではなく)。`pydoc_diff --roundtrip`(審判は向こうの読み手)の差は
6件 → 4件、段落の数の食い違いは**消えた**。

### **自分で書いた文書では出なかった穴が2つ**

corpus を書き手違いで2枚集めたことで出た。詳しくは `docs/corpus-docx.ja.md`:

1. **`xmlns:m` の置き場が書き手で正反対。** pandoc は root、
   LibreOffice は `<m:oMath>` の要素側。後者に宣言を足すと二重になって壊れる
2. **`xml:space="preserve"`。** `xml:` は宣言してはいけない既定の接頭辞なのに
   「解決できない」と数えていて、**LibreOffice の数式が4つとも落ちていた**。
   これは数式に限らず、**画像の `wrap_with_ns` にも同じ穴が空いていた**

### 残っている限界(**帳簿にそう書いてある**)

- **段落の中の位置は戻らない。** anchors は段落の頭に寄るので、
  文の途中の数式は文頭へ動く。**字は残るが並びは変わる。**
  独立した数式(`oMathPara`)は段落を独り占めするので見た目は変わらない。
  直すには anchors を run の並びに織り込む必要があり、模型の作り替えになる
  (画像も同じ限界を持っているので、直すならまとめて)
- **組版はしない。** writer の画面に数式は出ないし、編集もできない(上の順の 4)
- 帳簿の文言は「数式(段落の頭に寄るが、保存で残る)」。
  **もう起きない損(平文になる)は言わない**が、**黙りもしない**

### 呼ぶ側から見た変化(2026-08-10。pyoffice の指摘を受けて)

pyoffice から**「突き合わせが緑でも契約は守れていないことがある」**という

うちのサイドカーも xlsx 専用。**「向こうの試験をうちに掛ける」は docx では
成り立たない** — やっていないのではなく、掛ける先が無い。

代わりに、**うちの契約面**(`officework.doc`)で効く変化を確かめた:

- **`d[i].text` から数式の字が消えた。** 前は `<m:t>` が本文へ漏れていたので
  `text` に混ざっていた。いまは `anchors` に居るので出ない。
  **直した結果だが、呼ぶ側から見える変化ではある**(本文の字として
  数えていた人は数が変わる)
- `d[i].text = …` と段落の分割は**控えを巻き添えにしない**。
  分割時は前半に残り、二重にもならない(`engine` の `ps == pe` の枝)。
  画像と同じ約束で、試験で留めた

向こうの `math.test.ts` を**仕様書として読んだ**うえで、うちに覆いの無かった
形を3つ試験にした — **表のセルの中**・**ヘッダーの中**・**1段落に数式が2つ**。
3つとも既に通っていたので直しは無い。**穴ではなく覆いが無かっただけ**だが、
覆っていなければ次の書き換えで落ちる。


## 複数の節 — 用紙ごと組み直す(2026-08-10。上の順の 2)

**「持ち越す」で止めず、組版まで通した。** 途中で用紙の向きが変わる文書が、
向きの違うページとして正しく折れる。

### docx の書き分けと、1つずれる罠

docx は節の設定を**2か所に書き分ける**:

    途中の節 … その節の**最後の段落**の `w:pPr` の中
    最後の節 … `w:body` の直下(段落の外)

見分けは「段落の中に居るか」だけで付く(`w:p` で `para` が立ち、`/w:p` で
落ちる)。**`w:sectPr` は節の「終わり」に置かれる**ので、ある段落に効く用紙は
「その段落以降で最初に現れる節末」のもの。だから
[`section_geometry`] は**後ろから前へ**なぞる — 前から数えると必ず1つずれ、
**節末の段落自身がどちらの節か**を取り違える。発注者の指摘で試験に釘を打った
(3節・真ん中だけ横向き)。

### 何を変えたか

| 層 | 変更 |
|---|---|
| 模型 | `Paragraph::sect_raw`(保存用の原文)と `Paragraph::sect`(組版用の `PageSetup`)を**別に持つ**。`anchors` と `images` と同じ関係で、engine は docx を解析しない |
| `layout()` | 段落ごとに行長を引き直す。**紙の幅が変われば折り返しがやり直しになる**(折る所だけの話ではない)。節の切れ目で `breaks` と `sect_pages` を置く |
| `Sheet` | `sect_pages`(この y から先はこの紙)。**節が1つなら空**にしてあるので、今までの道は1ミリも変わらない |
| `paper` | `paginate_papers` が**ページごとの紙**も返す。`paginate` は今までの形のまま(呼ぶ側を壊さない)。PDF はページごとに大きさを変えて作る |

### 数で(実物: LibreOffice Writer の縦→横の2節)

    途中の節 1 ・ 最後の節 297x210(横)
    sect_pages  [(0.0, 210x297), (27.8, 297x210)]
    ページごとの紙  [(210x297), (297x210)]
    PDF の MediaBox  [210.0, 297.0] / [297.0, 210.0]   ← 紙そのもので確認

### **実物を PDF まで通して見つけた2つ**

手で組んだ試験だけでは出なかった。どちらも試験に落とし込んである:

1. **1ページ目だけ最後の節の紙で刷られていた。** `sect_pages` の先頭を
   上の余白(`y0_mm`)から置いていたので、その手前を引くと「節が無い」と
   読めて、呼ぶ側の紙(= 最後の節)へ落ちていた。先頭は **0 から**置く
2. **裏返しを文書の紙でやっていた。** PDF の原点は左下なので
   `height - y` で裏返すが、これを文書の紙(最後の節)の高さでやると、
   向きの違うページで字が紙の外へ出る(縦 297 と横 210 で 87mm)。
   **ページの大きさだけを見る試験は通ってしまう**ので、
   字の座標が紙に収まっているかを見る試験を別に足した

### 残り

- **writer の画面**(ページごとに大きさの違う紙を描く)は手つかず。
  UI 側だけの話なので区切りを跨がせない、という発注者の判断
- 画像と罫線の頁割りは `paginate` を使わず**自前で近似**していて、
  そこは文書の紙のまま。節が変わる文書では画像・罫線の位置が寄る
  (元からある弱さで、節の話とは別に直す所)
- ~~節の種類(`w:type`)を見ていない~~ → **`continuous` を入れた(下)**

### `continuous` の節では頁を割らない(2026-08-10。pyoffice の指摘)

**どの節も改ページ扱いにしているほうが危ない**という指摘を受けて直した。
段組みを変えるためだけの節が実物には多く、そこで頁を割ると見た目が大きく変わる。

    <w:type w:val="continuous"/>   → 頁を割らない(紙は前の節のまま)
    無い・nextPage・その他          → 割る(docx の既定は nextPage)

**ただし紙の大きさが違えば、continuous でも割る。** 1枚の紙は1つの大きさしか
取れないので従いようがない。そこも試験にしてある。

あわせて、節の3つの顔(**保存の原文・組版の用紙・改ページするか**)を
`kumihan::SectionBreak` に**1つにまとめた**。別々の欄に置くと、
片方だけ更新して食い違う事故が必ず出る — 必ず一緒に動く物だから。

### 画像と罫線の頁割りを本文と一本化(2026-08-10)

節の仕事で見えた**元からの弱さ**。`to_pdf_with` の中で、画像と罫線だけが
本文とは別に**「どの頁も同じ高さ」と決め打ちした近似**を持っていた。
節で紙が変わる文書では必ず外れるし、節が無くても本文とずれうる。

`paginate_full` が [`Pagination`] を返す形にして、**本文も画像も罫線も
同じ表を引く**ようにした。

**ここで自分の直しが1回落ちた。** 最初は `offsets`(頁ごとの繰り上げ量)で
「この y はどの頁か」を引こうとしたが、`offsets` は
`最初の行の y − 余白` なので**前の頁の裾と重なる**。行間(6.4mm)より
余白(20mm)のほうが大きいので、前の頁の最後の行まで次の頁に入ってしまう。
頁の**切れ目**(その頁の最初の行の y)を別に持つのが正しく、
`Pagination::starts` がそれ。

試験は「PDF が出来た」ではなく、**同じ y に居る本文の行と同じ頁に来るか**を
見ている。旧実装に戻すと2件とも落ちることを確かめてある
(SEKKEI.md「緑は『正しい』ではなく『この物差しでは差が出ない』」)。

## 脚注の印を持ち越した(2026-08-10。上の順の 3)

### **見立てが外れた — 部品の工事は要らなかった**

設計では「部品が増えるので `[Content_Types]` と rels の往復まで要る」と
見ていた。**保存に限れば要らない。** 保存の実装は

    // 本文だけがこちらの管轄。他の部品は原本のまま
    if name == "word/document.xml" { continue; }

で、**`document.xml` 以外を丸ごと持ち越す**。`[Content_Types]` と
`document.xml.rels` も原本を控えて足りない分を足すだけ。だから
`word/footnotes.xml` も宣言も関係も**最初から残っていた**。

落ちていたのは**本文の印だけ**。ただし結果は重く、
**脚注の文章は残ったまま指す物を失う**(開くと脚注が消えて見える)。
数式のときと同じ形 — 部品はあるのに繋がらない。

部品の工事が要るのは**新しく脚注を作るとき**で、失わないだけなら要らない。

### 印は run に持つ(**控えではなく**)

数式は控え(`anchors`)で妥協して段落の頭に寄せたが、**脚注は位置が意味そのもの**
── どの語に付いた注かが変わる。だから `CharFormat` に持たせた。
`field`・`ruby`・`sdt` と同じ持ち場で、理由も同じ(run の切り貼りが面倒を見る)。

    pub footnote: Option<FootnoteRef>   // { id: String, endnote: bool }

**id は字で持ち、振り直さない。** 書き手ごとに番号が違い(pandoc は 20・21・22、
LibreOffice は 2・3・4、仕切り線に -1 を使う物もある)、footnotes.xml とは
番号で繋がっているので、直すと切れる。

### **踏みかけた穴 — 印の run は字を持たない**

`<w:r><w:footnoteReference w:id="2"/></w:r>` に `<w:t>` は無い。ここが3か所に効いた:

1. 読み手は `</w:t>` で run を積む → **印の run は生まれない**
2. 書き手は `if run.text.is_empty() { continue }` → **書かれない**
3. `normalize_runs` は字の無い run を落とす → **編集や組版を一度通ると消える**

3つ目がいちばん危ない。読み書きだけ直すと**試験は緑で、使うと消える**。

### 数で(現物2枚 = pandoc・LibreOffice Writer)

| | 前 | 後 |
|---|---|---|
| 本文の印 | **0 / 6** | **6 / 6** |
| footnotes.xml の中身 | 6 / 6(元から無事) | 6 / 6 |
| zip の部品の欠け | なし | なし |

id も**位置も**原文どおり(同じ段落に2つ、文の途中に付く形も)。保存した物を
LibreOffice に開かせ直すと、**両方とも3つとも脚注の物体として読み直す**。
`pydoc_diff --roundtrip` は脚注の2枚とも **○**(差なし)。

### 残っている限界

- **本文には出ない。** 画面にも紙にも脚注の番号は出ないし、脚注の領域も無い
  (`layout` と `paginate` に手を入れる仕事。ここは別)
- **段落の text を丸ごと差し替えると、その段落の印は消える。**
  run を作り直すので当然で、`field`・`ruby` と同じ振る舞い(予測できる形で壊す)。
  **触っていない段落の印は残る** — 実物で確かめた(3 → 1、別段落を触れば 3 → 3)
- 新しく脚注を**作る**のはまだできない(部品の工事が要るのはそちら)

## 脚注を紙面に出した(2026-08-10。上の順の 3 の後半)

印を持ち越すだけだった脚注を、**番号と、紙の下の領域**として出るようにした。

### 三段

1. **中身を読む** — `word/footnotes.xml` / `endnotes.xml` を
   `Document::footnotes` へ。中の段落は本文とまったく同じ形なので、
   一つぶんを `w:body` に包み直して**本文の読み手を借りる**。
   **表示のためだけ**に読む(保存は部品を原本のまま持ち越すので触らない)
2. **番号を出す** — 本文の印の所に上付きの数字。
   **番号は出てくる順**で、docx の id ではない(LibreOffice は 2・3・4、
   pandoc は 20・21・22。id を出すと「脚注 2 番」から始まる文書になる)
3. **紙の下に組む** — `Sheet::notes` に組み上がりを持ち、
   頁割りが「その頁に載る脚注」を決め、`to_pdf` が仕切り線とともに引く

### **仕切り線の定義は脚注ではない**

実物2枚とも `footnotes.xml` の頭に `w:type="separator"` と
`continuationSeparator` が入っていた。数に入れると**番号が2つずれる**。

### 循環がある — 頁割りと脚注は切り離せない

> どの脚注がその頁に載るかは**頁割り**が決め、
> 脚注の高さは**本文に使える高さ**を削り、それが**頁割り**を変える

`paginate_full` の中で、行を1つ進めるたびに「この行に付いた脚注」を数え、
その高さぶん本文の底を上げる形にした。**行が次の頁へ動けば、その行に付いた
脚注も一緒に動く**(ここを忘れると、印は2頁目・脚注は1頁目に出る)。

### 印は本文の字ではない — バイト位置を動かさない

印の run は字を持たない。番号を run の text にすると、**後ろの全部の字の
バイト位置が1つずれて、カーソルが本文とずれる**。箇条書きの印と同じく
「組むときだけ現れる字」として置き、`off` は動かさない。試験で釘を打った。

### 確かめ方

**出来上がった PDF に聞いた。** 本文に 1・2・3 の上付き、紙の下に
仕切り線と3つの脚注が番号つきで並ぶ。あわせて、
**「脚注が出た」ではなく「字が紙の中に居るか」**を見る試験を置いた —
大きさだけを見る物差しは、紙の外へ出ていても緑になる(SEKKEI.md の教訓)。

### 残り

- ~~**writer の画面**は手つかず~~ → **脚注は出した(2026-08-11)。下に結果**
- ~~**文末脚注**の置き場~~ → **直した(2026-08-11)。下に結果**
- 頁をまたぐ長い脚注は**割らない**(その頁に丸ごと載せる)
- ~~新しく脚注を**作る**~~ → **できるようにした(2026-08-12)。下に結果**

### 脚注と文末脚注は **id が衝突する**(2026-08-10。自分で入れた穴)

紙面に出す仕事を入れた直後の見直しで見つけた。注を引くところが

    doc.footnotes.iter().find(|n| n.id == *id)

と **id だけで引いていた**。docx は `footnotes.xml` と `endnotes.xml` を
**別々に番号付けする**ので、どちらも 1・2・3… から始まり、
**両方を含む文書では id が必ず衝突する**。先に見つかったほう(= 脚注)が
勝つので、**文末脚注の印に脚注の文章が付いていた**。

印を畳むところ(同じ印の連なりを1つに数える)も同じ穴だった。
`FootnoteRef` ごと持って `id` と `endnote` の両方で見るように直した。

**「限界」として書いていたが、実際は取り違えだった。** 集めた現物2枚に
文末脚注が入っていなかったので出なかった — また
「その物差しでは差が出ない」形で、SEKKEI.md の型がそのまま当てはまる。
**corpus に文末脚注入りの1枚を足すこと**が次の手当てになる。

## 文末脚注をきちんと置いた(2026-08-11)

脚注と一緒くたにしていた文末脚注を、**別の数え方・別の置き場**に分けた。
きっかけは、脚注を紙面に出した直後に corpus の穴(文末脚注入りが1枚も無い)を
埋めたら、**取り違え**と**番号の飛び**が同時に出たこと。

### 三つ直した

| | 前 | 後 |
|---|---|---|
| **注の引き当て** | id だけで引く | **id と種類**で引く(下) |
| **番号** | 脚注と文末脚注で1本の連番 | **別々に数える** |
| **置き場** | どちらも紙の下 | 脚注は紙の下、**文末脚注は文書の末尾** |

### id は**必ず**衝突する

docx は `footnotes.xml` と `endnotes.xml` を**別々に番号付けする**ので、
両方を含む文書ではどちらも 1・2・3… になる。実物(`both-notes.docx`)は
**脚注 2・3 と文末脚注 2・3** だった。id だけで引くと、文末脚注の印に
脚注の文章が出る(直す前のコードで確認済み)。

### 番号の書式は文書が持っている

`settings.xml` に書いてある。実物はこう明記していた:

    <w:footnotePr><w:numFmt w:val="decimal"/></w:footnotePr>
    <w:endnotePr><w:numFmt w:val="lowerRoman"/></w:endnotePr>

**脚注は 1・2、文末脚注は i・ii。** 算用数字で通すと見た目から間違いになる。
`decimal` / `lowerRoman` / `upperRoman` / `lowerLetter` / `upperLetter` を持ち、
知らない書式は算用数字に落とす(**知った顔をしない**)。

**docx の既定を知っているのは読み手のほう。** settings が黙っていれば
文末脚注はローマ数字の小文字 — Word も LibreOffice もそうする。模型
(`kumihan`)の既定は算用数字で、docx の作法は `ooxml` が入れ直す。
札の中だけを見て引く(文書には他にも `w:numFmt` があるので、
範囲を切らずに探すと隣の設定を拾う。試験で留めた)。

### 実物での見え方

    紙面: 本文の一つ目です1。つづいて文末脚注i。
          二つ目の段落に脚注2と文末脚注ii。
          i  これは文末脚注の一つ目。        ← 文書の末尾へ流れる
          ii これは文末脚注の二つ目。
    紙の下: 1 これは脚注の一つ目。 / 2 これは脚注の二つ目。

文末脚注は**本文の行として後ろに足す**ので、普通に頁をまたいで流れる。

### 残り

- 文末脚注の前に**仕切りも見出しも置いていない**(1行あけるだけ)。
  Word は罫を引く。どこまで似せるかは決めていない
- **節ごとの文末脚注**(`w:sectPr` の `endnotePr`)は見ていない。
  文書の末尾に集めるだけ

## 画面にも脚注を出した(2026-08-11)

### **半分は既に出ていた**

調べたら、画面の描画は `fmt.superscript` を見て小さく上へずらす作りが
既にあった。脚注の**印(上付きの番号)は普通のセル**として `sheet.lines` に
入っているので、**手を入れなくても出ていた**。文末脚注も、本文の行として
末尾へ足す形にしてあるので同じ。

足りなかったのは**紙の下の領域**だけだった。

### 画面と紙で頁割りを一本にした

画面は `paper::paginate`(頁の位置だけ)を別に呼んでいた。**脚注はその頁の
本文の底を上げる**ので、別々に数えると**画面と PDF で脚注の出る頁が食い違う**。
`paginate_full` から `offsets` と `notes` を一緒に受け取る形に変え、
`Writer::page_notes` に持たせた。

試験は「脚注が出た」ではなく、**画面が持っている割り当てと紙が出す割り当てが
値として等しいか**を見ている(`page_notes` と `page_offsets` を直接突き合わせ)。

### 節ごとの紙は**入れていない**

画面の紙は**1枚の長い div**(`content_mm()` の高さ、`paper_w_mm()` の幅)で、
巻物をそのまま流す作り。**幅が途中で変わる文書をこの形では表せない** —
1ページ1枚の div に作り替える話になり、画面の骨格の作り直しになる。
別の仕事として残す。

### **目で見てはいない**

画面は GPUI で、この機械では起動して確かめられていない。確かめたのは
**割り当ての値が紙と一致すること**までで、**描く位置が正しいかは見ていない**。
紙(PDF)側は出来上がった PDF から読み出して確かめてあるので、
同じ座標の勘定を写してある — が、それは根拠であって確認ではない。

## 脚注を新しく作れるようにした(2026-08-12)

読んだ注は原本の部品がそのまま持ち越されるので触らない。**足したぶんだけ**
部品を用意する。`images` と `images_new` と同じ持ち場の分け方で、
`Footnote::added` が立っている物だけがこちらの管轄。

    let fr = doc.add_footnote(false, vec![脚注の段落]);   // 印が返る
    run.fmt.footnote = Some(fr);                          // 置いた位置が注の位置

### **3つ揃って初めて Word が出す**

`comments.xml` の型紙そのままで、4か所に手を入れた:

| | 何を |
|---|---|
| 持ち越しの輪 | 足したときだけ原本の `footnotes.xml` を外し、**原文は控える** |
| `[Content_Types]` | `footnotes+xml` / `endnotes+xml` の宣言 |
| `document.xml.rels` | `footnotes` / `endnotes` への関係 |
| 部品 | 控えた原文の**閉じ札の直前へ差し込む** |

**部品だけあっても、宣言か関係が欠ければ Word は無視する。** 試験は3つとも
別々に見ている(1つ忘れても緑にならないように)。

`footnotes.xml` には仕切り線の定義と、こちらが模型に持っていない書式が入って

原本が無いときだけ新しく作る。そのとき **`separator` と
`continuationSeparator` を必ず入れる** — これが無いと Word は注を出さない。

`footnotes` には仕切りを載せていない(本物の注ではないので)が、
**id は取られている**。載っている注だけを見て番号を選ぶと、
仕切りの id(-1 や 0、書き手によっては 1)とぶつかる。
読み手が**種類に関わらず全部の id を控える**ようにして、そこも避ける。

黙って落ちていた**。脚注に限らず**画像・コメント・設定も同じ道**を通るので、
そこも一緒に直った。元からあった穴で、脚注のせいではない。

## 脚注のボタンを付けた(2026-08-12)

参考資料タブに「脚注」。**選んだ字を注へ移し、跡に印を置く。**

    選択が空          → 「脚注にする字を選んでから押してください」
    段落をまたぐ選択  → 「脚注にできません(段落をまたぐ範囲は選べません)」
    それ以外          → 字が注へ移り、跡に印。紙の下に出る

**この操作は取り消せない。** 取り消しは `Editor` が持っていて、控えるのは
**平文だけ**。字を模型(注)へ移すこの操作は平文の巻き戻しでは戻らず、
平文を取り直す時点で**それまでの履歴ごと消える**(参照の更新も同じ形で、
先に「この操作は戻せません」と言っている)。

直せていないので**そう言う** — 文言に「取り消しはできません」を入れ、
**その約束が本当かを試験で見る**(黙って戻せなくならないように)。
直すには文書そのものの取り消しが要る。いまは平文の取り消ししか無い。

### 空の注を作って別の窓で打たせる形にはしない

Word は「脚注の挿入」で空の注を作り、そこへ打たせる。**こちらは注を打つ
場所をまだ持っていない**ので、その形にすると空の注だけができて、
中身を入れる術が無い — **持っていない物を持っている顔をする**ことになる。

いま持っている道具(選択)で完結する操作にした。既にある字を注へ移すのは
実際によくやる操作でもある。

### 段落をまたぐ選択は**断る**

またいだ範囲をどう畳むかに正解が無い(段落の切れ目を注の中で保つのか、
繋ぐのか)。**決められないことを黙って決めない**ので、断って理由を言う。

### 文言と表の足し方 — **番号がずれる罠**

`ui/i18n/<locale>.json` は**番号だけ**で訳を指している。文言を足すと
`keys.json` の番号が**途中から全部ずれる**(こちらの3句は 107〜109 に入り、
以降が3つずつ動いた)。番号のまま放っておくと、13言語 × 1490 句の訳が
**全部1つずつ隣の文言を指す**。

日本語の鍵で対応を取り直してから足した(落ちた句 0)。

**ついでに分かったこと: いまの木では `gen_lang.py` も
`gen_ribbon_locale.py` も回らない。** こちらと関係のない欠けが前からある:

- ロケールの訳が 12 句欠けている(`数学/三角`・`印刷`・`スタイル` など、
  リボンの語)→ `gen_lang.py <loc>` が止まる
- vendor から引けない語が 44 個ある(`0を表示する` など)
  → `gen_ribbon_locale.py <loc>` が止まる(`en` だけは通る)

なので**足す3行だけを手で入れた**。表は (日本語, 訳) の組で、
リボンの表も id・並び・ready・icon が ja と一致していれば通るので、
生成物と同じ形になっている(試験が保証する)。

### **アイコンの実体は誰も検査していない**

ボタンは `ICONS` の表に載っているアイコンしか出せない。表に足し忘れると
**ボタンだけが無地で出る** — 押せるし配線もされているので、配線の試験
(`wiring_tests`)も文言の門番も素通りする。自分で足し忘れかけた。

検査を書いてみたところ、**既に 81 個のボタンが実体の無いアイコンを
指していた**(`pivot-*`・`py-*`・`fontname`・`fontsize` など。多くは calc 側)。
数が大きく、持ち場も違うので**門番は入れていない** — 見つけたことだけ残す。
入れるなら 81 個を埋めるか、既知の欠けを表にして「増やさない」を守る形になる。

## 文書ごとの取り消し(2026-08-13。段階1)

### 測ったら「弱い」のではなく「無い」だった

脚注が戻せない件を追ったら、もっと広い話だった。実際に動かした結果:

| 操作 | Ctrl+Z |
|---|---|
| 打鍵 | 戻る |
| **太字** | `undo()` が false。**太字のまま** |
| **中央揃え** | `undo()` が false。**Center のまま** |

理由は持ち場:

    打鍵 → Editor.text が変わる(取り消しはここにある)
         → flush_target() → doc.set_body_text() で文書へ
    太字 → doc.apply_char_format() で文書を直に変える(Editor を通らない)

**取り消しは `Editor` が持っていて、控えるのは平文だけ。** 文書を直に変える
操作は最初から視界の外にあった。マクロだけが `doc_undo`(1枚)で例外的に
戻せた。

### 一本にまとめた

二本立て(平文の取り消し + 文書1枚)のままでは**順序が読めない** —
「打ってから太字」のあとの Ctrl+Z が打鍵のほうを戻してしまう。
控えを1つの山にして、打鍵も書式も同じ順で戻る形にした。

    Snapshot { doc, text, cursor, target }   // 4つを揃えて持つ
    checkpoint(typing)  // **変える前に**控える。続けた打鍵はまとめる
    undo_step / redo_step

**4つを揃えて持つ**のが要点。文書だけ戻すと画面の平文と食い違い、
平文だけ戻すと書式が残る。

- 続けた打鍵は1手にまとめる(1字ごとに文書を控えると重いし、戻し方も細かすぎる)
- 控えは 100 枚まで(文書を丸ごと持つので)
- 戻したあとに打つと、やり直しの先は捨てる(枝分かれさせない)
- **パネル**(ヘッダー・置換・ルビなど)の打鍵は文書を変えないので、
  そこは今までどおり `Editor` 自身の取り消しに任せる

打鍵の入口は `ui::handler::replace` で writer と calc の共通路なので、
`HasEditor` に `before_edit(typing)` を足した(既定は何もしない)。

### 段階1で繋いだもの

`toggle()` — **太字・斜体・下線・取り消し線・上下付き**が同じ道を通るので、
1か所で全部繋がった。マクロと AI の控えも新しい山へ移した。

### 段階2(2026-08-13)— 残りを繋ぎ、門番を置いた

アプリ側の**ヘルパーに控えを入れる**だけで大半が繋がった:
`para`(揃え・箇条書き・字下げ・行間)・`size`・`set_align`・
`set_para_style`・`each_cell_para`・`set_page`・`insert_ref`・`bm_add`・
`make_toc`・`make_tof`。命令ごとではなく**通り道**に置くのが効く。

**試して2つ取りこぼしを見つけた**: 脚注と縦書き(`direction`)。
どちらも文書を直に変えるのに控えを取っていなかった。

門番を置いた(`undo_coverage_tests`)。**文書を変える命令を並べ、
押して→戻して→指紋が一致するかを見る。** 控えを入れ忘れた命令が
落ちる。`wiring_tests` が「押せるのに何も起きない」を止めるのと同じ形で、
こちらは「変えたのに戻せない」を止める。控えを1つ外して**落ちることも
確かめた**(「direction が一手で戻らない」と名指しで出る)。

**指紋の欄が足りないと取りこぼしが隠れる。** 縦書きは最初この指紋に

### 段階3 — 一覧を手で持つのをやめた

`HANDLED`(アプリが受ける全命令)から導く形に変えた:

    HANDLED から、押さない物(窓を開く・外に出る・取り消し自身)を除き、

**命令を足せば自動で見張りに入る。** 除く物は理由つきで関数に書いてある。

### 一手で控えは1枚(入れ子を止めた)

## 数式は Python に組ませ、OMML は読まない(2026-08-13 発注者確定)

上の「数式を原文で持ち越した」の続き。設計文書が「1〜3 が済んでから別に
判断する」としていた分の結論。**組版は自前で書かず、OMML も読まない。**

### 決めたこと

**入力は LaTeX。** 数式のボタンで小窓が開き、LaTeX を打って Enter
(ルビ・脚注と同じ作法)。SymPy の式からも起こせるが、**SymPy は式を
書き直す** — `(a+b)/2` が `\frac{a}{2} + \frac{b}{2}` になる。帳票に要るのは
原本どおりの見た目なので、既定は LaTeX 直打ち。検算ができるのが SymPy の
取り柄で、欠陥ではなく性質なので、そのことを検査に固定してある
(pysheet/test_tex.py)。

**組むのは Python**(calc がグラフを matplotlib に任せるのと同じ分業)。
TeX があれば pdflatex で組み、無ければ matplotlib の mathtext に落ちる。
**mathtext は LaTeX の部分集合**で、`\begin{matrix}` の環境を持たない —
`\substack` に寄せて縦に積むが、**列は揃わない**(桁の違う数値行列は歪む)。
TeX があれば揃う。二段構えが許されるのは**数式が絵として保存される**から
で、機械による差は作ったときの見た目に閉じる。実行のたびに組み直す作りなら
許されなかった。

**渡すのは絵と原文の二枚組。** 画像の代替テキスト(`wp:docPr descr`)に
`officework:tex:` の印を付けて LaTeX を積む。渡した先の Word では絵として
見え、読み上げにも意味が伝わり、こちらでは式として直せる。**書くだけで
読まないと「officework で書いた数式が、開き直すともう編集できない」**という
穴になるので、往復の検査を先に置いた(ooxml/src/tests.rs)。

**OMML は読まない。** 既存の docx の数式は「原文を控えて保存で返す」ままで、
読んで組み直すことはしない。理由は3つ:

  1. **失われてはいない。** 2026-08-10 の工事で往復は無傷になっている
  2. corpus の実物2枚(pandoc 製と LibreOffice 製)は**書き方が正反対**で、
     原文を控えるだけの段階でも穴が2つ出た土地。組版まで踏み込む値打ちに
     見合わない
  3. 読まないので、**既存の数式に絵を足すこともしない** — anchor を画像で
     置き換えて編集不能に劣化させる、という分岐がそもそも生じない

つまり **画面と紙に出るのは、これから officework で書いた数式だけ**。
既存文書の数式は今までどおり出ない。そこは黙らずにそう言う。

### 実装の在り処

  officework/tex.py …… LaTeX → SVG / PNG。fit() が mathtext のために
    寄せる(環境 → substack、`\int\limits` → `\int`、`\le` → `\leq`)。
    寄せられないものは Muri で断る — **理由は mathtext の言い分をそのまま渡す**
  writer/src/py.rs …… その tex.py を **include_str! で埋め込む**。写しは
    作らない(実体は一つ)。おかげで pip install officework は要らず、
    要るのは matplotlib だけ(calc の CHART_PY などと同じ前提に揃えた)
  InlineImage.tex …… 原文の置き場。普通の画像は None

### 踏んだ穴(実機でしか出なかった)

**囲いの中から officework が見えない。** bwrap は /home を tmpfs にするので、
.venv と PYTHONPATH の置き場を ro-bind で見せないと import で落ちる。
押しても**何も起きずに終わる**ので、試験では出ない。
(いまは埋め込みにしたので officework 自体は不要だが、.venv は要る)

**同じ絵が二度描かれる。** 組版は `images`(読み込んだ絵)と `images_new`
(このアプリで足した絵)の**両方**を描く。足すときに両方へ入れると画面と紙で

いまは writer の試験が模型と組版の両方を見て縛っている。

### 残した宿題

  桁が不揃いな行列は mathtext だと崩れる(TeX があれば揃う)。列を揃える
    空白の入れ方は中身を見て決めるしかないので、AI に整形させる案が残る —
    **結果は LaTeX として文書に残る**ので、実行時に AI は要らない
  文中の数式は段落の頭に寄る。`anchors` の持ち方の限界で、画像も同じ問題を
    抱えている。直すなら模型の作り替えで、画像とまとめてやるべき

### 模型 — Document の意味の部分集合+Theme

新しい模型は作らない。**ネイティブ文書 = `Document` の意味の部分集合**:

- run に許す: 強調(strong/em — bold/italic の意味側)・ルビ・脚注・リンク・
  参照(field)・記入欄(sdt)・`style_id`
- 段落に許す: 役割(`ParaStyle` — 引用 `Quote` を足す)・リスト・`style_id`
- **見た目の欄(size_pt・font・color・shade・boxed・spacing…)はネイティブ
  では常に空** — 書くのはテンプレートだけ

`Theme`(テンプレートの読み込み結果)はスタイル名 → 段落書式+文字書式の表
+ページ設定+ヘッダー/フッター(差し込みの札つき)+表紙の組み方。TOML。

合成は1関数: 意味の Document の**写し**にテーマの書式を流し込み、出た
Document を今の `layout.rs` へ渡す(一方通行 — 写しから意味を推測して戻す
ことはしない)。**run 粒度の編集モデル(splice_text / normalize_runs)は
制限された Document の上でそのまま生きる。**

### UI — 封じ方

- ネイティブでは B / I は**強調**(意味)。見出し・引用・リストは今の道具のまま
- 大きさ・色・書体・塗りの操作は遮り、「この見た目に名前を付けてスタイルに」の

### テンプレートは指示する人が作る

役割の分け方が、そのまま画面の決まりになる。

- **書く人**は本文だけを書く。見た目のボタンはスタイルの一覧へ案内する
  (`Writer::LOOK_IDS`)
- **指示する人**がテンプレートを作る。役所の様式・社内の書式規程・学会の
  体裁は、この人の持ち物
- **配られたテンプレートは書き替えない。** 書式を直すと、書き先はいつも
  文書の隣になる。元が別の場所(置き場のテンプレートや同梱の既定)だった
  ときは「この文書だけの写しを作りました」と言う(`Writer::tmpl_path`)。
  黙って分かれると、配り主が元を直してもこの文書だけ古いままになる

Word にもスタイルはあったのに使われなかったのは、直接書式が同じくらい簡単
だったから。**簡単さの順番を入れ替える**のがこの設計の効き目で、役割の分け方は
その裏づけになる。

### 書式は増やさない(2026-08-18 発注者)

発注者「どちらにしても、複雑な書式にはしないほうがいいですね」。決めたのは
3つ。

1. **入れ子は3段で止める。** `[文書]` → 段落のスタイル → 文字のスタイル。
   内側が勝つ。Word の `basedOn`(スタイルがスタイルを継ぐ鎖)は入れない。
   たねの森のページを数えたとき、`styles.xml` の 9,060 要素はほとんどが
   この鎖だった。3段なら「その色はどこから来たか」を1行で言える
2. **1つの文書に効くテンプレートは常に1枚。** フォルダをまたいで合成しない
   (親フォルダの書式と混ぜない)。どの1枚かは状態行に出る
3. **鍵は12個で打ち止め。** 字に効くのが6つ(大きさ・書体・太字・斜体・
   下線・色)、段落に効くのが6つ(背景色・揃え・字下げ・前の空き・
   後の空き・行間)。手引きにも「この12個だけ」と書いた

**字下げは 2026-08-18 に足した**(発注者「でも、段落の書式が必要ですね」)。
模型は前から `first_line_twips` を持っていたが、**紙面では使っていなかった**。
書き方は全角の文字数(`字下げ = 1`)— 人が「1字下げ」と言うとおりに書ける。

組み方は、**1行目だけ行長を縮めて x をずらす**。最初は幅を持つ空白の桝を
1つ置く形にしたが、**画面と幅が合わない** — 桝の幅はこちらが決めても、
画面は空白の字をフォントの幅で描く(実機で見て気づいた。engine の数字は
3.70mm、画面は 2px しか空いていなかった)。

#### 「画面と紙は同じ紙面」はやめた(2026-08-18 発注者)

発注者「『画面と紙は同じ紙面』という約束はやめにしたら」。書き出し先ごとに

> **数える所は紙で数える。** 目次・図表目次・相互参照のページ番号と、

#### 処理の形(本家の言い方に合わせる)

発注者が本家の説明を引いた(2026-08-18):

> AsciiDoc は**書くための形式**であって、出すための形式ではない。ワープロの
> ような WYSIWYG ではない。書くのは AsciiDoc の原文で、処理系が変換して
> 出来た物を配る。処理系はまず原文を読んで**構造のある文書**にし、それを
> **変換器**に渡して出力の形にする。どの変換器かは **backend** で決まる。

うちの部品を本家の言い方に置き直すと、こうなる。

| 本家 | うち |
|---|---|
| AsciiDoc の原文 | `.adoc` の本文 |
| 処理系(読む所) | `kumihan::adoc::parse` |
| 構造のある文書 | `kumihan::Document`(模型) |
| 変換器 | `html_write`(HTML)・`paper`(PDF)・`ooxml`(docx)・`layout`+writer の画面 |
| backend の指定 | **無い。ボタン(書き出し先)で選ぶ** |
| 言語と変換器は結合していない | `adoc.rs` は出力を1つも知らない |

**writer の画面も変換器の1つである。** ここが要で、画面は紙の姿ではなく
「読み書きしやすい姿」でよい。「画面と紙は同じ紙面」をやめたのはこの筋に
沿っている。

**原稿の姿で書ける**(実機で確かめた)。フォルダのテンプレートに
`横幅 = "可変"` と `区切り = "なし"` を書けば、画面は窓の幅で組まれ、ページに
折られず、1本の流れになる。同じ本文が、紙のテンプレートでは A4 になる。

このとき**紙の幅も窓に合わせる**(`paper_w_mm`)。前は紙だけ A4 のままで、
窓の広い機械では本文と表が紙からはみ出していた。行長も左右の余白を紙と同じ
だけ空ける形にした(前は 16mm の決め打ちだった)。

### テンプレートは AI が作る — ここが要(発注者 2026-08-16)

「テンプレートを AI が作ってくれるというのが大きい」。この設計の効き目の
中心はここにある:

- Word でスタイルが使われなかったのは、**定義する手間**が直接書式より
  重かったから。テンプレートが TOML のテキストなら、「役所に出す様式で」
  「社内報告書らしく」と頼めば AI が丸ごと書ける — 定義の手間が消える
- だからテンプレートは**テキスト形式一択**(zip や独自形式にしない)。
  AI が読み書きでき、人が差分を読める
- 左パネルの AI の仕事に「テンプレートを書く・直す」が加わる。
  「見出しをもっと詰めて」→ AI がテーマの数字を直す → ライブ合成で全頁に
  効く、が対話の1往復で回る

### 媒体はテンプレートの違いでしかない — 組み方の3つの値(発注者 2026-08-16)

「テンプレートだけ変更すれば、Web やアプリビルダーも作れる。こちらは
横幅可変、ページ区切りなし。PowerPoint は、文字がページを跨がらない。
**それだけのこと**」。

媒体の違いは、テンプレートが持つ**組み方の3つの値**に還元される:

| 媒体 | 横幅 | 区切り | 跨ぎ |
|---|---|---|---|
| 紙(docx / PDF) | 固定(mm) | ページ | **跨ぐ**(文が次の頁へ流れる) |
| Web / アプリ | **可変** | **なし**(1本の流れ) | — |
| 発表(スライド) | 固定 | 1節=1枚 | **跨がない**(枚に収める) |

- 本文(意味)は3つとも**同じファイル**。スタイルの表も同じ。違うのは
  組み方の3値と寸法・配色だけ — だから「テンプレートだけ変更すれば」になる
- **アプリビルダーの正体**: 記入欄(sdt)を持つネイティブ文書 × Web の
  テンプレート = 記入して送る画面。writer の HTML(閲覧と記入・JS なし・
  2026-08-04)と記入欄の資産がそのまま材料になる — 新しい仕組みではなく、
  既にある2つが組み方1つで繋がる
- 発表用のアプリ(pptx エディタ)は**建てない**。同じ文書に発表の
  テンプレートを掛け、紙面の代わりに枚の面で組む(layout.rs の同族 —
  「跨がない」は折り返しの禁止という1つの制約)
- pptx は docx と同じく**書き出し口の1つ**(必要になったら)
- 「アプリは増える」(2026-08-12 の全体設計)の pptx の枠はこの形で受ける —
  アプリではなく、テンプレートと組み方が増える

実装の順は変えない(A〜D が先)。組み方の値をテンプレートの器に足すのは、
**最初の紙以外の組み手(Web の流し組み)が入る便で** — 効かない切替を
先に置かない(できないことを、できるように見せない)。

### 入った分(2026-08-17)

`[組み方]` の節に**3値とも**入れた:

```toml
[組み方]
横幅 = "可変"     # 紙の幅ではなく窓の幅で組む(Web)
区切り = "節"     # 見出し1 ごとに1枚(発表)。他に "ページ" と "なし"
跨ぎ = false      # 段落が枚を跨がない(発表)
```

- 組み手(`relayout`)と**数え手(`refresh_hf`)の両方**に通す。組み手が
  折らないのに数え手だけ折ると、1本のはずの流れが「3ページ」と言われる
  (実際に踏んだ)
- 効くのは**ネイティブ文書だけ**。互換(docx)は紙のまま

#### 発表(1節=1枚・跨がない)の実装(2026-08-17)

**どちらも「折り手に折らせる」**。組んだ後の紙面に頁の境だけ足すのではなく、
**合成した写しの段落に改ページの印(`page_break_before`)を付けて組み直す**
— docx の `w:pageBreakBefore` と同じ道で、`<<<` の改ページも通っている道。

- 1節=1枚: `theme::compose` が、`区切り = "節"` のとき見出し1 の段落に
  印を付ける。印は**写しの側**にだけ付く — 意味の正本は「ここが節の頭だ」
  としか言っておらず、そこで紙を改めるかはテンプレートの決め
- 跨がない: 組んでみて境を跨いだ段落があれば、その段落に印を付けて
  組み直す(1回に1段落。段落の数で必ず止まる)。自分で頁の高さを
  数えないのは、本物の折り手(脚注が本文の底を上げる)と食い違わないため
- そのため組みの本体は `Look::lay_once` に括り出した(`self` を借りずに
  何度でも組める形)

**踏んだ穴(2026-08-17)**: 最初は組んだ後の `Sheet::breaks` に境を足した。
枚数は 1→3 に増えたので試験は緑になったが、**実機で1枚目が見出しだけに
なった**。巻物は空きを詰めて流れるので、後から境を足しても行は動かない。
さらに、頁の割り当てを**紙の上端(`offsets`)**で決めていたのも誤りで、
上端は最初の行より余白ぶん上にある — 境に使うと前の頁の末尾が次の頁へ
化ける。割り当ては **`starts`(その頁の最初の行)** で決める形に直した
(`fold_print` / `fold_pages` / `page_of_roll`)。これは発表に限らない
**元からの穴**で、普通の文書でも頁末の1行が化け得た。

### 3つのビルダーを作った(2026-08-17)

発注者「時間の関係で当面は adoc 優先で、web ビルダー、アプリビルダー、
帳票ビルダーを優先」。3つとも「同じ本文にテンプレートを掛け替える」ので、
既にある仕組みの上に乗った。

**土台は HTML の書き出し**(`engine/src/html_write.rs`)。本文が HTML、
テンプレートが CSS になる。見た目を HTML に埋め込まないのが要で、埋め込むと
テンプレートを差し替えても何も変わらないものが出来上がる。

- **Web ビルダー** = HTML の書き出しそのもの。ファイルの面から
- **アプリビルダー** = 記入欄を form として出す。送り先はテンプレートの
  `[送り先]`。**送り先が無ければ form で包まない**(押しても何も起きない
  用紙を作らない)
- **帳票ビルダー** = `engine/src/fill.rs`。`{{名前}}` の差し込みと、

#### 決めたこと

**記入欄は意味である。** 前は「記入欄は docx だけの機能」としていたが、
「ここに名前を書く」は指示であって見た目ではない。意味だけの本文に書けな
ければ、意味だけの文書から申込用紙が作れない。adoc に `field:タグ[表示名,種類]`
を足した(ルビと同じ書き方に揃えた)。

**差し込みは文書の模型の上で行う。** 出力形式ごとに書くと、同じ雛形が PDF と
HTML で違う結果になる。模型の段階で埋めれば、PDF も HTML も docx も同じ。

**分からない名前は黙って空にしない。** `{{名前}}` のまま残して報告に挙げる。
空にすると「金額の欄が空いた請求書」が何も言わずに出来上がる。

**増やす印を別に書かせない。** `{{明細.品名}}` が入っていれば、その行が明細の
行だと分かる。書く人が覚えることを増やさない。

#### 残っていること

- 帳票を writer の画面から扱う道(いまは Python から)
- 記入欄を writer の画面から挿す道(いまは本文に `field:` と書く)
- 送り先へ実際に送った結果を受け取る仕組み

### やらないこと

- 互換モードの廃止・「開いたら常に蒸留」— 受け取った文書を黙って別物にしない
- ネイティブ独自の付帯データ(コメント・履歴の容れ物)— git の仕事
- 新しい組版エンジン — layout.rs は無傷
- 発表用の別アプリ(pptx エディタ)— 発表はテンプレートの1種
