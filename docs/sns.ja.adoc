作業用の文書です。利用者向けのマニュアルではありません。
投稿の文面は利用者が読むので、docs/ の手引きと同じ言葉の決まりで書きます
(CLAUDE.md の「言葉づかい」)。

== 受け持ち

SNS 担当(Claude)がすること:

* 投稿の文面を英語と日本語で書き、この文書に置く
* 投稿に使う写真を、リポジトリにある物(web/assets)か、自分で作った文書から用意する
* 出す前の確認(下の一覧)を通す
* 反応(不具合の報告、質問)への返事の下書きを書く

発注者がすること:

* アカウントを持ち、投稿のボタンを押す(push と同じで、外に出す操作は発注者がします)
* 報酬や募集の条件のように、お金と人に関わる決めを下す

== 決め

. **動いている物だけを書きます。** 手引きと紹介ページ(web/main.py)と同じ決めです。「〜できます(予定)」は書きません。これから作る物は「作っています」と書きます。
. **数字には日付を付けます。** 例:「2026 年 9 月 19 日の時点で 288 枚のうち 246 枚」。数字は SEKKEI.adoc の突き合わせの記録(「docx の Word 比較」の回ごとの集計)と紹介ページ(web/main.py)の数字と同じ物を使います。
. **写真に使えるのは、自分の文書と、役所が公開している様式です。** Word のテンプレート(web/gallery の物)は Microsoft の著作物なので、試験に使うのが基本です(SEKKEI.adoc「Word のテンプレートを英語版と日本語版で全部通す」)。ただし 1 つだけ、次の形で出します(2026-09-19 発注者「1 個ぐらいはあってもいい」)。Microsoft の決まり(https://www.microsoft.com/en-us/legal/intellectualproperty/permissions)は、画面の写しを宣伝や Web に断りなく使ってよいとしていて、条件は、大きさを変える以外に手を加えない、一部を切り出さない、「Used with permission from Microsoft」と添える、製品名を「Microsoft Word」と正式に書く、Microsoft が推していると読める書き方をしない、第三者の物が写っていない、です。
* 写真やイラストの入っていないテンプレート(請求書、議事録、送付状、履歴書など)を選ぶ。中の写真は Microsoft が借りている物なので避ける
* Word の窓ごと写す。aiseed office も窓ごと。切り出さない
* 添え書き:「Microsoft Word のテンプレート『○○』を、Microsoft Word と aiseed office で開いた物です。Used with permission from Microsoft」
* テンプレートのファイルは置かない。ダウンロードして試す形は役所の様式だけ
* 選ぶのは、英語版の比較で頁数と行の位置が合った物の中から
. **英語が先です。** 発注者の決め(2026-09-19)「日本に訴えるよりもまず世界に訴えた方がいい」に従い、英語の投稿を先に出し、日本語は同じ内容を後から出します。
. **売りは 1 つです。** 「受け取った docx と xlsx を、Word と Excel と同じに開いて刷る。同じファイルを両方で開けば誰でも確かめられる」。機能の数や AI の話は、この売りの後に添えます。
. **秘密の値と人の情報は出しません。** 様式を送ってくれた人の名前は、本人が認めた場合だけ、docs/corpus-docx.ja.adoc に書く形で残します。投稿には出しません。
. **同じ言葉の決まりで書きます。** 比喩や造語を使いません。Word と Excel のヘルプの言葉を使います。

=== Flet の位置づけ(2026-09-20 発注者「Flet を、これらを使う場合のカスタマイズ用のツールに」)

連載の一式(PocketBase、Forgejo、Stalwart、Jitsi、Cal.com、FastAPI、Ollama、aiseed office)は、それぞれ API を持ちます。その間をつなぐ小さな画面を作る道具が Flet です。承認と差し戻しの画面(3 段目の「人が決める」)、様式に打ち込む画面、様式を見て刷る画面、集計を見る画面。どれも Python 1 枚で、PocketBase の認証の後ろに置けます。各道具の管理画面や公開の Web(Cloudflare Pages)は作り直しません。作るのは、その一式を自分の業務に合わせる所だけです。

ビルダーの会の題は、この位置づけです。「連載の一式を自分の業務に合わせる画面を、Flet で 1 枚作る」。例は、様式に打ち込んで PDF にして、PocketBase に記録する画面。紹介ページと印刷の見本は、その途中の形として使います。

=== 2 本立て(2026-09-20 発注者「普通の人に参加してほしい」)

ビルダーの会は開発者向けです。普通の人(中小企業の事務の人、顧問)には別の会を開きます。

* ビルダーの会: この節の「AI と一緒に、自分の業務の画面を 1 枚作る」
* 普通の人の会: 「自分の様式を持ってきて、同じに開いて、刷る」だけの会。コードは出さない。持ってきた docx / xlsx を Word と aiseed office で並べて、「ここが違う」をその場で言ってもらう。テスターの募集と同じ物になり、差があった様式は集めに入れる(本人が認めた物だけ)。入るのに要る物はアカウント無し、インストーラー 1 つ、自分のファイル

. ビルダーとは何か(10 分)。AI がコードを書く。人は、何を作るか決め、AI と対話し、出てきた物を確かめ、既存の物と組み合わせる。連載「AI ネイティブな仕事の作法」の導入編(https://aiseed.dev/ai-native-ways/software/)がそのまま元。個人開発者(1 人で全部を書く人)は、ソフトウェアだけをやっていれば AI に代わられる。ビルダーになって、コミュニティで働く。業務を知っている人、他のビルダー、道具の作者と一緒に、既存が埋めない隙間を埋める。具体的な仕事は 2 つ。組織に OSS の一式(連載の自立編)を入れて動かすこと、その上に業務の画面と基幹の流れ(様式に書く → 受け取る → 処理する → 様式で返す)を Flet と Python で作ること。これをできる人はいまほとんどいなくて、SIer は金にならないのでやらない。汎用の物を作っても評価されず、評価されるのは隙間と自分だけが知っている業務。ソフトウェアの中は AI の世界で、人は外に出て答えを決める
. 自分の業務の画面を AI と作る(25 分)。連載の一式(PocketBase、FastAPI、aiseed office など)をつなぐ小さな画面を、Flet で 1 枚、その場で AI に書かせて動かす。例は、様式に打ち込んで PDF にして記録する画面。道具に Flet を使う理由は 3 つ
* 言語が 1 つ。HTML と CSS と JavaScript を分けず、Python のファイル 1 枚で画面と処理が書ける。`pip install flet` と `flet run` だけで動き、間違いは Python の例外で出る。AI に書かせて、動かして、直す、の回転が速い
* 手元でそのまま動く。HTML はブラウザが手元のファイルに触れさせないので、手元で動かすにはサーバーか Electron のような包みが要る。Flet は Flutter の窓で開き、処理は同じ Python なので、手元のファイルにも、officework のエンジンにも、プリンターにも、手元で動く AI にもそのまま触れる。`flet build` で Mac・Windows・Linux のアプリになり、同じコードが `--web` で Web にもなる
* ノーコードとの違い。AI を使えば、人はコードを書かなくてもいい。ノーコードは、人がコードを書けない。書かなくてもいい、は、書きたければ書ける、直したければ直せる、ということで、コードが手元に残る。残ったコードが Python なので、できることに天井が無い。言い方に注意: 「人が書かない」と「コードが無い」を分け、保管し(git)、動かし、確かめる人(ビルダー)が要ることを言う
+
VB との比べ(フォームに部品を置き、イベントに処理を書く、言語は 1 つ、の同じ形。VB と違って Mac・Windows・Linux と Web で同じコードが動く)と、印刷(flet-printing。sample/flet_insatsu)も、ここで見せる
. 動かし続ける(10 分)。作れることと動かし続けられることは別。版は止めずに保守する(Flet 1.0 で `page.launch_url` が消えて直した記録)。答え合わせを作る(役所の様式 288 枚と Word の PDF の比較)。ビルダーの仕事の半分はここ
. 質問(15 分)。答えられない物は #日本語 に持ち帰って書く

SIer と情シスの代わりは AI ができる。だから、現場を本来の姿に戻すだけ。現場でソフトウェアの開発もできるようにするだけのこと(2026-09-20 発注者)。現場はもともと、自分の仕事を自分の道具でやっていた。ソフトウェアが難しかったから、外に SIer、中に情シスという回り道ができた。AI がその難しさを取ったので、回り道を無くして、現場が自分の様式と自分の画面を持つ元の形に戻す。業務の人とビルダーと AI で直に作れる今、間の役は費用と時間と責任の押し付け合いを足すだけ(「AI 時代に SIer と情シスは要らない」は同じことの裏の言い方。外に出すときは「戻す」の側で言う)。細かい所: ベンダーの営業はライセンスで食べるので OSS を売らない。社内の情シスは「何かあったとき誰が責任を取るか」で測られるので、責任の置き場が無い OSS を避ける。外に出す文では「現場を本来の姿に戻す」の側で言う。通る道は 3 つ: (1) 情シスの無い組織(中小企業)から始める。業務の結果に責任を持つ人(社長、部門長)に直に話す。(2) 責任の置き場を作る。有料サポートで名前のある人が受ける。(3) 確かめられる形にする。同じファイルを両方で開けば分かる、データはファイルのまま残るので、やめても持って出られる(ロックインが無い)。連載の転換編 1(企業は自分でコードを書かない)と 4(ロックイン)がこの話。証拠: 有料サポートの窓口と、様式の比較

== 出す前の確認

投稿を出す前に、この順で見ます。

. 書いてあることは、いま動いている物か(手引きに載っているか)
. 数字に日付が付いているか。数字は SEKKEI.adoc の突き合わせの記録と同じか
. 写真は自分の文書か、役所の公開の様式か(Word のテンプレートではないか)
. 人の名前、ファイルの中身、秘密の値が写っていないか
. リンク先は開くか(紹介ページは公開後だけ)
. 言葉づかいは普通か(CLAUDE.md の表の言葉が入っていないか)
. 英語は 280 字、日本語は 140 字を目安に収まっているか
