# ExcelにPythonが搭載？その後の、その後 — 待つのをやめて自分で作った

8年前、マイクロソフトが Excel に Python を搭載するかどうかアンケートを実施した、というニュースがありました。Python Advent Calendar 2017 で「[ExcelにPythonが搭載？](https://qiita.com/yniji/items/2e80ace081c4b59bc327)」を書き、翌年の 2018 年には続編として「[ExcelにPythonが搭載？その後 - xlwings を使おう](https://qiita.com/yniji/items/b38bc312e860027108ac)」を書きました。

前回の記事は、こう締めくくっていました。

> 非公式の回答には 'In the meantime' とあるので、将来的には Excel に Python が搭載されると思っていいのではないでしょうか。そう期待して、今から xlwings を使いましょう。

搭載されました。期待は当たりました。**それでも、自分の仕事では使えませんでした。**

この記事は、その顛末と、結局どうしたかの話です。

## 搭載された。ただしクラウドで

2023 年 8 月にプレビューが発表され、2024 年 9 月 26 日に「Python in Excel」が正式リリースされました。Anaconda と組んでいて、pandas、Matplotlib、scikit-learn、seaborn といった定番のライブラリーが使えます。セルに `=PY(` と打つとセルが Python のエディターになり、`xl("A1:B10")` でセルの範囲を受け取れます。8 年前に投票していた人たちが望んでいたものが、だいたいそのまま出てきた形です。

ただ、実行される場所が手元ではありませんでした。

計算は **Microsoft Cloud（Azure）のコンテナ**の中で走ります。ハイパーバイザーで隔離された専用コンテナで、ブックを開いている間だけ生きていて、外向きのネットワークは持ちません。データは保存されず、第三者に渡されず、AI の学習にも使われない。GDPR と EUDB に準拠していて、EU の顧客のコンテナは EU で動く。

かなり真面目に作られています。マイクロソフト自身の説明は「ローカルのマシンで Python を安全に動かすのは難しい問題なので、まずクラウドから始めた」というものでした。技術的にはその通りだと思います。

問題は、そこではありませんでした。

## 難しい問題は、1 年足らずで解かれた

先に書いておきます。2024 年 7 月、Anaconda が「[Anaconda Code](https://www.anaconda.com/press/anaconda-code-toolbox-python-in-excel)」という Excel アドインを公開ベータで出しました。**手元で** Python が動きます。

仕組みは PyScript / Pyodide、つまり **WebAssembly にコンパイルした CPython** です。numpy も pandas も scikit-learn も WASM の砂場の中で動き、ネイティブの CPython をインストールする必要すらありません。ランタイムはワークブックに同梱するか、アドインが供給します。

「ローカルで安全に動かすのは難しい」と言われた問題は、1 年足らずで解かれました。しかも解いたのは、クラウド実行で組んだ相手方である Anaconda 自身です。

ここで、前回の記事に書いたことを思い出してください。マイクロソフトが Excel に載せると決めた言語は **JavaScript** でした。そして Office のアドインとカスタム関数は、**手元のサンドボックスの中で JavaScript を動かしています**。つまり「他人が書いたコードを、利用者の機械の上で、隔離して動かす」仕組みを、マイクロソフトは何年も前から Excel に積んでいるわけです。

その上で、Python にだけ「ローカルで安全に動かすのは難しい問題です」と言いました。

私はこれを、技術上の説明としては受け取っていません。クラウド実行なら Microsoft 365 の契約に紐づけられます。ローカル実行では紐づけられません。**難しかったのは技術ではなく、無料で使われては困るという事情の方**だったのだと思っています。

8 年前、Excel チームは「Python への熱狂を見られてうれしい」「アンケートには素晴らしい反響があった」「その反響に応える最善の方法を検討している」と書きました。断トツの投票数を集めた要望に対して、その後 5 年沈黙し、出てきたのは月額の要る、データが社外へ出る形でした。要望した人たちが求めていたものとは、違うものだったと思います。

そして WebAssembly はもともとブラウザーで動くものです。この道が通るなら、**Excel の Web 版でもスマホ版でも、同じやり方でローカル実行ができます。** クラウドを経由しなければならない理由は、もう技術の側には残っていないことになります。

では、これで私の問題は解決したのか。半分は解決しました。データは手元から出ません。

ただ、Anaconda Code の売り文句には、こう書かれています。

> keeping all code and data within the workbook
> （コードとデータを、すべてワークブックの中に保つ）

**実行する場所は変わりましたが、コードの置き場は変わりませんでした。** むしろ「ランタイムごとワークブックに入る」ので、以前より濃くなっています。

## 何が引っかかったか

自分が Excel を使うのは、事務の仕事です。見積書、請求書、台帳、様式。そこで扱っているのは、**外に出せない紙**です。

- 閉域網の中にいて、そもそも Azure に届かない
- 届いたとしても、顧客名簿を「計算のために」社外へ出す説明が、規程の上で立たない
- 「保存はされません」は本当だと思いますが、**通ったかどうか**を問われる場面が実際にあります

データ主権の話は、感情論ではなく手続きの話です。「安全です」ではなく「出していません」と言えるかどうか。多くの現場が基幹を共有フォルダーの xlsx で回し続けているのは、後ろ向きだからではなく、それが要件だからです。

それから、これは **Microsoft 365 のサブスクリプションが要ります。** 前回の記事で PyXLL を「年 $330 の使用料が必要になってくるので、個人や一般的な会社で手軽に使えるものではない」と外したのと、同じ物差しが当たります。買い切りの Excel を持っているだけでは使えず、払い続けている間だけ動く。現場が自分の判断で試せる道具ではなくなります。

もうひとつ、引っかかったことがあります。**コードがセルの中に入る**ことです。

`=PY(...)` の中身は、そのブックの一部として保存されます。つまりデータとプログラムが 1 つのファイルに同居する。これは .xlsm がやっていたことと、形の上では同じです。VBA の 20 年で私たちが学んだのは、「ファイルの中のコードは、差分が見えず、レビューできず、テストできず、そして受け取ったファイルが実行の起点になる」ということだったはずです。

前回の記事で私は、xlwings のこの点を評価していました。

> xlwings の場合は、別の独立した Python スクリプト (.py) ファイルになります。
> VBA の場合には、あの古びた VBE という専用のエディターを使わないといけないのですが、xlwings は、自分が日常使っている好みのエディターやデバッガーが使えるというのは大きなメリットです。

8 年経って、この一文が自分にとっては一番大事だったのだと分かりました。

## xlwings は今も現役、ただし Excel が要る

では xlwings を使い続ければいいのか、というと、こちらにも壁があります。xlwings は「ファイルではなくて Excel そのものを操作するライブラリー」なので、**同じマシンに Excel が必要**です。前回の記事にも書いたとおり、Linux では使えません。

自分の環境は、この 8 年でほとんど Linux になりました。前回「今後は Linux でしか使わなくなると思うので」と書いたのは、半分は負け惜しみでしたが、結果的には本当になりました。

整理すると、欲しかったものはこうです。

- 手元で動く（クラウドに出ない）
- Linux で動く
- コードは .py ファイルで、データとは別
- xlwings の書き味

全部そろっているものが、ありませんでした。それで作りました。

## officework

[officework](https://github.com/aiseed-dev/officework) は、表計算（calc）とワープロ（writer）の 2 本立ての事務ソフトです。Rust で書いていて、GPU で描いています。Python の連携は、xlwings の書き味をそのまま持ってきました。

考え方は一行で言えます。**VS Code と Excel を合体させて、VBA を取り除いたもの。** 表は .xlsx、コードは .py、どちらもファイルとして別々にある。文書の中にコードを埋める仕組みを、そもそも持っていません。

### Jupyter Notebook から使う

前回の記事のコードが、import の 1 行を差し替えるだけで動きます。

```python
import pandas as pd
from officework import calc as xw   # ← ここだけ

df = pd.read_csv('data2015-2017.csv', encoding='cp932')

wb = xw.Book()                       # 空白のブックが立ち上がる
wb.sheets.active['A1'].value = df    # シートに表示される
```

編集したものを Python に戻すのも同じです。

```python
df1 = wb.sheets.active['A1'].options(pd.DataFrame, expand='table').value
```

`Book` / `Range` / `.value` / `options(pd.DataFrame, expand='table')` / `save` が、記事に書いたとおりに動きます。裏側は COM ではなく、この機械の中だけのユニックスソケットです。TCP は開いていないので、ネットワークには最初から出られません。

### 速さ

前回の記事では、処理時間を測って「480 ms 程度なので実用上の問題はないと思います」と書きました。同じ規模のデータ（1096 行 × 20 列 = 21,920 セル）で測り直すと、こうなりました。

| | 2018 年の xlwings | officework |
|---|---|---|
| 書き込み（DataFrame → シート） | 480 ms | **44 ms**（3 回の最速。平均 113 ms） |
| 読み出し（シート → DataFrame） | 95 ms | **65 ms**（平均 73 ms） |

8 年前の別のマシンでの数字との比較なので、そのまま何倍とは言えません。ただ、遅くなる理由が減っているのは設計の側から説明できます。

- **表の模型は Rust** です。Python にはそれを pyo3 で見せています（`office_sheet`）。openpyxl のように XML を組み直したり、COM でセルを 1 つずつ往復したりしません
- **動いているブックとのやり取りは、範囲をまとめて 1 回で渡します。** xlwings が遅かったのは COM の往復が積み上がるからで、前回の記事にも「Excel の API や マクロをどんどん使用すると処理が遅くなります」と書いていました
- **走るのはネイティブの CPython** です。WebAssembly ではないので、機械に入っている polars も scipy も matplotlib も、コンパイル済みのものがそのまま動きます

最後の一点は、Anaconda Code が選んだ道との対比になります。ネイティブの CPython は手元で速く、WASM はどこでも動く。どちらが上という話ではなく、**得意な場所が違う**だけです。

そして Anaconda Code は、私にとっては朗報でした。**Python が WebAssembly で実用になる**ことを、製品として示してくれたからです。おかげで、officework の進み方がはっきりしました。

- **据え置きの機械では、ネイティブで速く回す**（いまの pyo3 + CPython）
- **ブラウザーとスマホには、WASM で届ける**

この二段構えなら、外出先でスマホから台帳を開いて追記し、事務所に戻って同じファイルを手元の calc で開く、ということができます。事務の仕事は机の上だけで完結しないので、そこは早く用意したいところです。**ブラウザー版とスマホ版は、これから作ります。**

設計の芯はそのまま持って行けます。データとプログラムを分ける、という一本の線は、動く場所が変わっても変わりません。ブラウザーでは `~/.config/office/plugins` に当たる置き場をどうするかを決める必要がありますが、**コードがファイルとして表の外にある**という形は保てます。

### Excel から Python を利用する — に相当するもの

ここからが本題です。前回の記事では、この部分に一番長く紙幅を割きました。今回は、**書くことが減りました。**

前回の SPLIT 関数は、こう書いていました。

```python
@xw.func
@xw.ret(expand='table')
def xwsplit(text, delimiter=None, maxsplit=-1):
    return text.split(delimiter, maxsplit)
```

officework では、こうです。

```python
def xwsplit(text, delimiter=None, maxsplit=-1):
    return text.split(delimiter, maxsplit)
```

デコレータがありません。`~/.config/office/plugins/` に置いた .py の中の `def` は、それだけでセルから呼べます。`@xw.func` は xlwings が Excel という他人の家に「この関数を公開します」と登録するための仕組みで、アドインと COM サーバーがある以上どうしても必要でした。officework はセルの側が自分で plugins を読んでいるので、登録する相手がいません。

`@xw.ret(expand='table')` も要りません。**返り値の形が広がり方を決めます。** 2 次元のリストなら右下へ表として広がり、1 次元なら縦に伸びます。前回「dynamic array formula」と呼んでいたものは、いまはスピルという名前で Excel にも入りましたが、officework でも同じように動きます。

呼び方も普通です。

```
=xwsplit(A1, " ")
```

`=PY("xwsplit", ...)` のような包みは要りません。**関数の名前は日本語でも構いません。**

```python
def 消費税(金額, 率=0.1):
    return round(金額 * 率)
```

```
=消費税(D12)
```

これは見た目の趣味の話ではなく、事務の様式に日本語の名前で関数が書けることには実利があります。引き継ぐ人が読めます。

そして、**引数が変われば勝手に計算し直します。** 明示のボタンはありません。裏で別スレッドがまとめて回して、答えが揃ってから 1 手として書き戻すので、画面は止まりません。

### マクロ

前回の請求書マクロは `xw.Book.caller()` で呼び出し元のブックを取っていました。これはそのまま使えます。

```python
from officework import calc as xw

def 請求書作成():
    wb = xw.Book.caller()
    請求情報 = wb.sheets['請求書作成']['A1'].options(expand='table').value
    ...
```

`@xw.sub` は要りません。そして `Book.caller()` は、実は `Book.attach()` と同じものです。xlwings ではアドイン経由で呼ばれたときと Python から触るときで入り口が違いましたが、officework にはその境目がないので、同じものになりました。

呼ぶときは、データ > Python の欄に `@請求書.請求書作成` と打ちます。**動いているブックをそのまま操ります**（一時ファイルの複製ではありません）。何回セルを書いても、Ctrl+Z 一回で手続きの前に戻ります。

### コードはブックに入らない

ここが Python in Excel と一番違うところです。

- 人とやり取りするのは**データだけ**。受け取ったブックにコードは 1 バイトも入っていません
- 関数も手続きも `~/.config/office/plugins/*.py` にあり、1 機械 1 回の据え付けです
- だから「開いただけで他人のコードが走る」が、原理的に起こりません

Python in Excel が外向きのネットワークを持たないコンテナを用意しているのは、**ブックに入っているコードは信用できない**からです。信用できないコードを安全に走らせる、という難しい問題を、マイクロソフトは真面目に解いています。officework は、その問題を**持たないことにしました**。コードがファイルで旅をしないなら、隔離する相手がいません。

副作用として、サンドボックスも外しました。plugins に置く .py は、VS Code から走らせるスクリプトと同じ扱いです。外部の CSV を読むにも、社内 API を叩くにも、普通にファイルとネットワークが使えます。残る安全は「置く前に読む」の一点で、これは自分でスクリプトを書くときと同じ規律です。

### おまけ：セルの文字はマークダウン

作っているうちに気づいたことがあります。セルの文字列をマークダウンとして描くようにすると、**セルの中の一部だけを太字にする編集機能が要らなくなります。**

```
これは**太字**です
[こちら](https://example.com)を見て
# 見出し
- 箇条書き
```

セルが持っているのは平文のままです。解釈するのは画面に描くときだけなので、数式バーに出るのも、Python が読むのも、xlsx に保存されるのも、いつも同じ平文です。往復で化けません。

もちろん `2*3*4`（掛け算）や `-100` や `2026-08-09` が勝手に化けては困るので、書式として読めるものが 1 つも無ければ何もしません。囲みの中身が数字だけのときは書式にしない、という線で分けています。

## 8 年後の答え合わせ

前回の記事で期待していたことが、どうなったかを並べておきます。

| 2018 年に書いたこと | 2026 年の答え |
|---|---|
| Dynamic Arrays が早期にリリースされてほしい | 来ました。スピルとして定着し、FILTER・SORT・UNIQUE も入りました |
| 将来的には Excel に Python が搭載されると思っていい | されました。2024 年 9 月に正式リリース。ただしクラウド実行です |
| Excel と相性がいいのは JavaScript ではなく Python, R, Julia | これは今もそう思っています |
| 企業の情シスは Excel のマクロを撲滅したいと思っている | ここが一番効きました。**ファイルの中にコードが無ければ、撲滅する対象がありません** |
| xlwings の `@xw.func` / `@xw.ret` | 自分で作ってみたら、**どちらも要りませんでした** |
| （書いていなかったこと） | ローカル実行は WebAssembly で解かれました。**残ったのは「コードをどこに置くか」だけ**です |

最後の行が、作ってみて一番意外だったところです。あのデコレータたちは Python の都合ではなく、**Excel という他人の家に間借りするための手続き**だったのだと、家を建ててみて初めて分かりました。

## それで、どちらを使えばいいのか

前回の記事で、私は PyXLL をこう書いて外しました。

> PyXLLの方は優れた製品なのですが、商用で年 $330 の使用料が必要になってくるので、個人や一般的な会社で手軽に使えるものではないと思います。

この物差しは、今回も同じにします。

**Python in Excel は、Microsoft 365 のサブスクリプションが要ります。** 機能としてはよくできています。しかし、これは「Excel を持っていれば使える」ものではなく、**払い続けている間だけ使えるもの**です。8 年前に年 $330 を理由に PyXLL を外した自分が、これを勧めるわけにはいきません。すでに会社が契約していて、なおかつデータをクラウドに出せる立場なら、追加の出費なしに使えます。当てはまるなら使えばいい、という程度の話です。

**xlwings は、8 年前と変わらず無料でよくできたライブラリーです。** ただし Excel が必要で、その Excel が有料です。Windows か Mac で、すでに Excel がある人にとっては、追加の費用ゼロで一番手堅い選択だと思います。今も現役です。

**officework は無料です。** AGPL-3.0 のオープンソースで、Linux で動き、手元だけで完結します。閉域網の中にいるか、Linux で仕事をしていて、データとプログラムを分けたいなら、選択肢になると思います。私はそのために作りました。

事務の現場に道具を入れるとき、いくら掛かるかは機能と同じくらい重い条件です。「月いくら」が発生するものは、その時点で稟議の話になり、現場が自分で判断できなくなります。無料で始められて、続けるのにも金の要らないものから試すのが、順番として正しいと思っています。

8 年前に「そう期待して、今から xlwings を使いましょう」と書いた自分に、いま何か言えるとすれば、「期待は当たるが、当たり方までは選べない」ということでしょうか。待っていた機能は本当に来ました。ただ、来たものが自分の要件に合わなかっただけです。

そういうときに、自分で作れる時代になったのは、いいことだと思っています。8 年前は、Excel に Python が載るのを待つしかありませんでした。いまは、Rust と pyo3 で表計算の中身を書き、WebAssembly でブラウザーとスマホまで運べます。部品は全部そろっていて、しかも無料で手に入ります。

次はブラウザー版とスマホ版です。できたら、また続きを書きます。
